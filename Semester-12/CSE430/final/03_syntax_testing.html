Topic 01

Where syntax testing fits

Just enough of the big picture to place the technique — this is not the exam's focus.

Your lecture opens with the usual scaffolding of a testing course: what testing even is (Hetzel's and Myers' definitions — "establishing confidence" vs. "executing with the intent of finding errors"), who does it, the V-model connecting requirements/design/code to system/integration/unit testing, and the fact that testing can never give 100% confidence because time is limited and specifications are never provably complete. You should be able to recognise these as background if a short-answer question quotes them, but they are not what this guide drills — that is syntax testing specifically.

The lecture places syntax testing inside a family of functional (black-box) testing techniques — ways of designing tests purely from what the software is supposed to accept and do, without looking at its source code. The faculty's list is:

  1. Equivalence class analysis
  2. Cause–effect graphs
  3. Syntactic testing ← this guide
  4. Random testing
  5. Transaction analysis
  6. Testing based on models
  7. Testing state transitions

Notice syntax testing sits alongside equivalence classes and cause–effect graphs — all three are ways of turning "what counts as valid input" into concrete test cases, they just use different tools to describe validity. Syntax testing's tool is a formal grammar.

Key idea

Syntax testing is one specific black-box technique: it designs tests directly from a grammar that defines what a legal input looks like.

Topic 02

What is syntax testing, and why does input format matter?

Definition, straight from the slide, unpacked term by term.

Think about any place software accepts something structured from the outside world: a command typed at a prompt, a line in a config file, a date field on a form, a URL, a row in a CSV upload. Before the software can act on that input at all, it first has to agree that the input is even shaped correctly — the right pieces, in the right order, spelled the right way. Get the shape wrong (a missing colon, an extra field, a letter where a digit belongs) and nothing downstream matters, because the program should refuse the input before it ever reaches the "real" logic. Syntax testing is the discipline of testing that gate — the part of the software that decides "is this input well-formed or not?"

Definition (faculty's own wording)

Syntax testing is a type of black-box testing technique used to examine the format and the grammar of the data inputs used in a software application, whether external or internal. The grammar may be formally described in technical or established & specified notations such as BNF, and that description can then be used to design input-validation tests.

Syntax testing is performed to verify and validate both internal and external data input to the system, against the specified format, file format, database schema, protocol, and other similar things. Because it involves producing a large number of tests, syntax tests are generally automated.

Two things are worth sitting with here. First, "grammar" is not a metaphor — it is used in the same sense as a grammar for a natural or programming language: a set of rules saying which sequences of symbols are legal. Second, syntax testing only checks shape, not meaning. A string can be perfectly well-formed and still be nonsense in context — we return to that limitation later, because it is exactly the kind of thing exam theory questions like to probe.

Watch out

"Black-box" here means the test cases come purely from the input's specified format — not from reading the source code. It does not mean syntax testing ignores structure; the grammar itself is a very precise structural description, it is just a description of inputs, not of the program's internals.

Topic 03

BNF notation, built from zero

If you have never read a grammar before, start here — everything later depends on this.

Picture a recipe card that lets you substitute ingredients: "sandwich = bread + filling + bread", and then a second card says "filling = cheese or ham or peanut-butter". You never memorise every possible sandwich; you memorise the two small substitution rules, and any sandwich you can build by following them, one substitution at a time, is a "legal" sandwich. A grammar is exactly this idea applied to strings of text instead of food: a small set of substitution rules that together define every legal string, without anyone having to list every string by hand.

BNF stands for Backus–Naur Form (the slide's own note, "BKF – Bakus-Naur Form", is a misspelling of this — the standard name and spelling is Backus–Naur Form, and that is what you should write on the exam). It is simply a fixed way of writing substitution rules like the sandwich example, using a small set of symbols:

BNF symbol legend

<name> a non-terminal — a placeholder that still needs to be substituted, e.g. <letter> ::= "is defined as" / "can be replaced by" — separates the placeholder from its possible substitutions | "or" — separates alternative substitutions for the same placeholder

So a rule <letter> ::= a | b reads as: "the placeholder <letter> can be substituted by either the literal a or the literal b." The angle-bracketed name on the left is called a non-terminal because it is not yet part of the final string — it still has substituting left to do. The plain literal symbols on the right that never get further substituted (here, a and b) are called terminals — they are the actual characters that end up in the finished, legal string. A grammar is "finished" being applied to produce one particular string exactly when every non-terminal has been substituted away and only terminals remain.

Key idea

Non-terminal = a name in angle brackets that still needs replacing. Terminal = an actual literal symbol/word that appears in the final string. ::= means "is defined as"; | means "or".

One more idea from the lecture, stated as an equivalent way of thinking about the same grammar: instead of substitution rules, picture a finite-state machine (a diagram of states and arrows) — a "syntax graph" that a string either can or cannot be traced through from start to finish. BNF and a syntax-graph/FSM describe exactly the same set of legal strings; BNF just writes it as text rules instead of a picture. The slide mentions both ("the formal description is a BNF or an FSM") — for the exam, be ready to recognise either form, but the worked examples in this guide (and almost certainly on your exam, since it is what the lecture worked through) use BNF.

Watch out

Do not confuse the vertical bar | (which means "or", inside one rule) with writing two separate rules for the same non-terminal — both notations exist in different textbooks, but the lecture's own grammar always uses the single-rule-with-| style, e.g. <command type> ::= copy | rename rather than two lines. Match the lecture's style on the exam.

Topic 04

The three-step methodology

How you actually do syntax testing, in the order the lecture gives it.

The slide titled "How to Perform Syntax Testing?" lays out the methodology as three steps. Read them as a recipe you will repeat, almost word for word, on every practice question below.

  1. Identify the target language or format. Decide exactly what kind of input you are testing — a command, a date, a filename, a protocol message — before writing anything formal.
  2. Define the syntax of the language. Every input has some syntax, even if it was never written down (it might be "formally pre-specified" already, or completely "undocumented" and you have to reverse-engineer it from the spec or the code's behaviour). Write that syntax as a BNF grammar.
  3. Test and debug the syntax to ensure its completeness and consistency, using two kinds of test conditions:
    • Normal condition — use a covering set of paths through the syntax graph/grammar (enough test strings that every rule and every alternative gets exercised at least once) for the minimum necessary requirements.
    • Garbage condition — deliberately feed in invalid input, built so that it breaks one specific rule of the grammar, to check the software correctly rejects it.
Key idea

Step 1 says what you're testing, step 2 says what "correct" means for it (formally), step 3 is where you actually generate test cases — both the ones that should pass and the ones that should be rejected.

Topic 05

Generator vs. recognizer, and the two ways a routine can fail

The mental model that makes "who does what" click.

Once you have a grammar, there are naturally two roles in play, and it is worth being very clear about which one is which, because exam questions like to ask you to name them. The piece of software under test — the part of the program that reads an input string and decides whether to accept or reject it — is acting as a recognizer: given a string, it recognizes (accepts) it if the string is a legal member of the language, and should reject it otherwise. You, the tester, are acting as a generator: you use the grammar to generate strings — both strings that are legal (which the recognizer must accept) and strings that are illegal (which the recognizer must reject) — and throw them at the recognizer to see if its verdicts match what the grammar says they should be.

Roles (faculty's own wording)

"The routine is a string recognizer."    "The tester is [a] string generator."

Because the recognizer only ever has two possible verdicts (accept / reject) and the string only ever has two possible true statuses (valid / invalid), there are exactly two ways the recognizer can be wrong — and the lecture names both:

  1. The recognizer does not recognize a good string — it wrongly rejects a string that the grammar says is valid. (A "false negative" — the software is too strict.)
  2. It accepts a bad string — it wrongly accepts a string that the grammar says is invalid. (A "false positive" — the software is too permissive.)
Watch out

Both failure modes are real bugs, and one is not automatically worse than the other for an exam answer — but in practice, "accepts a bad string" is often the more dangerous failure, because garbage data then flows further into the system (a database insert, a shell command, a file operation) instead of being stopped at the door. If a question asks you to justify garbage testing's importance, that is the point to make.

Topic 06

Worked example: the copy/rename command grammar

This is the lecture's own running example — reproduced exactly, step by step.

The lecture wants to test a small command interpreter that only understands two kinds of one-line commands: copying a file, or renaming a file, where filenames happen to be built only from the letters a and b (a deliberately tiny alphabet, so the whole set of legal strings is small enough to reason about by hand). Applying step 1 of the methodology: the target language is "a copy-or-rename command over one- or two-letter filenames drawn from {a, b}".

Step 1 (of the worked example) — the grammar

Applying step 2 of the methodology, the syntax is written formally as BNF, exactly as given on the slide:

The grammar (verbatim from the lecture)

<command> ::= <command type> <file name> to <file name> <command type> ::= copy | rename <file name> ::= <letter> | <letter><letter> <letter> ::= a | b

Read it top-down, the way you'd read the recipe cards: a <command> is a <command type>, then a <file name>, then the literal word to, then another <file name>. A <command type> is either the literal copy or the literal rename. A <file name> is either a single <letter> or two <letter>s back to back. A <letter> is either a or b. Only four non-terminals, five terminal symbols (copy, rename, to, a, b) — and yet this already generates a precise, non-trivial little language.

Step 2 (of the worked example) — the derivation tree

A derivation tree is simply the record of which alternative you picked, at each non-terminal, while walking down from the grammar's starting symbol. Every branch point in the tree is a non-terminal that had a choice (marked "or" below, matching the lecture's own green "OR" markers); every leaf is a terminal symbol that actually appears in the output string. The lecture numbers every node 1–23 so that later it can talk about "covering" specific numbers — keep that numbering, it is reused in the next step and in the practice questions.

Derivation tree — numbered exactly as in the lecture
1 <command>
├── 2 <command type>
│     └─ 6 copy  (or)  7 rename
├── 3 <file name>            [1st file name]
│     └─ 8 <letter>  (or)  9 <letter><letter>
│           8 → 12 a (or) 13 b
│           9 → <letter>                    <letter>
│                  16 a (or) 17 b          18 a (or) 19 b
├── 4 to
└── 5 <file name>            [2nd file name]
      └─ 10 <letter>  (or)  11 <letter><letter>
            10 → 14 a (or) 15 b
            11 → <letter>                    <letter>
                   20 a (or) 21 b          22 a (or) 23 b

Read the tree as: node 1 always expands into nodes 2, 3, 4, 5 (that part is fixed, no "or" — every command has exactly this shape). Node 2 then has a genuine choice between copy (6) and rename (7). Nodes 3 and 5 are both <file name>, but they are two separate occurrences (the source filename and the destination filename) — each gets its own independent choice between the one-letter branch (8 or 10) and the two-letter branch (9 or 11). Every individual <letter> (nodes 8, 10, and the four leaves under 9 and 11) independently chooses a or b. One traversal from root to leaves, always picking one option at every "or", produces exactly one legal command string.

Step 3 (of the worked example) — deriving the test commands

Applying step 3 of the methodology (normal condition, then garbage condition), the lecture builds its test set by node coverage: pick the smallest set of valid strings whose derivation trees, laid on top of each other, touch every node in the tree at least once. This is the same instinct as branch coverage in code — every "or" choice should be exercised on both sides at least once across your test set, not just once overall.

Reasoning · why these commands, in this order

  1. copy a to b

    Pick the "everything short" path: copy (6), the one-letter branch for both filenames (8 and 10), each letter the first option (a). This single string already exercises nodes 1, 2, 3, 5, 8, 10 (non-terminals) and 6, 12, 15 (terminals) — a good first test because it is the shortest possible legal command and touches the "copy" and "one-letter filename" branches in one shot.

  2. copy aa to bb

    Now deliberately pick the other branch at node 3 and node 5 — the two-letter <file name> alternative — so the tree's two-letter machinery (nodes 9 and 11, and their four letter-leaves) gets exercised too. This covers non-terminals 1, 2, 3, 5, 9, 11 and terminals 6, 16, 18, 21, 23. Between test 1 and test 2, every non-terminal in the tree (1,2,3,5,8,9,10,11) has now been visited at least once.

  3. Terminals not yet covered after tests 1–2: 7 13 17 19 20 22

    Node coverage isn't finished until every leaf has appeared at least once too — so far both tests always picked copy (never rename — node 7 unused) and always picked the first letter option at nodes 8, 9's-left-letter, and 11's-right-letter branches in various spots. Checking node-by-node against the tree above shows exactly these six leaves are still untouched.

  4. rename b to a

    Switches node 2 to rename (7, finally exercised), and picks the "second" letter option where tests 1–2 had picked the first: b at node 8 (13) and a at node 10 (14). Covers terminals 7, 13, 14 — matching the lecture's own note.

  5. copy bb to aa

    Back to copy, but now flips every remaining not-yet-seen leaf inside the two-letter branches: b for both letters of the first filename (17, 19) and a for both letters of the second (20, 22). Covers terminals 17, 19, 20, 22 — the last four still missing.

Result

These four strings together — copy a to b, copy aa to bb, rename b to a, copy bb to aa — touch all 23 numbered nodes of the derivation tree at least once. That is the "normal condition" test set finished. Garbage-condition strings (deliberately breaking one rule each) are worked in the practice questions below, since the lecture slides stop at the valid set.

Watch out

Node coverage is a minimum, not a guarantee of correctness — it only promises every rule was exercised by some test, not every combination of rules (e.g. no test here uses rename together with a two-letter source filename). For a small grammar like this you could also just test every possible string; the coverage approach is what scales when the alphabet or the strings get bigger.

Topic 07

Practice questions

Work these with pen and grammar in hand before opening any solution.

Question 1 · easy

In the grammar
<command> ::= <command type> <file name> to <file name>, <command type> ::= copy | rename, <file name> ::= <letter> | <letter><letter>, <letter> ::= a | b — list every terminal and every non-terminal symbol.

Show worked solution

  1. Non-terminals: <command>, <command type>, <file name>, <letter>

    A symbol is a non-terminal exactly when it appears in angle brackets and has a rule (a ::= line) that defines it. These four are the only names to the left of a ::= anywhere in the grammar.

  2. Terminals: copy, rename, to, a, b

    A terminal is any literal symbol on the right-hand side of a rule that is not itself defined by another rule — it is where substitution stops. to is easy to miss because it looks like an ordinary word, not a special symbol, but it never appears in angle brackets and no rule defines it — so it is a terminal, exactly like a or copy.

Answer

4 non-terminals, 5 terminals — 9 distinct symbols total.

Question 2 · easy · short answer

In one or two sentences each: what does ::= mean in a BNF rule, and what does | mean? Then give the one-line definition of "generator" and "recognizer" from the lecture.

Show model answer
What this tests & where it comes from Pure vocabulary recall from the "Data Validation and Syntax Testing" slide and the BNF notation build-up (Section 3 of this guide) — the kind of definition question that opens a mixed-format exam.

::= means "is defined as" or "can be substituted by" — it links a non-terminal on its left to the possible things it can be replaced with on its right. | means "or" — it separates alternative substitutions for the same non-terminal, so only one of the alternatives is chosen at a time in any single derivation. Generator: the tester, who uses the grammar to produce test strings (both valid and invalid). Recognizer: the routine under test, which reads a string and decides whether to accept or reject it.

Question 3 · easy

Is the string Copy a to b (capital "C") a legal <command> under the grammar? Justify your answer using a specific rule.

Show worked solution

  1. <command type> ::= copy | rename

    This is the only rule that can produce the first word of the command. Its terminals are the exact literal strings copy and rename, lowercase.

  2. Copy ≠ copy

    BNF terminals are literal, case-sensitive strings — there is no rule anywhere in this grammar that produces a capital C. Even though a human reader would obviously understand the intent, the grammar has no way to derive Copy.

Answer

No — invalid. It violates the <command type> rule: Copy is not one of the literal terminals copy or rename. A recognizer that accepted this string would be committing the "accepts a bad string" failure mode from Section 5.

Question 4 · medium

Using the same file-copy grammar, derive three new valid test strings that were not among the lecture's own four examples (copy a to b, copy aa to bb, rename b to a, copy bb to aa). For each, show which rule/alternative was chosen at every non-terminal.

Show worked solution

Try your own three before reading these — any string not in the lecture's set of four is a valid answer, as long as every step follows a real rule.

  1. Target: rename aa to ab

    Choose: <command type> → rename; first <file name> → <letter><letter> → a,a = "aa"; literal to; second <file name> → <letter><letter> → a,b = "ab". Every non-terminal was expanded, every leaf is a legal terminal — the string is valid.

  2. Target: copy ba to a

    Choose: copy; first <file name> → two letters b,a = "ba"; to; second <file name> → one letter a. Mixing a two-letter source with a one-letter destination is perfectly legal — the two <file name> occurrences (nodes 3 and 5) choose independently.

  3. Target: rename a to bb

    Choose: rename; first <file name> → one letter a; to; second <file name> → two letters b,b = "bb". Again a legal, if previously untested, combination.

Answer

rename aa to ab, copy ba to a, rename a to bb — all derivable in one pass through the grammar, all distinct from the lecture's four.

Question 5 · medium

Construct three garbage (invalid) strings for the file-copy grammar. For each one, name the exact rule it violates and explain why.

Show worked solution

  1. copy abc to a

    Violates <file name> ::= <letter> | <letter><letter>. A <file name> can only ever be exactly one or exactly two letters long — there is no alternative that produces three. abc cannot be derived by any sequence of substitutions from this grammar.

  2. move a to b

    Violates <command type> ::= copy | rename. move is not one of the two literal terminals this rule allows — the grammar simply has no notion of a "move" command, however sensible it sounds in English.

  3. copy a b

    Violates <command> ::= <command type> <file name> to <file name>. The top-level rule requires the literal word to between the two filenames; dropping it breaks the overall <command> shape even though copy, a, and b are each individually legal symbols elsewhere in the grammar.

Watch out

Notice the three examples deliberately break three different rules (the filename-length rule, the command-type rule, and the overall command-shape rule). On an exam, if asked for "garbage tests", pick ones that each isolate a different rule — a set of garbage strings that all break the same rule is weaker evidence that the recognizer works, because it never probes the untested rules at all.

Question 6 · medium

Explain, using this file-copy example specifically, what a generator and a recognizer are doing, and give one concrete hypothetical bug that would illustrate each of the two failure modes.

Show model answer
What this tests & where it comes from This connects the abstract "generator/recognizer" framing (Section 5) to the concrete worked example (Section 6) — exactly the kind of "apply the general idea to the specific case" question a mixed-format exam favours.

Here, the recognizer is whatever part of the command interpreter parses a typed line like copy a to b and decides whether to run it or report a syntax error. The generator is you, the tester, using the grammar to produce a batch of strings such as copy aa to bb (should be accepted) and move a to b (should be rejected), then feeding all of them to the interpreter and checking its verdicts against what the grammar predicts.

Failure mode 1 (rejects a good string): suppose the interpreter's parser was written assuming filenames are always exactly one letter, and it throws a syntax error on copy aa to bb even though the grammar clearly allows two-letter filenames. Failure mode 2 (accepts a bad string): suppose the parser only checks that the line contains the word to somewhere and never actually validates the command-type word, so it happily accepts move a to b and tries to execute it as if it were copy or rename — a much more dangerous bug, since garbage now executes.

Question 7 · hard

Draw the full derivation tree, step by step, for the new valid string rename ab to a, numbering non-terminal/or nodes the way the lecture does.

Show worked solution

  1. Start: <command>

    Every derivation begins at the grammar's top-level non-terminal.

  2. Expand via <command> ::= <command type> <file name> to <file name>

    The only rule for <command> — no "or" choice here, it always expands to these four children.

  3. <command type> → rename (choosing the "or" alternative copy | rename)

    We want the string to start with "rename", so we pick the second alternative of the <command type> rule.

  4. 1st <file name> → <letter><letter> → a, b = "ab"

    We want a two-letter source filename, so we take the second alternative of <file name>, then resolve its two <letter> children to a then b.

  5. Literal to

    No choice — the grammar's top rule fixes this terminal between the two filenames.

  6. 2nd <file name> → <letter> → a

    We want a one-letter destination filename, so this second (independent) occurrence of <file name> takes the first alternative, resolving to the single letter a.

Resulting tree
<command>
├── <command type>
│     └─ copy (or) rename  ← chosen
├── <file name>  (1st)
│     └─ <letter> (or) <letter><letter>  ← chose 2-letter branch
│           1st letter: a (or) b → chose a
│           2nd letter: a (or) b → chose b
├── to
└── <file name>  (2nd)
      └─ <letter> (or) <letter><letter>  ← chose 1-letter branch
            a (or) b → chose a
Answer

Reading the leaves left to right gives rename ab to a — matching the target string exactly.

Question 8 · medium

The lecture picked copy a to b and copy aa to bb as its first two normal-condition tests, then added rename b to a and copy bb to aa. Explain the reasoning behind this exact order — why not, say, start with rename a to b instead?

Show model answer
What this tests & where it comes from Tests whether you understand node coverage as a strategy, not just a checklist — from the "Third step" slide of the worked example.

There is nothing uniquely forced about starting with copy specifically — rename a to b would have covered exactly the same non-terminals and an equally-sized set of terminals as copy a to b, since the two alternatives of <command type> are structurally symmetric. What is principled is the shape of the first two choices: test 1 is the shortest possible legal command (both filenames take the one-letter branch), maximising the chance of catching a basic parsing bug cheaply, and test 2 deliberately flips both filenames to their two-letter branch so that, together, tests 1 and 2 already cover every non-terminal in the tree (both file-name alternatives, both command-type alternatives are still outstanding at this point though — command type only shows "copy" so far). Tests 3 and 4 are then chosen specifically, by checking the tree against what's covered so far, to sweep up the exact six leaf terminals — 7 (rename), 13, 17, 19, 20, 22 — that tests 1–2 happened to leave untouched. In short: the first two tests establish structural (non-terminal) coverage cheaply, and the last two are reverse-engineered from exactly which terminals remain uncovered — not chosen arbitrarily.

Question 9 · hard

Design a brand-new, small BNF grammar for a simple two-character username format: the first character must be a letter (a or b), and the second character may be either a letter (a or b) or a digit (1 or 2). Write the grammar, draw its derivation tree, and give one fully-derived valid test string and one fully-derived garbage test string, explaining exactly which rule the garbage string breaks.

Show worked solution

  1. Step 1 — identify the language: "exactly two characters; first is a letter; second is a letter or a digit".

    Following the 3-step methodology: before writing any BNF, pin down in plain English exactly what counts as legal.

  2. Step 2 — the grammar:

    Translate the plain-English description into rules, reusing the same style as the lecture's own grammar (small alphabets, one rule per concept).

New grammar — username format

<username> ::= <letter> <suffix> <suffix> ::= <letter> | <digit> <letter> ::= a | b <digit> ::= 1 | 2

Derivation tree
<username>
├── <letter>
│     └─ a (or) b
└── <suffix>
      └─ <letter> (or) <digit>
            a (or) b       1 (or) 2

  1. Valid test: b1

    Derive: <username> → <letter> <suffix> → (<letter> → b) then (<suffix> → <digit> → 1). Every step follows a real rule, so a correct recognizer must accept it.

  2. Garbage test: 1a

    Violates <username> ::= <letter> <suffix>: the very first character must come from <letter> ::= a | b, but 1 is a <digit>, not a <letter> — no derivation of <username> can ever place a digit first, regardless of what follows it.

Question 10 · medium

Still using the username grammar from Question 9, give two more valid strings and one more garbage string, each with a one-line justification.

Show worked solution

  1. Valid: aa

    <letter> → a, then <suffix> → <letter> → a — both positions use the letter alternative, which is allowed since <suffix> permits either.

  2. Valid: b2

    <letter> → b, then <suffix> → <digit> → 2.

  3. Garbage: a3

    Violates <digit> ::= 1 | 2 (reached via <suffix>): 3 is neither of the two allowed digit terminals, and it also is not one of the two <letter> terminals — so no alternative of <suffix> can produce it.

Question 11 · medium

Is the string abc a valid username under the grammar from Question 9? Explain why length matters here even though every individual character (a, b, c) might look plausible.

Show worked solution

  1. <username> ::= <letter> <suffix>, and both <letter> and <suffix> resolve to exactly one character each

    Every alternative of <letter> (a/b), <digit> (1/2), and hence <suffix> is a single literal symbol — none of them expand to two characters. So <username> always derives a string of exactly two characters, never more or fewer.

  2. abc has 3 characters

    No matter which alternatives you pick, the grammar cannot produce a three-character string — the length itself is already disqualifying, independent of which letters appear.

Answer

Invalid — also, separately, c is not a legal <letter> or <digit> terminal at all, so even a two-character prefix like ac would fail on the second symbol. Two independent violations, either one sufficient to reject it.

Question 12 · short answer

Explain why syntax testing alone is not sufficient to fully test a piece of software. What kinds of bugs can it never catch, no matter how thorough the grammar coverage is?

Show model answer
What this tests & where it comes from This connects the definition of syntax testing (Section 2 — "examines the format and grammar", i.e. shape, not meaning) to the list of sibling black-box techniques (Section 1) that exist precisely to cover what syntax testing structurally cannot. The examiner wants you to see syntax testing as one tool among several, not a complete testing strategy on its own.

Syntax testing checks whether an input is shaped like a legal string of the grammar — nothing more. It has no way to know whether a syntactically valid input is semantically sensible or produces the correct output, because the grammar never encodes meaning, only structure. Concretely, in the file-copy example, copy a to a is perfectly valid syntax (both filenames legally derive from <file name>), yet it is a source-equals-destination command that a well-designed system probably should reject or warn about — a purely semantic bug that no amount of grammar-based testing would ever surface, since the string is 100% legal by the rules in Section 6. Likewise, syntax testing says nothing about: whether the copy actually happens correctly on disk (that needs functional/black-box testing at the behaviour level); how the system behaves across a sequence of commands over time (that is what testing state transitions, from the Section 1 list, is for); which combinations of input conditions trigger which internal effects (cause–effect graphs); performance, concurrency, or usability issues (outside functional testing entirely); or bugs in code paths the grammar never exercises because the input space it describes is narrower than the program's actual behaviour. In short: syntax testing answers "is this well-formed?" — it was never designed to answer "is this correct?", and that gap is exactly why the lecture lists it as one technique among seven rather than the whole testing strategy.

Question 13 · short answer

A colleague asks you to syntax-test a new input field that accepts a simple time-of-day string like 9:30. Walk through the three-step methodology conceptually for this field (you do not need to write the full BNF) — what would you do at each step?

Show model answer
What this tests & where it comes from Direct application of Section 4's three-step methodology to a scenario the lecture did not itself work through — checking that you can transfer the method, not just recite the file-copy example.

Step 1 — identify the language: decide precisely what "time of day" means for this field — is it hours:minutes only, is a leading zero on the hour allowed or required, is a 12-hour or 24-hour clock in use, is there an AM/PM suffix? This has to be pinned down before anything else, because the grammar in step 2 will only be as correct as this specification.

Step 2 — define the syntax formally: write BNF rules such as <time> ::= <hour> : <minute>, <hour> ::= 0 | 1 | ... | 23, <minute> ::= 00 | 01 | ... | 59 (or a more compact digit-based version) — capturing every constraint decided in step 1 as an explicit rule, the same way the lecture turned "copy-or-rename over one/two-letter filenames" into the four-rule grammar in Section 6.

Step 3 — test normal and garbage conditions: for the normal condition, pick a covering set of valid times that exercises every rule and boundary (e.g. 0:00, 9:30, 23:59) the same way node coverage was used for the file-copy grammar. For the garbage condition, construct strings that each violate exactly one rule — 25:00 (hour out of range), 9:60 (minute out of range), 9-30 (wrong separator, breaking the top-level <time> rule) — and confirm the field correctly rejects each one.

Question 14 · easy

True or false, with a one-line reason: "A derivation tree and a BNF grammar for the same language contain exactly the same information, just presented differently."

Show worked solution

  1. The grammar describes every possible legal string, in general.

    A grammar is a compact, reusable rule-set — it defines the whole (possibly infinite) language at once.

  2. One derivation tree records only one specific choice path, producing one specific string.

    Building the tree means picking one alternative at every "or" — information about the alternatives you didn't pick is not retained in that particular tree.

Answer

False. The grammar is the general rule-set that can generate every legal string in the language; a derivation tree is the record of one particular walk through those rules, producing exactly one string. Many different derivation trees come from the same grammar (as Section 6 and Question 4 show), but no single tree, by itself, tells you the whole grammar.

Last-minute revision — Syntax Testing

BNF symbol legend

<name> = non-terminal (still to substitute). ::= = "is defined as". | = "or", separates alternatives. Literal words/letters with no rule of their own = terminals (end up in the final string).

3-step methodology

1. Identify the target language/format.
2. Define its syntax formally (BNF).
3. Test normal condition (covering set of valid paths) + garbage condition (invalid strings, one broken rule each).

Generator / recognizer, one-liner

Tester = generator (produces valid & invalid strings); software under test = recognizer (accepts/rejects). Two failure modes: rejects a good string, or accepts a bad string.

The lecture's grammar

<command>::=<command type><file name> to <file name>
<command type>::=copy|rename
<file name>::=<letter>|<letter><letter>
<letter>::=a|b

The lecture's 4 test commands

copy a to b, copy aa to bb, rename b to a, copy bb to aa — together cover all 23 numbered nodes of the derivation tree.

What syntax testing can't catch

Semantic/logic bugs in syntactically valid input (e.g. copy a to a), behaviour over time, performance, and anything the grammar's input space doesn't cover.
