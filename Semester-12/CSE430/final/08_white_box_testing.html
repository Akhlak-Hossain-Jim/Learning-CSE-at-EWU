Topic 01

White-box vs black-box testing

Same goal — finding bugs before the user does — two completely different vantage points.

Picture two people trying to find out if a vending machine is broken. One of them can only put coins in and see what comes out — they never open the machine. The other has the wiring diagram, the internal circuit board, and can watch every relay switch as a coin drops. Both are legitimately "testing" the machine, but they're testing it from opposite sides.

The first person is doing black-box testing: they test based on what the software is supposed to do (its requirements), feeding in inputs and checking outputs, with no knowledge of how the code inside is written. The second person is doing white-box testing: they test using knowledge of the program's internal structure and implementation — the actual statements, the decisions (if/else), the loops, and the paths control can take through the code. That is the faculty's exact definition, and it is the one to reproduce on the exam if asked to define the term.

Key idea

White-box testing looks inside the code — at statements, branches, loops, control flow, and execution paths — instead of only at inputs and outputs. The central question the whole lecture is built around is: which parts of the program have actually been exercised by our tests?

Side-by-side comparison (faculty's table)

Black-Box TestingWhite-Box Testing
BasisBased on requirementsBased on internal code
What it examinesInputs and outputsStatements, branches, and paths
Code knowledgeNot requiredRequired
What it detectsFunctional problemsStructural weaknesses

White-box testing specifically examines: executable statements, decisions and branches, loops and conditions, control flow, execution paths, and reachable vs. unreachable code — this list is the syllabus for the rest of the lecture; every remaining section is one of these six items explained in depth.

Watch out

Do not write "white-box is better than black-box" on the exam. The lecture is explicit: these are complementary techniques, not competitors. Black-box gives you the requirements view, white-box gives you the code view, and together they produce better tests than either alone.

Topic 02

Building a Control Flow Graph (CFG)

The running example the whole lecture is built on: calculatePayable(amount, isMember).

Before you can measure any kind of coverage, you need a map of every route control can take through a function. That map is called a Control Flow Graph, or CFG. Think of the code as a small city: each block of straight-line instructions is one building, each decision (an if) is an intersection with two roads leading out of it (one for "true", one for "false"), and the CFG is simply the road map connecting entry to exit.

Key idea

A Control Flow Graph (CFG) represents the possible flow of execution through a program. It shows how control may move — not what output the program produces.

The five building blocks (faculty's terms)

  • Node — a statement, or a sequence of statements that always execute together.
  • Edge — a possible transfer of control from one node to another.
  • Decision node — a condition with two (or more) possible outcomes.
  • Entry node — the beginning of execution.
  • Exit node — the end of execution.

Construction rules

  • Sequential statements connect directly (one arrow, no branching).
  • A decision creates a True branch and a False branch.
  • Branches merge back together at a common continuation point.
  • A loop contains an edge that goes back to an earlier node.

The running example

This is the exact pseudocode the lecture uses for every coverage calculation from here on — memorise its shape, because branch coverage, path coverage, feasibility, and reachability are all demonstrated on this one function.

function calculatePayable(amount, isMember):

    discount = 0

    if amount >= 1000 then
        discount = 100

    if isMember = true then
        discount = discount + 50

    payable = amount - discount

    if payable < 0 then
        payable = 0

    return payable

Business rules behind it: a purchase of $1,000 or more earns a $100 discount; a registered member gets an additional $50 off; and the payable amount can never be negative (it's floored at zero).

Step by step: turning the code into nodes

Walk through the code top to bottom. Every straight-line statement becomes its own node; every if becomes a decision node with two outgoing edges.

  1. N1: discount = 0

    First executable line. It always runs, so it is a plain node directly after Entry — one incoming edge, one outgoing edge.

  2. N2: amount >= 1000 ? decision

    This is an if, so it is a decision node: it needs two outgoing edges, one labelled True and one labelled False.

  3. N3: discount = 100

    This line only runs when N2 is True — so the True edge from N2 points here. The False edge from N2 skips straight past it.

  4. N2's True edge (via N3) and N2's False edge merge

    Merge rule: whether or not the discount was applied, execution continues at the same next line — so both branches of N2 reconnect into a single edge before the next statement.

  5. N4: isMember = true ? decision

    Second if in the code — second decision node, again with a True and a False outgoing edge.

  6. N5: discount = discount + 50

    Runs only on N4's True edge; N4's False edge skips it. The two branches merge again right after, by the same merge rule as step 4.

  7. N6: payable = amount - discount

    Unconditional statement — it isn't guarded by any if, so it's a single plain node that both merged paths flow into.

  8. N7: payable < 0 ? decision

    Third and final if — third decision node.

  9. N8: payable = 0, then N9: return payable

    N8 runs only on N7's True edge; N7's False edge skips straight to N9. Both branches merge into N9, which flows to Exit.

Quick check (memorise these three numbers)

Decision nodes: N2, N4, N7 → 3 decisions. Each decision has 2 outcomes (True/False), so total branch outcomes = 3 × 2 = 6. Total nodes (including the always-executed statements): 9 (N1–N9).

One concrete route through this graph — an execution path — is written as a sequence of nodes with the decision outcome in brackets: N1 → N2(T) → N3 → N4(T) → N5 → N6 → N7(F) → N9. That single path corresponds to running the function with, say, amount = 1200, isMember = true. You'll use this exact notation constantly for the rest of the lecture.

Watch out

A CFG shows how control may move — not what output the program produces. Don't confuse "this edge exists in the graph" with "this edge will always be taken" — that depends entirely on the input values, which is exactly what coverage testing is about to measure.

Topic 03

Statement coverage

The most basic question you can ask of a test suite: did we even run every line?

Once you have a CFG, the simplest thing to check is whether your tests ran every executable statement at least once. If a line of code was never executed by any test, you have zero evidence about whether that line works — it could be silently broken and you'd never know.

Statement coverage
\[ \text{Statement Coverage} = \frac{\text{Executed statements}}{\text{Total executable statements}} \times 100\% \]

A statement is "covered" the moment any test case in the suite executes it at least once — you don't need the same test to hit every line, you need the union of all your tests to hit every line.

Faculty's convention — read this carefully

In the running example, only the assignment and return statements are counted toward the total: N1, N3, N5, N6, N8, N9 — six statements. The three decision nodes (N2, N4, N7) are not counted as "statements" for this formula; they're counted separately, in branch coverage.

Worked example: TC1

Test case TC1: amount = 1200, isMember = true. Trace it through the CFG from Topic 2.

  1. N2: amount >= 1000? → 1200 >= 1000 → True

    Substitute the test input into the first decision. Since it's True, we take the N3 branch.

  2. N4: isMember = true? → True

    Substitute isMember = true into the second decision. True, so we take the N5 branch.

  3. discount = 100 + 50 = 150; payable = 1200 − 150 = 1050

    N3 sets discount to 100, N5 adds 50 more, then N6 computes payable from these values.

  4. N7: payable < 0? → 1050 < 0 → False

    Substitute the computed payable into the third decision. It's False, so N8 is skipped and we go straight to N9.

  5. Path: N1 → N2(T) → N3 → N4(T) → N5 → N6 → N7(F) → N9

    Assemble the path from the three decision outcomes found above.

  6. Executed statements: N1, N3, N5, N6, N9 (5 of them). Not executed: N8.

    Read off every non-decision node the path passes through; N8 (payable = 0) is the one node this path never reaches, because N7 was False.

  7. Statement Coverage \( = \dfrac{5}{6} \times 100\% = 83.33\% \)

    Apply the formula: 5 executed out of the 6 total executable statements (N1, N3, N5, N6, N8, N9).

Answer

TC1 alone achieves 83.33% statement coverage. The uncovered statement is N8 (payable = 0), because this particular test never drives payable below zero. Sanity check: 5/6 = 0.8333…, times 100 gives 83.33% — matches.

What statement coverage buys you: it proves every executable instruction has been exercised at least once, so untested portions of the program become visible, and you know exactly which additional test cases to add next (here: something that forces payable negative, to reach N8).

Topic 04

Branch coverage

Running a line isn't the same as running it both ways.

Statement coverage has a blind spot: an if statement can be marked "covered" the instant its body runs even once — but that tells you nothing about what happens when the condition is false. Branch coverage fixes this by tracking decision outcomes instead of lines.

Key idea

Branch coverage measures whether every possible outcome of each decision has been executed by the test suite. For a Boolean decision, that means both its True branch and its False branch must each be taken by at least one test.

Branch coverage
\[ \text{Branch Coverage} = \frac{\text{Executed branch outcomes}}{\text{Total branch outcomes}} \times 100\% \]
Watch out

Branch coverage is calculated using decision outcomes, not the number of test cases. Two test cases can, between them, cover six branch outcomes; one badly-chosen test case might cover none beyond the first.

The running example has 3 decisions (N2, N4, N7), each with 2 outcomes: 3 × 2 = 6 branch outcomes total.

Worked example: designing TC1 + TC2 for 100%

This time the faculty uses a different pair of test cases than the statement-coverage example, chosen specifically so their outcomes are complementary:

TC11200FalseTrueFalseFalse
TC220TrueFalseTrueTrue

  1. TC1 path: N1 → N2(T) → N3 → N4(F) → N6 → N7(F) → N9

    amount = 1200 ≥ 1000 → True; isMember = False → N4 is False; discount stays 100, so payable = 1200 − 100 = 1100, not < 0.

  2. TC2 path: N1 → N2(F) → N4(T) → N5 → N6 → N7(T) → N8 → N9

    amount = 20 < 1000 → N2 False; isMember = True → N4 True, discount = 0 + 50 = 50.

  3. For TC2: discount = 50; payable = 20 − 50 = −30. Therefore payable < 0 is True.

    Compute payable explicitly to justify why N7 comes out True for TC2 — this is the branch statement coverage alone couldn't force.

  4. N2 outcomes seen: True (TC1) and False (TC2) → both ✓

    Collect, decision by decision, which outcomes appear across both test cases combined.

  5. N4 outcomes seen: False (TC1) and True (TC2) → both ✓  |  N7 outcomes seen: False (TC1) and True (TC2) → both ✓

    Same check for the remaining two decisions — every decision now has both a True-case and a False-case somewhere in the suite.

  6. Branch Coverage \( = \dfrac{6}{6} \times 100\% = 100\% \)

    Apply the formula: all 6 branch outcomes (3 decisions × 2 outcomes) are now executed by the two test cases together.

Answer

Only two carefully chosen test cases are needed to cover all six branch outcomes: 100% branch coverage. Note the general rule the lecture states explicitly: 100% branch coverage normally provides 100% statement coverage (every node here does get executed by TC1 or TC2), but as Topic 5 shows next, the reverse is not guaranteed.

Topic 05

Statement coverage vs branch coverage

100% on one does not mean 100% on the other — this is the single most examinable idea in the whole lecture.

To make the gap between the two criteria unmistakable, the faculty switches to a second, smaller function, checkResult(mark), and shows that a single test can max out statement coverage while leaving branch coverage at only half.

function checkResult(mark):

    status = "Fail"

    if mark >= 40 then
        status = "Pass"

    print status

Run it with one test case: mark = 60

  1. status = "Fail" executes

    Unconditional first line — always runs.

  2. Condition mark >= 40 → 60 >= 40 → True

    Substitute mark = 60 into the decision.

  3. status = "Pass" executes

    Because the condition was True, the body of the if runs, overwriting status.

  4. print status executes

    Unconditional last line — always runs regardless of the decision's outcome.

  5. Executable statements = {status="Fail", status="Pass", print status} = 3 total, all 3 executed.

    List every non-decision statement and check off which ones this single test hit.

  6. Statement Coverage \( = \dfrac{3}{3}\times100\% = 100\% \)

    All three statements ran — full statement coverage from just one test case.

  7. Branch outcomes: mark≥40 True ✓ executed. mark≥40 False — never executed.

    There is exactly one decision with 2 outcomes; this test only ever produced the True outcome.

  8. Branch Coverage \( = \dfrac{1}{2}\times100\% = 50\% \)

    Only 1 of the 2 branch outcomes was executed — the False path (mark < 40, status stays "Fail") was never tested even though statement coverage says 100%.

Answer — the gap, in one line

Statement Coverage = 100%, Branch Coverage = 50%. The false outcome of mark ≥ 40 has never been tested — no test has checked mark < 40 — yet statement coverage was completely blind to that gap.

Comparison pointStatement coverageBranch coverage
FocusExecutable statementsDecision outcomes
RequirementExecute every statementExecute every True and False branch
Relative strengthBasic structural criterionStronger structural criterion
Main limitationMay miss untested branchesMay miss branch combinations
Typical useInitial test adequacy checkDecision-oriented test evaluation
Watch out — this is the exact exam trap

Do not assume "100% statement coverage" means the code has been thoroughly tested. A stronger coverage criterion reveals testing gaps that a weaker criterion may miss entirely. Whenever a question gives you 100% statement coverage and asks "is this enough?", the answer is: check the branches.

Topic 06

Path coverage and the 2ⁿ formula

You already handled this style of question quickly in your diagnostic — here's the vocabulary that goes with the number.

A path is a complete sequence of nodes followed from the program's entry all the way to its exit. Where branch coverage only asks "was each decision's True and False outcome hit somewhere?", path coverage asks the much stronger question: "was every specific combination of decisions exercised?"

Path coverage
\[ \text{Path Coverage} = \frac{\text{Executed feasible paths}}{\text{Total feasible paths}} \times 100\% \]

For a snippet with two independent decisions:

if A then
    execute S1

if B then
    execute S2

Decision A can be True or False; independently, decision B can be True or False. That gives four combinations, laid out as four paths:

PathDecision ADecision B
P1TrueTrue
P2TrueFalse
P3FalseTrue
P4FalseFalse
Maximum combinations for n independent Boolean decisions
\[ \text{Maximum combinations} = 2^n \]

Here n = 2 decisions, so \(2^2 = 4\) — matching the four paths above. Applied to the running example, calculatePayable has 3 decisions (N2, N4, N7), so the theoretical maximum is \(2^3 = 8\) possible decision combinations, i.e. up to 8 candidate paths.

Watch out

Path coverage is more thorough than statement or branch coverage — it examines order, combinations of decisions, and complete routes — but complete path testing is often impractical: the number of paths grows exponentially with the number of decisions, and (as the next section shows) not every mathematically-possible combination can actually happen.

Topic 07

Feasible vs infeasible paths

2ⁿ tells you the upper bound. It does not tell you how many of those paths a real input can actually produce.

Definitions — get these exact, they're often asked as a short-answer pair

Feasible path: a path that can be executed by at least one valid input. Infeasible path: a path that appears in the CFG's structure, but no valid input can ever execute it.

Infeasible paths arise when two decisions in the same path both depend on the same variable in a way that contradicts itself. Consider:

if x > 10 then
    execute A

if x < 5 then
    execute B
x > 10x < 5Feasibility
TrueTrueInfeasible
TrueFalseFeasible
FalseTrueFeasible
FalseFalseFeasible

No number x can be simultaneously greater than 10 and less than 5 — those two conditions on the same variable can never both hold, so that one row of the truth table is structurally present but never reachable by any real input.

Worked example: is a path in the running example infeasible?

Consider the path where amount ≥ 1000 = True, isMember = True, payable < 0 = True all hold at once.

  1. If amount ≥ 1000 is True and isMember is True, then discount = 100 + 50 = 150.

    Both discount-granting decisions fired, so both discounts stack: N3 gives 100, N5 adds 50.

  2. payable = amount − 150

    Substitute discount = 150 into N6's formula.

  3. Since amount ≥ 1000 on this path, payable ≥ 1000 − 150 = 850.

    Use the constraint from the first decision (amount ≥ 1000) as a lower bound on amount, and substitute the smallest possible amount to find the smallest possible payable.

  4. Therefore payable < 0 cannot be True on this path.

    payable is provably at least 850, which can never be negative — so the third decision's True outcome is logically incompatible with the first two.

Answer

The path N1 → N2(T) → N3 → N4(T) → N5 → N6 → N7(T) → N8 → N9 is infeasible. It exists as a structural combination of the CFG's decisions, but no valid amount can make payable negative once both discounts have already been applied.

Watch out

Unexecuted paths should not automatically be treated as testing failures. Before proposing a new test case to "fix" a missing path, always check feasibility first — you may be chasing a path that no input can ever satisfy.

Topic 08

Reachability analysis

"Nobody has tested it yet" and "nobody ever could" are two very different diagnoses.

Key idea

Reachability analysis determines whether a statement, branch, or program location can be executed from program entry using at least one valid input. The five questions the faculty says to ask: Can a valid input execute this statement? Can both outcomes of the decision occur? Does an earlier statement prevent execution? Are required conditions logically consistent? Do input constraints make the branch impossible?

if age >= 18 then
    status = "Adult"

if age < 0 then
    status = "Invalid"

The second branch (age < 0) is structurally reachable — there's a real edge in the CFG leading to it — but whether it is practically reachable depends on a question the graph alone can't answer: does the system's input validation even allow negative ages to reach this function in the first place? Reachability, in other words, sometimes needs domain knowledge, not just the code.

Worked example: is N8 in the running example reachable?

From Topic 3, TC1 (amount = 1200, isMember = true) left N8 (payable = 0) uncovered. Does that mean N8 is unreachable code?

  1. Try amount = 20, isMember = true.

    Pick a small amount so the $100 threshold discount does not apply, but keep isMember true so the $50 discount still does.

  2. N2: 20 ≥ 1000? False → discount stays 0. N4: isMember = true? True → discount = 0 + 50 = 50.

    Trace the two discount decisions with this new input.

  3. payable = 20 − 50 = −30

    Apply N6's formula with amount = 20 and discount = 50.

  4. N7: payable < 0? −30 < 0 → True → N8 executes.

    This input drives payable negative, so the True branch of N7 fires and N8 runs.

Answer

N8 is reachable — it just wasn't covered by TC1. Uncovered does not always mean unreachable. The faculty's own distinction: uncovered code means no current test executes it; unreachable code means no valid test ever could. Reachability analysis is exactly the step that tells you which of the two you're looking at — and therefore whether the fix is "write another test" or "this code cannot ever run."

Topic 09

Dead code vs unreachable code

Two different diseases that both show up as "this code doesn't matter" — but for opposite reasons.

One-line definitions

Unreachable code: code that can never be executed from the program entry — there is no control-flow path that reaches it at all. Dead code: code that executes, or may execute, but has no meaningful effect on the program's behaviour.

The distinction is about where the problem lives. Unreachable code is a control-flow problem — the wiring simply doesn't connect to that block. Dead code is a data-flow / logic problem — the wiring does connect, the block does run, but its result is thrown away or never used.

Unreachable code — example

return total
print("Calculation completed")

The print statement can never execute, because the function has already returned on the line before it — control leaves the function permanently at return total, so nothing after it in the same block is ever reached, no matter what input you give.

Dead code — two examples

rate = 5
rate = 10
print(rate)

Here, both lines do execute — but rate = 5 is overwritten by rate = 10 before it is ever read. The first assignment has no effect on the final value that gets printed, so it is dead: it runs, and it accomplishes nothing.

if age < 18 and age > 60 then
    category = "Special"

This one is subtler: no single value of age can be both less than 18 and greater than 60 at the same time, so the condition is always false and category = "Special" can never actually run.

Watch out — faculty's specific classification

You might expect an impossible condition like the one above to be filed under "unreachable", the way the lecture's own path-feasibility examples were. But the lecture places it under dead code instead — because the if-check itself is structurally reachable (there is a real edge into it), it is only the body that a logically-impossible input condition prevents from ever firing. This overlaps conceptually with the infeasible-path idea from Topic 7; if a question asks you to classify a snippet like this, you can mention both labels and explain the overlap — that shows you understand the nuance rather than just memorising a category.

Comparison table

TypeCan execute?Affects behaviour?
Reachable and usefulYesYes
Dead codePossiblyNo meaningful effect
Unreachable codeNoNo

Why it matters, straight from the lecture: dead and unreachable code both increase maintenance difficulty, hide logical errors, reduce code clarity, mislead coverage analysis (a coverage tool might report a lower percentage that looks like a testing gap when it's really an unfixable code smell), increase testing effort spent chasing the impossible, and can even create security or reliability risks.

Key idea

Coverage tools reveal unexecuted code automatically. They cannot tell you why it's unexecuted — that always requires your own logical analysis, which is exactly what Topics 7, 8, and 9 have been building toward.

Topic 10

Practice questions

Every question is fully worked, line by line. Cover the solution, attempt it, then reveal.

Reference: three new functions, same pseudocode style

These three short functions are used across the questions below. They follow exactly the same style as calculatePayable, so you can practise building CFGs and computing coverage on material you haven't already memorised the answer to.

function gradeAttempt(score, attempts):
    result = "Retry"
    if score >= 60 then
        result = "Pass"
    if attempts > 3 then
        result = "Locked"
    return result
function classifyTemperature(temp, isRaining):
    label = "Mild"
    if temp >= 35 then
        label = "Hot"
    if temp <= 10 then
        label = "Cold"
    if isRaining = true then
        label = label + " and Wet"
    return label
function computeShippingFee(weight, isExpress):
    fee = 5
    if weight > 20 then
        fee = fee + 15
    if isExpress = true then
        fee = fee * 2
    if fee > 50 then
        fee = 50
    return fee

Exit ticket and short theory answers

Question 14 · short answer

Exit ticket (lecture's own): A test suite achieves 100% statement coverage but only 75% branch coverage. What does this indicate?

Show model answer
What this tests & where it comes from This tests whether you understand the relationship between the two coverage criteria (Topic 5) — specifically that statement coverage is the weaker criterion and branch coverage is stronger, so a gap between the two numbers is diagnostic information, not a contradiction.

It indicates that at least one branch outcome remains untested — every statement has run at least once, but for one or more decisions, only one of its two outcomes (True or False) has actually been exercised by the suite. Concretely, with 6 total branch outcomes, 75% means 4.5 → practically, at least one decision (out of however many exist) still has an untested side. This is exactly the pattern from the checkResult example in Topic 5: full statement coverage can hide an entirely untested branch. Additional test cases are required — specifically ones chosen to flip the missing decision outcomes to their untested value — before you can claim the branches are adequately tested.

Question 15 · short answer

Explain the difference between white-box and black-box testing, and why the lecture insists neither one replaces the other.

Show model answer
What this tests & where it comes from This tests the definition from Topic 1 plus the "complementary, not competitors" framing — the examiner wants you to state both definitions accurately and connect them to why combining both views produces better tests than either alone.

White-box testing designs test cases using knowledge of the program's internal structure and implementation — it examines executable statements, decisions, branches, loops, and execution paths, so it requires reading the code (Topic 1). Black-box testing instead designs test cases from the requirements, checking only inputs against expected outputs, with no knowledge of the code required. They detect different classes of problems: black-box catches functional problems (the software doesn't do what it's supposed to), while white-box catches structural weaknesses (a branch nobody tested, a path that behaves unexpectedly, dead or unreachable code). Because each technique is blind to what the other one sees, the lecture treats them as complementary: combining the requirements view with the code view produces stronger, more complete tests than relying on either view by itself.

Question 16 · short answer

In your own words, distinguish dead code from unreachable code, and give one example of each that is not from the lecture slides.

Show model answer
What this tests & where it comes from This tests the Topic 9 distinction — the examiner wants you to show that "code that doesn't matter" splits into two structurally different causes: a control-flow problem versus a data-flow/logic problem, not just recite the two labels.

Unreachable code can never be executed at all, because no path in the control flow graph connects the program entry to it — for example, a line placed after an unconditional return in the same block, like the print("Calculation completed") example from Topic 9. Dead code, by contrast, does execute — control does reach it — but it has no meaningful effect on the program's behaviour, typically because its result is immediately overwritten or its condition can never actually be satisfied by valid input, like rate = 5 being overwritten by rate = 10 before ever being read. An example not in the slides: a function that computes total = total * 1 partway through a calculation — the line executes every time, but multiplying by 1 changes nothing, so it is dead code, whereas a break statement placed one line after another unconditional break inside the same loop body would be unreachable code, since the first break already exits the loop before the second line can run.

Last-minute revision

Statement coverage

\( \dfrac{\text{Executed statements}}{\text{Total executable statements}} \times 100\% \) — counts lines, not decisions.

Branch coverage

\( \dfrac{\text{Executed branch outcomes}}{\text{Total branch outcomes}} \times 100\% \) — needs both True and False of every decision.

Path coverage

\( \dfrac{\text{Executed feasible paths}}{\text{Total feasible paths}} \times 100\% \); upper bound \( 2^n \) for n independent Boolean decisions.

calculatePayable CFG

9 nodes, decisions N2/N4/N7, 6 branch outcomes. Memorise this shape — three new example functions in this guide reuse it exactly.

Feasible vs infeasible

Feasible = at least one valid input can execute it. Infeasible = structurally present, but no valid input ever can — usually two decisions contradicting each other on the same variable.

Reachability

Uncovered code = no current test hits it (might just need a new test). Unreachable code = no valid test ever could.

Dead vs unreachable

Unreachable = control flow never gets there. Dead = control gets there and it runs, but has no meaningful effect.

Coverage hierarchy

Statement → Branch → Path, each stronger than the last. 100% on a weaker criterion never guarantees 100% on a stronger one.

Golden rule

Coverage measures test execution, not software correctness. High coverage is necessary evidence, never proof of a defect-free program.
