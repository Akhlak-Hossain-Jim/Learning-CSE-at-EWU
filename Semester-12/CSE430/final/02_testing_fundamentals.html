Principle 01 of 7

Testing Shows Presence of Defects, Not Their Absence

Passing every test tells you what wasn't found — not that nothing is there.

Think about a medical screening test. If it comes back positive, you've learned something concrete: there is a problem, and you know roughly where. But if it comes back negative, all you've really learned is that this particular test didn't detect a problem — not that you are guaranteed to be perfectly healthy. A different test, looking at a different marker, might still find something. Software testing works the same way. A defect is a flaw in the software that causes it to behave incorrectly; a test case is one specific check designed to catch a particular kind of defect if it exists.

Put formally, in the lecture's own words: testing can reveal defects, but it never proves their absence — even when none are found. If every test in your suite passes, that only means no defects were found by the tests that were run. It does not mean the software is defect-free; it means your confidence has gone up, while certainty has not been reached, because untested paths could still be hiding a problem.

Key idea

Testing reduces risk — it does not eliminate it.

Faculty's worked example: a banking app passes all 500 of its test cases, covering login, transfer, and balance operations. Later, in production, a critical bug turns up in currency conversion — a path the 500-test suite never actually covered. The suite wasn't wrong to pass; it simply never asked the question that would have caught this bug.

Watch out

The classic exam trap is a scenario that says "the team ran the full test suite and got zero failures — is the software bug-free?" The correct answer is always no: zero failures on the tests you ran is not the same claim as zero defects in the system. Don't let "100% pass rate" and "0% defect rate" collapse into the same sentence in your answer.

Question 1 · warm-up · short answer

Why can't testing ever prove that software is 100% defect-free? Explain your answer using the difference between "passing a test suite" and "having zero defects."

Show model answer
What this tests & where it comes from This is the faculty's own quick-review question 1 from the end of Lecture 14. It is testing whether you can state Principle #1 (Testing Shows Presence of Defects, Not Their Absence) precisely, rather than just recognising it when you see it.

Testing works by running a finite, chosen set of test cases and checking whether the observed behaviour matches the expected behaviour. If a test fails, we have direct evidence of a defect — that is what "presence of defects" means. But if every test passes, all we can conclude is that the specific inputs, paths, and scenarios we happened to check behaved correctly. We never execute every possible input, path, and combination of conditions the software could encounter (this connects directly to Principle #2, exhaustive testing is impossible), so there will always be paths that were never exercised. A defect sitting on one of those unexercised paths simply never gets the chance to reveal itself. That's why a 100% pass rate only ever means "no defects found by these tests" — it lowers the probability of undiscovered defects, it does not drive that probability to zero.

Principle 02 of 7

Exhaustive Testing Is Impossible

You cannot try every combination — so you have to choose which ones matter.

Imagine a combination lock with enough dials that trying every possible setting would take longer than anyone's patience allows — you'd give up long before you tried them all, even though in principle you could. Software has the same problem, at a much larger scale. Exhaustive testing means testing every possible input, every possible path through the code, and every possible combination of conditions.

The lecture's point is blunt: testing all combinations is infeasible. Time, cost, and complexity make 100% coverage impractical even for genuinely small components — this isn't about lazy testers, it's a hard combinatorial wall. The response is to stop chasing "everything" and instead prioritize using risk analysis, focusing limited testing effort where it matters most.

Faculty's worked example

A simple form with just 10 fields, each with 5 possible values, already has \( 5^{10} \approx 9.7 \) million possible combinations. Even running 1,000 tests every second, that's still days of testing — for one form.

Key idea

We can't test everything — we test what matters most.

Watch out

Don't read this principle as "write as many test cases as possible." The lecture explicitly says the answer is to prioritize by risk, not to maximize raw test-case count. A smaller, well-chosen set of tests aimed at the highest-risk areas beats a huge unfocused set every time — and it's this principle that later justifies techniques like equivalence partitioning and boundary value analysis from earlier lectures, which exist precisely to pick a small, representative sample instead of testing exhaustively.

Question 2 · warm-up · worked problem

A configuration screen has 9 independent toggle-fields, each of which can be set to one of 5 possible states. (a) How many total input combinations would exhaustive testing of this one screen require? (b) At a throughput of 1,000 test executions per second, how many minutes of pure execution time would exhaustive testing take? (c) What does Principle #2 say the team should do instead?

Show worked solution

  1. \( \text{combinations} = 5^9 \)

    Each of the 9 fields is an independent choice among 5 states, so — exactly as in the faculty's 10-field example — the counts multiply together rather than add.

  2. \( 5^9 = 1{,}953{,}125 \)

    Evaluate the exponent: 5 multiplied by itself 9 times.

  3. \( \dfrac{1{,}953{,}125 \text{ tests}}{1{,}000 \text{ tests/sec}} = 1{,}953.125 \text{ sec} \)

    Divide total combinations by throughput to get total time in seconds.

  4. \( 1{,}953.125 \div 60 \approx 32.6 \text{ minutes} \)

    Unit conversion to a human-readable figure: seconds ÷ 60 = minutes.

Answer

≈1.95 million combinations, roughly 33 minutes of nonstop execution — for one screen, in isolation, with no setup time between tests. Per Principle #2, exhaustive testing here is already impractical, so the team should apply risk-based prioritization (e.g., boundary values, high-risk field combinations, pairwise testing) rather than attempt full coverage.

Principle 03 of 7

Early Testing Saves Time and Money

The same defect gets more expensive to fix the later you find it.

Catching a typo while you're still drafting a document costs you a few seconds. Catching that same typo after the document has been printed, bound, and shipped to a warehouse means reprinting the whole run. The defect didn't change — only how much has already been built on top of it did. Software defects behave the same way across the SDLC (software development life cycle — the sequence of phases a system passes through: requirements, design, coding, and beyond).

The lecture states this directly: defects found early in the SDLC are far cheaper to fix than those found later, so testing activities should begin at the requirements and design stages — not just after coding is done. This is exactly why static testing (Topic 8 below) matters: reviews and inspections let a team catch defects before code even exists.

Requirements1×

Key idea

A bug caught in a requirements review is far cheaper than one caught in production.

Watch out

The multiplier is indexed to Requirements = 1, not 0 — every phase still costs something. Also, the jump from Coding (10×) to Post-release (100×) is a 10× jump on its own, which is often what an exam question is actually probing, rather than the full 100× compared to Requirements.

(c) How many times more expensive is the post-release fix compared to catching it during coding?

Show worked solution

  1. \( \text{Coding} = 10\times \text{ base unit} = \$200 \Rightarrow \text{base unit (1×)} = \$200 / 10 = \$20 \)

    The table's multipliers are all relative to the same base unit (Requirements = 1×); use the known Coding cost to back out that base unit.

  2. \( \text{Requirements cost} = 1 \times \$20 = \$20 \)

    Substitute the base unit into the Requirements multiplier (1×).

  3. \( \text{Post-release cost} = 100 \times \$20 = \$2{,}000 \)

    Substitute the base unit into the Post-release multiplier (100×).

Requirements-phase equivalent: $20. Post-release cost: $2,000. The post-release fix is 10× more expensive than fixing it during coding (and 100× more expensive than fixing it at the requirements stage) — the same defect, just discovered later.

Principle 04 of 7

Defect Clustering

Most bugs don't spread evenly — they pile up in a few hot spots.

If a restaurant gets complaints, they're rarely spread evenly across the whole menu — usually one or two dishes generate most of the trouble, while the rest of the menu is fine. Software defects behave the same way: a small number of modules usually contain most of the defects in a system.

This follows the Pareto principle — a general pattern where a small proportion of causes produces a large proportion of effects. In testing terms, roughly 80% of defects are typically found in roughly 20% of modules. Past defect data helps predict where new defects will cluster, which is valuable information for planning where limited testing time goes.

Faculty's worked example — payment module, past release

The payment module made up just 15% of the codebase, but accounted for 65% of all reported defects.

Key idea

Past defect patterns guide where testing effort should concentrate.

Watch out

Defect clustering is a reason to concentrate testing effort, not a licence to skip the other modules entirely — a low-defect-history module can still ship a first-time defect. It's also easy to confuse with Principle #2 (exhaustive testing is impossible): that principle is about the sheer size of the input space, while clustering is about where, historically, defects actually turn up within that space.

This doesn't mean ignoring the rest of the system — Principle #1 (testing shows presence, not absence, of defects) still applies everywhere — but with finite time, concentrating effort where defects have clustered historically gives the best return on testing investment.

Principle 05 of 7

Pesticide Paradox

Running the exact same tests, forever, eventually tells you nothing new.

Picture a farmer who sprays the same pesticide on their field, season after season. In year one, it wipes out most of the pests. But any insects that happened to survive that first spraying pass on whatever let them survive — and over time, the surviving population is made up almost entirely of insects that specific pesticide simply doesn't affect anymore. The chemical hasn't gotten weaker; the population it's up against has changed to route around exactly what it checks for.

A regression suite is a fixed set of test cases, re-run after every change, to confirm old functionality still works. The pesticide paradox says: running the identical set of tests repeatedly eventually stops finding new defects — not because the software has become defect-free, but because that suite only ever checks for the specific things it was built to check, and everything that could trip those specific checks has already been fixed. Test cases must be reviewed and updated regularly to keep finding new kinds of defects, the same way a farmer would eventually need to rotate to a different pesticide.

Faculty's worked example

A regression suite of 200 test cases, unchanged for 18 months, keeps returning 200/200 passing. It isn't because the software is defect-free — it's because those 200 tests only ever check old, already-fixed scenarios. A critical crash then shows up in a feature the suite never covered.

Key idea

Stale test suites give false confidence — tests must evolve with the software.

Watch out — the mechanism, made explicit

This is the trap worth slowing down on, because "100% passing" and "safe" feel like the same thing and they aren't. Each test case in the suite was written to check one specific thing — usually a defect that was found once and fixed. The very first time you run the suite, that's genuinely useful information. But once the surrounding code stabilizes, that same test just keeps confirming the same fact over and over: "the thing I check for is still fixed." It has nothing to say about any code the suite doesn't touch. Meanwhile the software keeps changing underneath it — new features, new branches, new edge cases get added — and none of that is covered by a suite that hasn't changed. So the pass rate can sit at 100% for 18 straight months while real, uncovered risk quietly accumulates in exactly the parts of the system the old tests never look at. That's the paradox: the more reliably a fixed suite passes, the less information each additional run of it is actually giving you.

What to do instead: don't throw the old suite away — it still guards against old bugs resurfacing. Instead, (1) periodically retire or rewrite tests that never fail and add nothing new, (2) add fresh test cases targeting recently changed code, new features, and any defect found in production, (3) vary the input data and edge cases inside existing tests instead of always rerunning identical fixed values, and (4) pair the regression suite with exploratory or risk-based testing that deliberately probes areas the fixed suite doesn't reach. The goal is a suite that keeps refreshing itself, the way a farmer rotates pesticides, rather than one that just gets re-run unchanged.

Question 5 · core · short answer

Explain the pesticide paradox in software testing, using the farming analogy it's named after. Why doesn't a regression suite that has passed 100% of the time for 18 months guarantee the software is defect-free, and what should the team do about it?

Show model answer

Just as a fixed pesticide eventually only kills the insects that were never resistant to it, leaving a population immune to that one chemical, a fixed set of test cases eventually only catches the specific defects it was designed to catch — and once those are fixed, it has nothing left to find. A team has been using the same 200 regression test cases for 18 months. All tests pass, and the team confidently ships a new release. Two days later, users report a critical crash in a feature that was never part of the original test suite. (a) Which testing principle(s) explain what went wrong? (b) What could the team have done differently?

Show model answer
What this tests & where it comes from This is the faculty's own in-class discussion scenario ("Apply the Principles," Lecture 14), turned into an exam question. It deliberately combines two principles rather than testing one in isolation — the examiner wants you to notice both and connect them, not just name the more obvious one.

Two principles are at work here together. First, the pesticide paradox (Principle #5): an unchanged 200-test suite run repeatedly for 18 months will keep passing once it has already caught everything it's capable of catching — a 100% pass rate on a stale suite is not evidence of low risk, only evidence that the suite hasn't been challenged with anything new. Second, testing shows presence of defects, not their absence (Principle #1): because the crashing feature was never part of the original suite, no test ever had the chance to reveal that defect — the passing result said nothing at all about that feature, in either direction. Combining the fixed regression suite with some exploratory testing of new or high-risk areas before release would also have given the untested feature at least some chance of being checked.

Principle 06 of 7

Testing Is Context Dependent

The right amount of testing depends entirely on what's at stake.

A bridge and a garden shed are both "structures," but nobody expects them to be inspected the same way — the cost of a bridge failing is catastrophic, while a shed failing is a minor inconvenience, so the inspection regime for each is calibrated to that risk. Software testing works the same way: testing is done differently depending on the context of the software, and no single "one-size-fits-all" approach works for every system. Relevant context factors include the domain, the risk level, applicable regulation, the user base, and how fast the release cycle moves.

Safety-critical softwareE-commerce website
e.g., aircraft flight control, medical devicesfaster-paced, iterative release cycles
Exhaustive, rigorous testingPrioritizes usability & performance
Formal verification methodsTolerates minor defects if fixed quickly
Regulatory certification (e.g., DO-178C, IEC 62304)Faster testing cycles, less formal process
Key idea

There is no universal "right amount" of testing — it depends on what's at stake.

Watch out

Resist the instinct to answer "more testing is always better." Over-testing a low-risk system wastes time and budget just as surely as under-testing a high-risk one endangers people — the point of this principle is calibration to context, in either direction, not maximization.

Show model answer
What this tests & where it comes from Principle #6 (Testing Is Context Dependent), using the lecture's own contrast pair. The examiner wants named context factors, not just "one is more important than the other."

Two context factors drive the difference. Risk level and regulation: a flight-control system failing can cost lives, so it is subject to exhaustive, rigorous testing, formal verification methods, and mandatory regulatory certification such as DO-178C; an e-commerce site failing typically costs a delayed transaction or a frustrated customer, so that level of rigor would be disproportionate. Release cycle and user base: the e-commerce site iterates quickly to meet shifting user demand and competitive pressure, tolerating minor, quickly-fixed defects in exchange for speed, while a flight-control system's release cycle is slow and deliberate precisely because the cost of a missed defect is so much higher. Neither approach is "more testing" in an absolute sense — each is calibrated to what failure would actually cost in its own context.

Principle 07 of 7

Absence-of-Errors Fallacy

A system with zero known bugs can still be a system nobody can actually use.

Imagine a car that rolls off the assembly line with flawless build quality — no rattles, no defects, every part exactly to spec — but with the steering wheel installed on the wrong side for the country it's being sold in. Mechanically it's perfect. It is still useless to the person who has to drive it. Fixing every known defect doesn't guarantee a useful system, because "correct" and "useful" are answering two different questions.

This is the distinction between verification (did we build the system right — does it match its specification?) and validation (did we build the right system — does it actually meet user and business needs?). A system can be 99%, or even 100%, defect-free by its own specification and still fail if that specification never captured what users actually needed.

Faculty's worked example

A system is delivered on time with zero reported defects — 100% of tests passed. It still fails, because it doesn't support the barcode scanners the warehouse actually uses. Correct, but unusable.

Key idea

Bug-free is not the same as fit-for-purpose.

Watch out

Don't read a QA report showing "0 defects" as automatic proof of success — that report is only telling you the system matches its written specification (verification). Whether that specification captured what users actually need (validation) is a separate question this principle forces you to ask.

Topic 08

Static vs Dynamic Testing

Two complementary ways of checking software — one before you ever run it, one only once you can.

Can you "test" software before a single line of code is even run? Surprisingly, yes — and the lecture treats this as one of the two fundamental ways testing gets done.

Static testing

Static testing examines artifacts without running the code — requirements documents, design models, and source code itself, all inspected as text and structure rather than executed. Because it needs no working code, it can start as early as the requirements or design stage, which is exactly what makes it the practical engine behind Principle #3 (early testing saves money). It's well suited to finding requirement ambiguities, design flaws, standard violations, and unreachable code. Common static techniques include reviews, walkthroughs, inspections, and static analysis tools (these connect back to Reviews & Inspections in Lecture 7 and Software Audits in Lecture 8).

Example: a static analysis tool flags an unused variable, and a peer review catches an ambiguous requirement — "system should respond quickly" — before design even begins.

Dynamic testing

Dynamic testing requires execution: it runs the software with real or simulated inputs and observes actual behavior — outputs, performance, crashes, response times. It necessarily happens later in the SDLC, since it needs working code, unlike static testing. Dynamic techniques include black-box testing, white-box testing, and unit, integration, and system testing.

Example: running a login test case with valid and invalid credentials, then observing whether the system correctly grants or denies access.

Side-by-side comparison
AspectStatic testingDynamic testing
Code execution?NoYes

Key idea

Both are complementary — not competing approaches.

Watch out

"White-box testing" (Lecture 15) is a dynamic technique that happens to use knowledge of the code's internal structure — don't confuse the term with static testing just because it involves looking at code. The distinguishing question is always: does this technique require the software to actually run? White-box testing does; static analysis does not.

Worked example — static vs dynamic in action: a requirements document states "the system should handle a large number of concurrent users." Caught statically, a requirements review flags "large number" as ambiguous and untestable — there's no measurable threshold — and it gets fixed before coding begins. If that review misses it, the same gap is instead caught dynamically: load testing during system testing reveals the app crashes at 500 concurrent users — but only after the system has already been built, making it far more expensive to redesign.

Topic 09

Test Oracles

Something has to decide pass or fail — an oracle is that something.

Every test produces some actual output. But an output on its own doesn't tell you anything — you need to know what the output was supposed to be, so you can compare. A test oracle is the mechanism used to judge a test's outcome: it decides pass or fail. It answers the question, "what did we compare the actual output against?" For simple systems the answer is obvious (a calculator's "2+2" should show "4"), but for complex systems deciding what counts as "correct" behavior isn't always straightforward — this is sometimes called the oracle problem.

Example: a test sends login credentials and observes the response. The oracle is whatever tells us whether "access granted" was the correct response — usually the requirements specification.

Key idea

Every test needs an oracle — even if it's implicit, someone (or something) decides pass or fail.

Four types of test oracle

TypeHow it decides correctness
Specification-basedExpected result derived directly from requirements/spec documents.
Derived (heuristic)Estimated from domain knowledge, prior versions, or reasonable expectations.
Consistency (differential)Compare output against another version of the same system.
No oracle / self-verifyingCheck general properties instead of one fixed expected value.

The lecture's own closing prompt on this table asks: which of these oracle types would be hardest to automate, and why? The usual answer is the derived/heuristic oracle — it relies on a human tester's domain knowledge and judgment about what "feels right," which is exactly the kind of subjective, hard-to-codify check that resists being turned into an automated assertion. A specification-based or property-based oracle, by contrast, can usually be written as an explicit rule a script can check.

Question 11 · warm-up · short answer

What is the difference between a specification-based oracle and a heuristic (derived) oracle? Give an example of each.

Show model answer
What this tests & where it comes from The faculty's own quick-review question 3. It wants the defining difference (source of the expected result) plus a concrete example of each, matching the lecture's own worked table.

A specification-based oracle derives its expected result directly from a requirements or specification document — for example, verifying that a login screen rejects an incorrect password because the requirement explicitly states "shall deny access for invalid credentials." A heuristic (derived) oracle instead estimates the expected result from domain knowledge, prior versions of the system, or reasonable tester expectations, rather than an explicit written rule — for example, judging whether a "Submit" button behaves the way similar buttons behave in comparable applications, based on the tester's own experience rather than a documented spec. The key difference is the source of "correct": an explicit document versus informed judgment.

Applying the same four categories the lecture defines, to new scenarios instead of the ones on the slide:

  1. (a) Consistency (differential) oracle

    Correctness is judged by comparing the new module's output against another version of the same system (the legacy module) — the defining trait of a differential oracle.

  2. (b) No oracle / self-verifying (property-based)

  3. (c) Specification-based oracle

    The expected result — the exact wording — comes directly from a specification document, the defining trait of this oracle type.

  4. (d) Derived (heuristic) oracle

    Correctness is judged using the tester's domain knowledge and prior experience, not a written rule — the defining trait of a heuristic oracle, and typically the hardest of the four to automate.

Topic 10

Test Levels and the SDLC

Different SDLC phases are checked by different levels of testing.

Software isn't tested all at once — it's tested in layers, each aimed at a different scale of the system, and each layer traces back to a specific stage of the development process (a "V-model" style pairing). The higher up the development phase, the higher up the corresponding test level:

These four levels are where everything else in this guide actually gets applied: static and dynamic testing both happen across all of them, and every test at every level still needs a test oracle to decide pass or fail — the levels are the "where," oracles are the "how you judge it," and the seven principles are the "why we test this way" underneath all of it.

Watch out

A very common exam trap: a defect where "two correctly-built modules fail to exchange data properly" sounds like it could be a unit-testing problem (since each module individually works fine), but it's actually an integration testing defect — the scope that specifically targets interfaces and interaction between modules, not the modules' internal correctness.

Question 13 · warm-up · short answer

Which test level would most likely catch a defect where two correctly-built modules fail to exchange data properly? Justify your answer using the scope of that test level.

Show model answer
What this tests & where it comes from The faculty's own quick-review question 4. It's specifically designed to catch students who reason "each module works, so it must be a unit-level issue" — the examiner wants you to recognise the scope shift to interfaces.

Integration testing. Unit testing checks each module in isolation, so a module that is internally correct will pass its unit tests regardless of how well it cooperates with other modules — that's precisely why the defect wasn't caught there. Question 14 · core · apply

For each defect described below, identify the most appropriate test level and justify your answer using its scope.

  • (a) A tax-calculation function returns an incorrect result for negative input values.
  • (b) Data sent from the payment module is not correctly received by the shipping module.
  • (c) The complete checkout workflow fails when exercised end-to-end as a whole system.
  • (d) The delivered dashboard technically works but does not match what business stakeholders actually asked for.
Show worked solution

  1. (a) Unit testing

    The defect is confined to one function in isolation — exactly the scope of unit testing, and boundary/calculation errors are its typical defect category.

  2. (b) Integration testing

    The problem is in the data-passing between two modules, not either module's internal logic — the defining scope of integration testing.

  3. (c) System testing

    The failure only shows up when testing the complete, integrated system as a whole end-to-end — the scope reserved for system testing, run by an independent test team.

  4. (d) Acceptance testing

    The system works technically but is misaligned with business/user needs — precisely the scope and typical defect of acceptance testing, performed by users/clients/stakeholders.

Question 15 · stretch · long answer

A financial services company ships a new feature after its full automated regression suite — unchanged for over a year — passes 100%. Two weeks later, a critical defect is discovered in production that could have been caught by a simple negative-number test case that was never included in the suite. Using at least three named concepts from this lecture, explain: (a) why the passing suite gave false confidence, (b) why the team could never have tested every possible scenario in the first place, and (c) one specific, concrete action that would most improve their testing process going forward.

Show model answer
What this tests & where it comes from A capstone question spanning the whole lecture — it's designed the way a mixed-format final exam often closes a topic, asking you to weave several named principles into one coherent explanation rather than recalling them one at a time.

(a) The false confidence comes from two combined effects. First, Principle #1 (testing shows presence, not absence, of defects): a 100% pass rate only confirms that the tests actually run found nothing — it says nothing about the negative-number case that was never included. Second, Principle #5 (the pesticide paradox): because the suite was unchanged for over a year, it had long since stopped teaching the team anything new — it kept passing not because the software had become safer, but because it was only ever re-checking the same old, already-fixed scenarios.

(b) The team could never have tested every possible scenario because of Principle #2 (exhaustive testing is impossible): the space of possible inputs — including every boundary and edge case such as negative numbers — grows combinatorially, so time, cost, and complexity make full coverage impractical even for one module, let alone a whole financial system. Some form of prioritization was always going to leave some scenario untested; the real failure was which one got left out.

(c) A concrete, specific action: add negative-number and other boundary-value test cases to the regression suite for this feature (closing the immediate gap), and — reflecting the pesticide paradox's remedy — schedule a periodic review of the whole suite (e.g., every release cycle) specifically to retire tests that add no new information and add tests targeting recently changed code and previously missed edge cases, rather than letting the suite run unchanged indefinitely.

Last-minute revision: Testing Fundamentals

1 — Presence, not absence

Testing can reveal defects but never prove their absence, even when none are found.

2 — Exhaustive testing impossible

Can't test every input/path/combination — prioritize by risk instead.

3 — Early testing saves money

Cost to fix roughly: Requirements 1× → Design 5× → Coding 10× → Post-release 100×.

4 — Defect clustering

Pareto pattern: ~80% of defects typically found in ~20% of modules; history predicts risk.

5 — Pesticide paradox

Unchanged tests stop finding new bugs, like pests becoming immune to a repeated pesticide. Refresh and vary the suite.

6 — Context dependent

No universal "right amount" of testing — rigor matches risk/domain (safety-critical ≠ e-commerce).

7 — Absence-of-errors fallacy

Bug-free ≠ fit-for-purpose. Must validate (right system), not just verify (built right).

Static vs dynamic

Static = examine artifacts, no execution, early, cheaper. Dynamic = run the software, later, needs working code.

Test oracle types

  • Specification-based — from requirements
  • Derived (heuristic) — domain knowledge
  • Consistency (differential) — vs another version
  • No oracle — check general properties

Test levels (low → high)

  • Unit — developers, isolated functions
  • Integration — dev/testers, module interfaces
  • System — independent team, whole system
  • Acceptance — users/stakeholders, business needs
