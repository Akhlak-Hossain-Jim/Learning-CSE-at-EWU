Integration Testing

Course: CSE430 — Software Testing and Quality Assurance (East West University) Based on: Integration Testing (Dr. Shamim Hasnat Ripon) Exam: ~25 Aug 2026 (mixed format)
Topic 01

What integration testing is, and why it exists

Context first: where integration testing sits among the four testing levels, then the definition, the motivation, and the trade-offs.

Think of building a car. One team builds the engine, another the brakes, another the dashboard electronics. Each team can bolt their own part onto a test rig and check that it works — that is unit testing: testing one component in isolation. But a working engine and a working dashboard don't guarantee the dashboard's "check engine" light actually turns on when the engine misfires. Something has to test the connections between the parts. That is integration testing.

The lecture frames this as four fundamental levels of software testing, each looking at the system from a different vantage point:

01 · Unit Testing
testing individual components 02 · Integration Testing
testing component groups 03 · System Testing
testing the integrated system 04 · Acceptance Testing
testing the final system

Definition, in the faculty's words

Integration testing means you integrate/combine unit-tested modules one by one and test the behaviour as a combined unit. Its main goal is to test the interfaces between the units/modules — not to re-check what each module does internally (unit testing already covered that), but to check what happens at the seams where modules talk to each other.

The normal order is: unit test each module in isolation first, then start integrating the unit-tested modules one at a time, checking the combined behaviour after each addition, until every module is integrated and you've validated that the requirements are implemented correctly as a whole.

Key idea

Unit testing asks "does this one piece work?" Integration testing asks "do these pieces work together?" — same modules, different question, different bugs.

Why bother — where the bugs actually come from

When an application is broken into modules, different developers usually build different modules. That alone creates risk, for reasons the lecture calls out directly:

  • Different developers, different logic. Two people rarely implement the same kind of decision the same way, so it becomes important to check whether the logic one developer wrote actually matches what the next module expects.
  • Data changes shape as it travels. A value that looks fine leaving Module A might get fields appended or stripped by the time it reaches Module B — and that mismatch only shows up once the two are connected.
  • Third-party tools and APIs. Modules often call out to external services; you need to check both that you're sending correct data to that API and that you're handling the response it sends back correctly.
  • Frequent requirement changes. A very common real-world problem: a developer ships a change without unit testing it. Integration testing is what catches the resulting interface break before it reaches users.

Advantages

  • It makes sure the integrated modules/components work properly — not just each one alone.
  • You can start integration testing as soon as the modules you need are available — you don't have to wait for every other module to be finished, because stubs and drivers (next section) can stand in for the missing pieces.
  • It specifically detects errors related to the interface — exactly the class of bug unit testing structurally cannot see.

Challenges

  • It's not enough to test just the integration links — an exhaustive test considering the whole environment is needed, because there can be many different paths and permutations through an integrated system.
  • Managing it gets complex fast because of factors like the database, the platform, and the environment all being in play at once.
  • Integrating a new system with a legacy system (or two legacy systems with each other) requires heavy changes and testing effort.
  • Integrating two systems built by two different companies is especially risky: you often can't be sure how a change in one system will ripple into the other.
Watch out

A very common exam trap: describing integration testing as "just running unit tests together." It isn't — it targets a different failure class (interfaces, data hand-off, control flow between modules), not internal module logic.

Topic 02

Big Bang vs. Incremental — and the dummy programs both may need

The first fork in the road: integrate everything at once, or a few modules at a time. Then meet stubs and drivers, which make the incremental route possible.

There are two families of integration strategy. The lecture lays them out as one tree:

Types of integration testing
Integration Testing
↓
Big Bang Approach Incremental Approach
↓ (incremental splits three ways)
Top-Down Bottom-Up Sandwich

Big Bang integration

Once every module has been developed and unit tested individually, you integrate all of them at once and test the whole assembled system in one shot — like connecting all the wires in a circuit only after every component has been soldered, then flipping the power switch for the first time.

AdvantagesDisadvantages
Suitable for smaller systems — genuinely, the lecture calls out this as the only advantage.
  • Fault localisation is tough (a failure could be anywhere among dozens of modules)
  • A lot of delay before testing can even begin
  • Critical issues don't get resolved on priority
  • Difficult to find the root cause of problems
Watch out

Students often assume "test everything together" sounds thorough and therefore good. On the exam, the correct framing is the opposite: Big Bang is the weak default, tolerable only for small systems, precisely because it makes debugging so hard.

Incremental integration — the overview

Incremental testing connects two or more logically related modules together first, tests that small group, then adds more modules and re-tests, repeating until every module is integrated and tested successfully. It comes in three flavours — Bottom-Up, Top-Down, and Sandwich — covered in the next three sections.

Stubs and drivers: the dummy stand-ins

Here's the practical problem incremental testing runs into immediately: if you want to test Module A together with Module B, but Module B isn't built yet, you're stuck — unless you fake Module B. That's exactly what the lecture means when it says: while testing, some modules are still under development, so for testing purposes they get replaced with dummy programs. These dummy programs are called stubs and drivers.

The direction of the "calling" relationship is what decides which dummy you need. Take the lecture's own example: Component 1 = Login Page (Module A) calls Component 2 = Admin Page (Module B).

Application vs. stub-testing vs. driver-testing

Key idea — the one distinction the exam loves to test

A stub is a dummy stand-in for a module that is called — it fakes something below the module you're testing. A driver is a dummy stand-in for a module that calls — it fakes something above the module you're testing. Say it out loud: "stub = fake subordinate, driver = fake driver-seat caller."

For simple applications a stub can just return control straight back to its caller; for complex applications (say, the called module normally talks to a database) the stub has to simulate a realistic range of responses. Drivers, similarly, invoke the module under test, pass it test data, and receive its output data, standing in for whatever higher-level module doesn't exist yet.

Watch out

Don't memorise "stub goes with top-down, driver goes with bottom-up" as an arbitrary rule — derive it. Top-down testing starts at the top and the modules below aren't ready yet, so you stub them. Bottom-up testing starts at the bottom and the modules above (the callers) aren't ready yet, so you need drivers to call the bottom modules. The direction of missing-module always matches the direction you're testing away from.

Topic 03

Top-Down Integration Testing

Start at the top of the control flow, work downward, and stub whatever isn't built yet.

Top-down testing starts by testing the top-most module(s) and gradually moves down to the lowest set of modules, one by one — following the control flow of the software system from top to bottom. Since the lower-level modules a top module calls might not exist yet, you plug in stubs in their place. For simple applications the stub just hands control back; for complex applications (e.g. one that would normally hit a database) the stub has to simulate the full range of expected responses — which in practice is often harder than it first sounds.

AdvantagesDisadvantages
  • Fault localisation is easier (you add one layer at a time)
  • The test product is extremely consistent
  • Stubs are quicker to write than drivers
  • Critical / high-level modules are tested on priority
  • Major design flaws surface as early as possible
  • Requires several stubs
  • Poor support for early release of low-level functionality
  • Basic (low-level) functionality is only tested at the end of the cycle
Key idea

Top-down proves the high-level control flow and business logic first — good when you want confidence in the "shape" of the system early, at the cost of not exercising the lowest-level, most detailed logic until late.

Topic 04

Bottom-Up Integration Testing

Start at the lowest units, work upward, and drive whatever caller isn't built yet.

Bottom-up testing starts with the lowest units of the application and gradually moves up, one by one — testing takes place from the bottom of the control flow upwards. Integration continues until all modules are integrated and the entire application is tested as a single unit.

Because it's entirely possible that a higher-level module hasn't been developed yet by the time its lower modules are ready and unit-tested, the missing caller's functionality is simulated with a driver — a program that invokes the module under test, passes it test data, and receives its output.

Faculty's worked example — module tree
A
↓ ↓
B1 B2
↓ ↓      ↓ ↓
B1C1 B1C2 B2C1 B2C2

B1C1, B1C2, B2C1, B2C2 are the lowest modules, and they're already unit tested. But B1 and B2 are not yet developed — their job would be to call B1C1/B1C2 and B2C1/B2C2 respectively. Since B1 and B2 don't exist yet, you need a "stimulator" program that calls B1C1, B1C2, B2C1, B2C2 in their place: that stimulator is the driver.

AdvantagesDisadvantages
  • Development and testing can proceed together, so the product ends up more efficient overall
  • Test conditions are much easier to create at the low level
  • Requires several drivers
  • Data flow between modules is only tested very late
  • The need for drivers complicates test data management
  • Poor support for early release
  • Key interface defects are detected late
Watch out

Notice top-down and bottom-up have almost mirror-image trade-offs: top-down finds design/interface flaws early but leaves low-level logic untested until late; bottom-up nails down low-level logic early but leaves the actual data flow and interfaces between high-level modules untested until late. Neither is strictly "better" — that's precisely why Sandwich exists.

Topic 05

Sandwich (Hybrid) Integration Testing

Take the best of both directions at once, and Big-Bang the middle.

To overcome the limitations of top-down and bottom-up while keeping their advantages, you can run a hybrid: sandwich integration testing (also called mixed integration testing). The system is viewed as three layers:

  • A main target layer in the middle — the layer you actually care about testing.
  • A layer above the target layer.
  • A layer below the target layer.

Top-down is used from the top layer down to the middle layer; bottom-up is used from the bottom layer up to the middle layer; and the Big Bang approach is used to assemble the modules that make up the middle layer itself.

Faculty's worked example — three layers
M1
Layer 1 (top-down meets here ↓)
M2 M3 M4
Layer 2 — main target layer (Big Bang inside this row)
M5 M6 M7
Layer 3 (bottom-up meets here ↑)
AdvantagesDisadvantages
  • Top-down and bottom-up work can happen in parallel, or one after the other
  • Very useful for large enterprises and huge projects with several subprojects
  • Cost requirement is very high
  • Cannot be used for smaller systems that have huge interdependence between modules
  • Different skill sets are required for testers working at different levels
Key idea

Sandwich isn't a fourth, independent technique — it's literally "run top-down on the top half, bottom-up on the bottom half, and Big Bang the middle where the two meet." If you can explain top-down, bottom-up, and Big Bang, you already know sandwich.

Topic 06

The M1–M7 comparison: watching both approaches integrate the same tree

The same seven-module tree, integrated two different ways — this is the faculty's direct side-by-side, and a favourite source of exam questions.

Take one fixed module tree: M1 at the top, with children M2, M3, M4; M3 has a child M5; M4 has children M6 and M7.

Shared tree for this comparison
M1
↓
M2 M3 M4
↓ (from M3)        ↓ ↓ (from M4)
M5 M6 M7

Bottom-Up order

Bottom-up starts at the leaves and works up, using drivers for whichever parent isn't attached yet:

Stage 1 M5M6M7M2 — each leaf cluster tested alone (M2 has no children, so it's a leaf too); drivers stand in for M3, M4, M1
Stage 2 M3+M5M4+M6+M7 — each parent is joined to its now-real children; a driver still stands in for M1
Stage 3 M1+M2+M3+M4+M5+M6+M7 — M1 joins in for real; drivers are gone, full system integrated

Top-Down order

Top-down starts at the root and works down, using stubs for whichever child isn't attached yet:

Stage 1 M1 — tested alone, with stubs for M2, M3, M4
Stage 2 M1+M2+M3+M4 — real M2, M3, M4 added; stubs now cover M5, M6, M7
Stage 3 M1+M2+M3+M4+M5 — M3's stub is swapped for the real M5; M6, M7 still stubbed
Stage 4 M1+M2+M3+M4+M5+M6+M7 — M6 and M7 join in for real; full system integrated
Key idea

Bottom-up grows the tree from several small clusters at once and merges them upward (fewer, bigger stages). Top-down grows the tree from a single root and widens/deepens it one level at a time (one module or one level added per stage). Same tree, same seven modules, genuinely different order and different intermediate states — which is exactly why the choice of approach changes what gets tested early versus late.

Topic 07

Worked example: GUI / multitier integration testing

A concrete, black-box style example of integration testing on a real multitier web application — this is the lecture's central applied example.

A web application is typically a multitier application: a front end visible to the user, a middle layer holding business logic and validation (and often third-party API integrations), and a back layer that's the database. The lecture's running example: an advertising company posts ads on different websites, and at month's end the owner wants a report of how many people saw the ads and how many clicked, so clients can be billed accordingly.

Architecture (front layer → middle layer → back layer)
Front layer
UI
⇄
Middle layer
BL VAL CNT
⇄ all three feed into →
EN (Engine)
⇅ also talks to
Scheduler
→
Back layer
DB

What each module does, in the faculty's own definitions:

  • UI — the User Interface module, visible to the end user, where all inputs are given.
  • BL — the Business Logic module: all the calculations and business-specific methods.
  • VAL — the Validation module: validates the correctness of the input.
  • CNT — the Content module: holds static content specific to what the user entered, displayed in the reports.
  • EN — the Engine module: reads all the data coming from BL, VAL and CNT, extracts the SQL query from it, and fires it at the database.
  • Scheduler — schedules the reports based on the user's selection (monthly, quarterly, semiannually, annually).
  • DB — the Database.

Where XML comes in

In the real world this hand-off between modules is usually done in XML format. So whatever data the user enters into the UI gets converted into an XML document, which the BL, VAL, and CNT modules interpret. The EN module reads the resulting XML generated by those three, extracts the SQL from it, and queries the database. EN then converts the result set it gets back into another XML document and returns it to the UI, which converts it into a human-readable form for display. In the middle, the Scheduler receives the result set from EN and uses it to create and schedule the reports.

Key idea — where integration testing actually lives here

Testing whether this data flows correctly is the integration test. Concretely, that means: are the XML files generated correctly? Do they carry the correct data? Is the data transferred correctly from one module to the next? In practice you try to capture or generate the actual XML files, inspect/alter their tags, and observe the behaviour — a different flavour of testing from ordinary black-box testing, but one that builds a much deeper understanding of the application.

The faculty's nine verification questions

These are the exact questions the lecture poses to illustrate what "checking the integration" means for this architecture:

  1. How will the BL, VAL and CNT modules read and interpret the data entered in the UI module?
  2. Is BL, VAL and CNT module receiving the correct data from UI?
  3. In which format is the data from BL, VAL and CNT transferred to the EN module?
  4. How will the EN read the data and extract the query?
  5. Is the query extracted correctly?
  6. Is the Scheduler getting the correct data for reports?
  7. Is the result set received by the EN, from the database, correct and as expected?
  8. Is EN able to send the response back to the BL, VAL and CNT module?
  9. Is the UI module able to read the data and display it appropriately on the interface?

Three of them, worked as mini test-design examples

Q2 — "Is BL, VAL and CNT receiving the correct data from UI?" In practice: enter a known set of values into the UI, capture the XML document the UI produces, and check field-by-field that every value the user typed actually appears in the XML, untruncated and in the right tag. If the UI silently drops a field converting it to XML, BL/VAL/CNT will never see it — and no amount of testing BL/VAL/CNT in isolation would ever have caught that.

Q3 — "In which format is data from BL, VAL and CNT transferred to EN?" The lecture's answer is XML. The test isn't "does XML exist" — it's schema-level: does the XML EN receives use the tags EN expects, in the structure EN's parser expects? A tag renamed on one side and not the other is a classic integration bug that unit tests on either side, run alone, would both pass.

Q7 — "Is the result set received by EN from the database correct and as expected?" This checks the return trip: EN built a SQL query from the merged BL/VAL/CNT data, fired it at the DB, and got rows back. You'd verify the query EN actually built matches the input (e.g. the right date range, the right client ID) and that the rows returned match what's really in the DB for that query — not what EN merely assumes it asked for.

A few other sample test conditions the lecture calls out

  • Are the menu options generating the correct window?
  • Are the windows able to invoke the window under test?
  • For every window, identify the function calls it should allow, and all calls it should be able to make to other features.
  • Identify reversible calls: closing a called window should return you to the calling window.
  • Identify irreversible calls: the calling window closes before the called window appears.
  • Test the different ways of triggering a call to another window — e.g. menus, buttons, keyboard shortcuts.
Topic 08

Kicking off integration testing

An eight-step process for going from "here's an architecture" to "here are runnable test cases."

The lecture gives a concrete, ordered checklist for starting integration testing on any system:

  1. Understand the architecture of your application.
  2. Identify the modules.
  3. Understand what each module does.
  4. Understand how data is transferred from one module to another.
  5. Understand how data is entered into and received from the system (the entry point and exit point of the application).
  6. Segregate the application to suit your testing needs.
  7. Identify and create the test conditions.
  8. Take one condition at a time and write down the test cases.
Key idea

Notice the order: you understand the system (steps 1–5) completely before you touch a single test case (steps 7–8). Step 6 — segregating the application — is where you'd decide top-down vs. bottom-up vs. sandwich, based on what you learned in steps 1–5.

Topic 09

Entry/exit criteria and what integration test cases actually check

When are you allowed to start, when are you allowed to call it done, and what do the test cases themselves focus on?

Entry criteria

  • The integration test plan document is signed off and approved.
  • Integration test cases have been prepared.
  • Test data has been created.
  • Unit testing of the developed modules/components is complete.
  • All critical and high-priority defects (from unit testing) are closed.
  • The test environment is set up for integration.

Exit criteria

  • All integration test cases have been executed.
  • No critical, P1, or P2 defects remain open.
  • A test report has been prepared.
Watch out

Entry criteria include "unit testing complete" — integration testing is not a substitute for unit testing, and starting it before units are individually verified just buries interface bugs under module bugs, making both harder to diagnose.

What integration test cases focus on

Because the modules being integrated are already unit tested — their functionality and other testing aspects are already covered — integration test cases zero in on three things: the interface between the modules, the integrated links, and the data transfer between them. The core idea is simple: check that two modules which each work fine on their own also work as expected once wired together.

Worked example: LinkedIn-style test cases

The lecture illustrates this with sample integration test cases for a LinkedIn-like application. Each one is phrased as "verify the interface link between page X and page Y":

  • Verify the interface link between the login page and the home page — i.e. when a user enters valid credentials and logs in, they should be directed to the home page.
  • Verify the interface link between the home page and the profile page — the profile page should open up correctly.
  • Verify the interface link between the network page and the connections page — clicking "Accept" on an invitation from the network page should make that connection show up on the connections page.
  • Verify the interface link between the notifications page and the "say congrats" button — clicking it should direct the user to a new message window.

Every one of these is testing a hand-off: an action on one screen, and the correct consequence appearing on the next screen. That pattern — action here, verified consequence there — is exactly what integration test cases are for, and it's the pattern you'll reuse in the practice questions below on a new scenario.

Topic 10

Is integration testing white box or black box?

A trick question by design — the lecture poses it, then answers "it depends."

Black box testing means the tester needs no internal knowledge of the system — no coding knowledge required, you only care about inputs and outputs. White box testing means you need internal knowledge of the application (its code, its structure) to design the tests.

Integration testing can be done using either technique, depending on what exactly you're integrating:

  • Testing two integrated web services that fetch data from a database and return it as required often needs white-box knowledge — you may need to understand the service's internal query logic to design meaningful tests.
  • Testing a new feature being integrated into a website can typically be tested using black-box technique — you just check that the feature behaves correctly from the outside.
Key idea (the faculty's actual answer)

It's not fixed either way. Integration testing can be counted as both a black-box and a white-box technique — which one applies depends on the specific modules being integrated and how much internal knowledge you need to design a meaningful test for that particular seam.

Topic 11

Tools, and how integration testing differs from system testing

Integration testing tools

The lecture lists several tools available for integration testing:

  • Rational Integration Tester
  • Protractor
  • Steam
  • TESSY

Integration testing vs. system testing

Integration testingSystem testing
One or two modules that are already unit tested get integrated, and verification checks whether the integrated modules work as expected together. The system as a whole is tested — all modules/components are integrated together, to verify the entire system works as expected and no issues arise from having integrated the modules.
Key idea

Scale is the difference, not technique. Integration testing looks at a seam or a small cluster of modules; system testing looks at the fully-assembled product end to end. In the M1–M7 tree, every intermediate stage (M3+M5, M1+M2+M3+M4, etc.) is an integration-testing moment; only the very last, fully-assembled stage is what system testing then takes over and evaluates as a whole.

Topic 12

Practice questions

Attempt each one before revealing the solution. They span recall, applied scenario-design, and one question that forces you to weigh trade-offs across all four approaches at once.

Question 1 · short answer, easy

In your own words: what is integration testing, and why is it normally done after unit testing rather than instead of it?

Show model answer
What this tests & where it comes from Tests the core definition from Topic 1 — specifically whether you can articulate that integration testing targets interfaces, not internal module logic, and why unit testing has to come first.

Integration testing combines unit-tested modules and tests their combined behaviour, with its main goal being to test the interfaces between the modules — the seams where data or control passes from one module to another. It comes after unit testing because unit testing already verifies that each module's internal logic is correct in isolation; if you skip straight to integration, a failure could be caused either by a module's own bug or by a bad interface, and you'd have no way to tell which. Doing unit testing first removes one whole source of failure, so integration testing can assume "each piece works alone" and focus purely on whether the pieces work together.

Question 2 · compare/contrast, easy

Distinguish a stub from a driver: what does each replace, and in which integration approach does each get used?

Show model answer
What this tests & where it comes from This is the single most confusable pair in the whole topic (Topic 2). The examiner wants you to connect "which module is missing" to "which dummy program fills the gap" to "which approach that implies."

A stub is a dummy program that stands in for a module that gets called — it fakes something below/downstream of the module under test. A driver is a dummy program that stands in for a module that calls — it fakes something above/upstream, invoking the module under test, feeding it data, and collecting its output. Stubs are used in top-down integration, because when you test from the top down, the lower modules a top module calls aren't built yet. Drivers are used in bottom-up integration, because when you test from the bottom up, the higher-level caller of a low module isn't built yet. (Using the lecture's Login/Admin Page example: a dummy Admin Page standing in for the real one is a stub; a dummy Login Page standing in as the caller is a driver.)

Question 3 · compare/contrast, easy

Compare Big Bang integration with Incremental integration. Under what circumstance would each be the more reasonable choice?

Show model answer
What this tests & where it comes from Tests Topic 2's overview — the examiner wants a genuine trade-off comparison, not just two definitions side by side.

Big Bang integrates every unit-tested module at once and tests the whole assembled system in a single pass; its only real advantage is that it suits small systems, and its costs are steep — fault localisation is tough, there's a long delay before any testing happens, critical issues don't get fixed with priority, and root causes are hard to find. Incremental integration connects a small, logically related group of modules, tests it, adds more modules, and repeats — via top-down, bottom-up, or sandwich. Big Bang is reasonable only when the system is small enough that "test it all at once and debug whatever breaks" is still tractable. For anything nontrivial, incremental is the safer default, because it isolates failures to a small, recently-added group of modules instead of the whole system at once.

Question 4 · scenario, medium

A team is building QuickBite, a food-ordering app, with this module dependency tree:

F1 · QuickBite App (root UI)
↓
F2 · OrderManager F3 · NotificationManager
↓ ↓        ↓ ↓
F4 · PaymentService F5 · InventoryService F6 · SMSGateway F7 · EmailGateway

Management wants to demo the app's main screen flow to stakeholders as early as possible, even if payment and notifications aren't fully wired up yet. Which incremental approach fits best, what would you need to simulate at each stage, and in what order would modules be added?

Show worked solution
What this tests & where it comes from Applies Topic 3 (top-down) to a fresh tree, in the style of the M1–M7 comparison (Topic 6) — the examiner wants you to reason from "what does the business priority imply" to "which approach" to "concrete stage-by-stage order."

Top-down is the right fit. "Demo the main screen flow early" means the priority is the top-level control flow (F1 → F2/F3) — exactly what top-down tests first, since it starts at the top and stubs whatever is below.

  1. Stage 1: test F1 alone.

    F1 is the root; stub out F2 and F3 since neither exists yet in this stage.

  2. Stage 2: integrate F1 + F2 + F3.

    Replace the F2 and F3 stubs with the real modules; now stub F4, F5, F6, F7 (the next level down) since the demo doesn't need them working yet.

  3. Stage 3: integrate F1 + F2 + F3 + F4 + F5.

    Swap in real PaymentService and InventoryService once ready; F6/F7 stay stubbed if notifications are still lower priority.

  4. Stage 4: integrate all seven modules.

    Swap in real SMSGateway and EmailGateway last; full system integrated.

Answer

Top-down, because it lets the team demonstrate and validate the top-level flow (F1→F2→F3) immediately using stubs, and defer the lower-priority, lower-level modules (payment, inventory, notifications) to later stages — matching exactly what the business asked for.

Question 5 · scenario, medium

Same QuickBite tree as Question 4 — but now suppose the situation is reversed: PaymentService (F4), InventoryService (F5), SMSGateway (F6), and EmailGateway (F7) are all finished and unit tested first, while OrderManager (F2), NotificationManager (F3), and the root app UI (F1) are still being built. Which approach now fits naturally, and what will the team need to simulate as they go?

Show worked solution
What this tests & where it comes from Tests whether you can tell that the same tree calls for a different approach once the order in which modules become available flips — direct application of Topic 4.

Bottom-up fits here. The lowest-level modules (F4, F5, F6, F7) are ready first, but their callers (F2, F3, and ultimately F1) aren't — exactly the situation bottom-up is designed for.

  1. Stage 1: test F4, F5, F6, F7 individually.

    Each is a leaf module; since F2 and F3 (their callers) don't exist yet, a driver is needed to invoke each one and feed it test data.

  2. Stage 2: integrate F2 with F4+F5, and F3 with F6+F7.

    Once OrderManager and NotificationManager are built, they replace the drivers that were calling their respective children directly.

  3. Stage 3: integrate F1 with F2 and F3.

    Once the root app UI is ready, it replaces whatever driver was standing in as its caller, and the whole tree is now real, no dummies left.

Answer

Bottom-up — because development finished the low-level modules first, and drivers let testing start on them immediately rather than waiting for OrderManager, NotificationManager, and the app UI to exist.

Question 6 · identify stub/driver/neither, medium

For each mini-scenario below, say whether the tester needs a stub, a driver, or neither — and why.

  1. You want to test the Login module, which calls a Payment module, but Payment hasn't been built yet.
  2. You want to test the ReportGenerator module, which is called by the Dashboard module, but Dashboard hasn't been built yet.
  3. You want to test the Validation module. Its caller (Controller) is already built and working, and the module it calls (DatabaseAdapter) is also already built and working.
Show model answer
What this tests & where it comes from Direct application of the stub/driver distinction (Topic 2), including the trap case (c) where neither dummy is needed — an easy mark to lose if you assume every integration test needs a dummy program.

(a) Stub. Payment is a module Login calls, and it doesn't exist yet — you need a dummy called-program (a stub) standing in for Payment.

(b) Driver. Dashboard is the module that calls ReportGenerator, and it doesn't exist yet — you need a dummy calling-program (a driver) to invoke ReportGenerator and feed it test data.

(c) Neither. Both the caller and the callee already exist and work — this is a plain integration test between two real, ready modules. Stubs and drivers only exist to cover for a module that isn't ready; when everything needed is already built, you integrate the real modules directly.

Question 7 · scenario, medium

A payroll system has three layers: a PayrollUI on top; a middle layer of SalaryCalculator, TaxDeductor, and BonusEngine (the layer the QA team cares most about); and a bottom layer of EmployeeDB, TaxRatesAPI, and BonusRulesDB. The team decides to use sandwich integration. Describe what happens at each of the three layers.

Show model answer
What this tests & where it comes from Direct application of Topic 5 (sandwich testing) to a new three-layer scenario, mirroring the faculty's M1–M7 sandwich diagram.

The middle layer (SalaryCalculator, TaxDeductor, BonusEngine) is the main target layer, and its three modules are assembled and tested together using the Big Bang approach, since it's the layer under the closest scrutiny. Between the top layer and the middle layer, a top-down approach is used: PayrollUI is tested first, stubbing the middle-layer modules until they're ready, then integrated down into them. Between the bottom layer and the middle layer, a bottom-up approach is used: EmployeeDB, TaxRatesAPI, and BonusRulesDB are tested with drivers standing in for the middle-layer modules that call them, then integrated upward as those modules become ready. The two directions can run in parallel or one after another, and they converge at the middle layer.

Question 8 · applied, medium

Referring to the GUI/multitier example (UI / BL / VAL / CNT / EN / Scheduler / DB): the lecture's Question 3 asks, "In which format is the data from BL, VAL and CNT transferred to the EN module, and is that transfer actually correct?" Concretely, what would you check to answer this, beyond just confirming "yes, it's XML"?

Show model answer
What this tests & where it comes from Reproduces one of the lecture's nine verification questions (Topic 7) and asks you to turn it into an actual test design — the examiner wants concrete checks, not a one-word restatement.

Knowing the format is XML is only step one. To actually verify the hand-off you would: (1) capture the real XML document that BL, VAL, and CNT produce for a known input; (2) confirm it's well-formed XML that EN's parser can read without error; (3) check that the tag names and structure match what EN's parsing logic expects — a tag renamed on one side and not the other would break the hand-off even though both sides individually "work"; (4) confirm no data is lost or truncated between what BL/VAL/CNT wrote and what EN reads back; and (5) check that types and encoding are consistent (e.g. a numeric field isn't silently read as text). Each of these is a place the two sides could individually pass their own unit tests while still failing to communicate correctly — which is exactly the class of bug integration testing exists to catch.

Question 9 · applied, medium

Still on the GUI/multitier example: the lecture also asks, "Is the result set received by EN from the database correct and as expected?" Explain what could go wrong here even if the EN module and the database are each functioning correctly on their own.

Show model answer
What this tests & where it comes from Another of the lecture's nine verification questions (Topic 7), used to reinforce that "each side works alone" does not imply "the seam works" — the central theme of the whole topic.

EN builds a SQL query out of the merged BL/VAL/CNT data and fires it at the database; the database then returns whatever rows match that exact query. Even if EN's query-building logic is bug-free and the database correctly executes whatever query it's given, the integration can still fail if EN builds the wrong query from otherwise-correct input — for example, using the wrong date range field, mismatching a client ID, or misreading a filter that VAL sent through. The database would then correctly return rows for the wrong question, and both EN and the database would individually "pass" their own tests while the report shown to the ad company's owner is quietly wrong. Verifying this means checking the actual SQL EN generates against the input, not just checking that EN returns some result set.

Question 10 · worked test-case design, core

A university is building CampusEvents, an app with these screens: Login → Dashboard → Event Details → tapping "RSVP" → Confirmation page, which also triggers a Notifications page entry reminding the student closer to the event date. In the style of the lecture's LinkedIn example, write four integration test cases for this flow.

Show worked solution
What this tests & where it comes from Directly extends the lecture's LinkedIn-app worked example (Topic 9) to a new scenario. Each LinkedIn test case had the same shape — action on one screen, verified consequence on the next — and that shape is what's being reused here.

  1. Verify the interface link between the Login page and the Dashboard.

    Mirrors the LinkedIn "login page → home page" case: entering valid credentials should direct the user to the Dashboard, not leave them on Login or show an error.

  2. Verify the interface link between the Dashboard and the Event Details page.

    Mirrors "home page → profile page": tapping an event card on the Dashboard should open the correct Event Details page — for that specific event, not a different one.

  3. Verify the interface link between the Event Details page's "RSVP" button and the Confirmation page.

    Mirrors "network page → connections page after Accept": tapping RSVP should produce a Confirmation page reflecting that this student is now registered for this specific event.

  4. Verify the interface link between a successful RSVP and the Notifications page.

    Mirrors "notifications page → say congrats → new message window": completing an RSVP should create an entry on the Notifications page that will remind the student before the event — checking that the RSVP action correctly propagates into a different module (notifications) than the one the user is looking at.

Answer

Each test case names two screens/modules and one action, and specifies the exact consequence expected on the other side — that action→consequence pairing across a module boundary is what makes it an integration test case rather than a UI or unit test case.

Question 11 · scenario, easy–medium

A test lead says: "Unit testing on three of our five modules is still incomplete, but let's start integration testing anyway to save time." Using the entry/exit criteria, explain whether this is a good idea.

Show model answer
What this tests & where it comes from Direct application of the entry criteria list (Topic 9) to a realistic project-management scenario.

No — this violates one of the stated entry criteria directly: "Unit testing of developed modules/components is complete" must be satisfied before integration testing begins. Starting early with two-fifths of the modules unverified means any failure found during integration could be caused by an internal bug in one of those unverified modules rather than by a genuine interface problem, and there would be no way to tell which without going back and unit testing them anyway. Rather than saving time, this typically costs more time overall, since defects get muddled together and root-causing becomes harder — exactly the failure mode entry criteria exist to prevent.

Question 12 · short answer, easy

Is integration testing a white box technique or a black box technique? Justify your answer with an example.

Show model answer
What this tests & where it comes from Direct recall + justification from Topic 10 — the examiner is checking you don't force a false either/or answer.

Neither exclusively — it can be either, depending on what's being integrated. If you're integrating two web services that fetch data from a database and you need to understand their internal query logic to design a meaningful test, that's white-box in character. If you're integrating a brand-new feature into an existing website and you're only checking that it behaves correctly from the outside — without needing to know how it's coded internally — that's black-box in character. Since the same testing level (integration) can be approached either way depending on the specific modules involved, integration testing is not fixed to one category.

Question 13 · compare/contrast, short answer

Distinguish integration testing from system testing. Give an example of a test activity that belongs to each.

Show model answer
What this tests & where it comes from Direct recall from Topic 11 — the examiner wants the scope distinction, not a vague "they're similar" answer.

Integration testing checks one or two unit-tested modules once they're combined, verifying that the integrated modules work together as expected — for example, checking that the OrderManager module correctly hands data to the PaymentService module. System testing checks the system as a whole, once every module/component has been integrated, to verify that the whole application behaves correctly and that no issues have arisen purely from having combined all these modules — for example, placing an entire order end-to-end through the finished QuickBite app and confirming the receipt, inventory update, and notification all happen correctly together. In short: integration testing checks seams a few modules at a time; system testing checks the fully-assembled product as a single whole.

Question 14 · stretch — combines all four approaches, hard

A hospital is building a Patient Records System with this tree:

H1 · PatientPortal (UI)
↓
H2 · AppointmentManager H3 · RecordsManager
↓ ↓        ↓ ↓
H4 · DoctorAvailabilityAPI H5 · SMSReminder H6 · LabResultsDB H7 · PrescriptionDB

Constraints: (i) the hospital's compliance office needs to see the core patient-safety flow — records lookup and prescriptions — working correctly and demoed very early, before anything else; (ii) the team has a very limited budget for writing dummy programs, and has noted that stubs for H4–H7 would be more complex to write than drivers for H2/H3, since H4–H7 involve real external APIs and databases with complicated response shapes; (iii) this is a single, tightly-coupled small system, not a multi-team enterprise project. Recommend an approach (you may combine ideas), and justify it against all three constraints — including explaining why the other approaches you rejected don't fit as well.

Show worked solution
What this tests & where it comes from A stretch question combining Topics 2–5: it forces you to weigh Big Bang, top-down, bottom-up, and sandwich against each other on the same scenario, using the exact advantage/disadvantage lists from the lecture rather than picking an approach by name-recognition alone.

  1. Rule out Big Bang.

    Even though constraint (iii) says it's a small system — Big Bang's one listed advantage — the compliance office needs an early demo of a specific flow, and Big Bang offers no visibility until every module is finished and integrated at once. That directly conflicts with constraint (i).

  2. Rule out Sandwich.

    Sandwich is explicitly disadvantaged for tightly-coupled small systems (per the lecture's own disadvantage list) and has a high cost requirement — conflicting with both constraint (ii) and (iii). It's really meant for large, multi-subproject enterprises, which this isn't.

  3. Compare Top-Down vs. Bottom-Up against constraint (i).

    Constraint (i) wants the H1→H3 records/prescriptions flow demoed early. Top-down naturally front-loads exactly this: test H1 alone, then H1+H2+H3, giving a working (stubbed) records/prescriptions flow at the UI level in just two stages.

  4. Compare Top-Down vs. Bottom-Up against constraint (ii).

    Top-down needs stubs for H4–H7; the team already noted stubs for these would be complex (real external APIs/DBs with complicated responses) — a genuine cost. Bottom-up would need drivers for H2/H3 instead, which the team says are simpler to write. This point favours bottom-up.

  5. Resolve the conflict: recommend Top-Down anyway, with a narrowed scope.

    Constraint (i) is explicitly a compliance requirement — a hard priority, not a preference — while constraint (ii) is a cost concern that can be mitigated: write only simple "return a fixed valid response" stubs for H4–H7 at first (the lecture notes stubs can be simple for straightforward cases), deferring the full realistic simulation until later stages. This satisfies the urgent, hard constraint while containing the cost concern rather than ignoring it.

Answer

Top-down, accepting the extra stub-writing cost as a controlled trade-off (using simple stubs initially) because constraint (i) — an early compliance demo of the core H1→H3 flow — is the hard requirement top-down satisfies fastest, while Big Bang and Sandwich each violate at least one constraint outright.

Last-minute revision — Integration Testing

Integration testing, one line

Combine unit-tested modules and test the interfaces between them — not their internal logic.

Big Bang

Integrate every module at once, test once. Only good for small systems; fault localisation is tough.

Top-Down

Test from the top module downward; use stubs for the not-yet-built lower modules. Finds design flaws early, low-level logic tested last.

Bottom-Up

Test from the lowest modules upward; use drivers for the not-yet-built higher (calling) modules. Low-level logic solid early, data flow/interfaces tested late.

Sandwich

Top-down from the top layer, bottom-up from the bottom layer, Big Bang at the middle target layer. High cost; great for large, multi-team systems.

Stub vs. Driver

Stub = dummy for a module that is called (fakes below). Driver = dummy for a module that calls (fakes above).

Entry criteria checklist

Test plan signed off · test cases prepared · test data created · unit testing complete · critical/high defects closed · environment ready.

Exit criteria checklist

All test cases executed · no open critical/P1/P2 defects · test report prepared.

White box or black box?

Both — depends on the modules being integrated (internal-knowledge-needed seams are white box; behaviour-only seams are black box).

Integration vs. System testing

Integration = a few modules' seams. System = the entire assembled product, end to end.

8-step kickoff (compressed)

Understand architecture → modules → what each does → data transfer → entry/exit points → segregate → test conditions → test cases.
