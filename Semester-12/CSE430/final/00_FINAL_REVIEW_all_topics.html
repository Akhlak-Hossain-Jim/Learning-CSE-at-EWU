Topic 01 · Lecture 14

Testing Fundamentals

The seven principles everything else in the course quietly assumes.

Every principle in this lecture is really answering one question: what can testing actually promise you, and what can't it? Testing can show you defects exist; it can never prove they don't. You can't test every input, so you prioritize by risk instead of trying to test everything. Fixing something found in requirements costs roughly 1×; the same defect found after release costs roughly 100× — so testing earlier isn't a nicety, it's a cost decision. Defects cluster (Pareto-style: a small share of modules produces most of the bugs), so history should steer where you look next. A test suite that never changes eventually stops finding anything new — the pesticide paradox — because each fixed test is only re-confirming the one thing it already knows to check, while the software keeps growing new, uncovered surface underneath it. How much testing is "enough" depends on context — a pacemaker and a shopping cart don't get the same rigor. And zero bugs found is not the same claim as "this system does what users need" — that's verification (built it right) versus validation (built the right thing), and confusing them is the absence-of-errors fallacy.

Watch out — the concept you didn't know

Pesticide paradox, rebuilt from zero: imagine a fixed set of test cases as a fixed pesticide sprayed on a field. The first time you spray, it kills the pests it's designed for. Spray the exact same pesticide every season and the surviving pests are, definitionally, the ones that pesticide never affected — nothing new dies. A test suite works the same way: each test was built to catch one specific defect (usually one that was already found and fixed). Run it once and it tells you something real. Run the identical suite for the 50th time against code that has since changed and it can only ever tell you "the thing I check is still fixed" — it says nothing about the new branches, new features, or new edge cases added since. The fix isn't to test more of the same; it's to periodically revise and add new test cases so the suite keeps pace with what the software has become.

Static vs dynamicStatic = examine artifacts (code, docs) without running them — early, cheap, catches things like unreachable code or spec ambiguity. Dynamic = actually execute the software — needed to see runtime behaviour, but later and costlier per defect found.
Test oraclesThe rulebook that decides pass/fail: (1) specification-based — check against a written spec; (2) derived/heuristic — check against expectation without a formal spec; (3) consistency/differential — compare against a previous version or a different implementation; (4) no-oracle — you can observe behaviour but there's no ground truth to check against (hardest to automate).
Test levelsUnit → Integration → System → Acceptance, mapped onto the SDLC: each level has a different scope, a different "who does it," and catches a different class of defect (unit = logic bugs inside one module; integration = interface/hand-off bugs between modules; system = end-to-end behaviour of the whole product; acceptance = does it satisfy the user/business need).
Quick self-test 1 · recall

A team runs its full regression suite for the 40th consecutive release and gets zero failures. Which principle explains why that result alone shouldn't make anyone feel fully confident, and why?

Show answer

Pesticide paradox. A suite unchanged for 40 releases is only proving that the specific things it was built to catch are still fixed — it has no power to say anything about code, features, or edge cases added since it was last updated. Zero failures on an old suite is not the same claim as "this release has no new defects."

Quick self-test 2 · apply

A payment-processing module and a "share to social media" button both need testing. Should they get the same amount of testing rigor? Which principle justifies your answer?

Show answer

No — testing is context-dependent. Rigor should track risk and consequence of failure, not be applied uniformly. A payment module failing has direct financial/legal consequences and warrants far more exhaustive testing than a low-risk social-share button, where a bug is an inconvenience, not a liability.

Topic 02

Cause-Effect Graphing

Turning a requirement's logic into a graph, then a decision table, then test cases.

Cause-effect graphing takes the boolean logic hiding inside a plain-English requirement ("if A or B, but not both, and C, then do X") and makes it explicit and testable. You identify the causes (input conditions) and effects (output conditions) in the requirement, wire them together with five notations — Identity (cause flows straight through), OR, NOT, AND, and Exclusive (a constraint between causes, not an effect — it says two causes can never both be true at once) — add any constraints, then mechanically convert the finished graph into a decision table where every column is one legal combination of causes, and each column becomes one test case.

The lecture's worked example — Print Message
\( E_1=(C_1\oplus C_2)\wedge C_3 \)    \( E_2=\lnot(C_1\vee C_2) \)    \( E_3=\lnot C_3 \)

With \(C_1\) and \(C_2\) marked mutually exclusive, that graph legally produces 6 test cases, not the 8 you'd get from three free boolean inputs — the exclusive constraint rules out the two columns where \(C_1=C_2=1\).

Watch out

Two different cause-combinations can produce the same effect value and still need two separate test cases — a decision table row is per legal combination of causes, not per distinct outcome. Don't collapse rows just because their effect columns look identical.

Quick self-test 1 · recall

What's the difference between the AND notation and the Exclusive constraint — aren't they both "these things can't both happen"?

Show answer

No. AND is a graph node that produces an effect: it fires (effect = 1) only when all its input causes are 1. Exclusive is a constraint drawn between causes themselves, not feeding into any effect node — it simply forbids two specific causes from both being 1 at the same time, which prunes rows out of the decision table before you even get to the effects.

Quick self-test 2 · apply

Given \(E = C_1 \wedge \lnot C_2\), how many test cases does the decision table need, assuming no constraints between \(C_1\) and \(C_2\)?

Show answer

4 — one per combination of two independent binary causes (\(2^2\)): \((C_1{=}1,C_2{=}0)\to E{=}1\); \((1,1)\to 0\); \((0,0)\to 0\); \((0,1)\to 0\). No constraint means no rows get pruned.

Topic 03 · Lecture 15

White-Box Testing

Coverage is about how much of the code your tests actually exercised — not whether the code is correct.

White-box testing uses knowledge of the code's internal structure to design tests, in contrast to black-box testing which only uses the spec/interface. The core tool is the Control Flow Graph (CFG): nodes are blocks of sequential statements, edges are the possible jumps between them, and every decision (if/while) becomes a node with two outgoing branches. From a CFG you can measure three nested strengths of coverage — statement, then branch, then path — each strictly stronger than the last, meaning 100% on a weaker one never guarantees any particular result on a stronger one.

The three coverage formulas
\[ \text{Statement} = \frac{\text{executed statements}}{\text{total executable statements}} \times 100\% \qquad \text{Branch} = \frac{\text{executed branch outcomes}}{\text{total branch outcomes}} \times 100\% \] \[ \text{Path} = \frac{\text{executed feasible paths}}{\text{total feasible paths}} \times 100\% \, ; \quad \text{upper bound } 2^n \text{ for } n \text{ independent decisions} \]
calculatePayable CFG9 nodes, 3 decision nodes, 6 branch outcomes — the running example used for every worked coverage calculation in the full guide.
Feasible vs infeasible pathFeasible = some valid input can actually drive execution down it. Infeasible = the path exists structurally in the graph, but no input can ever satisfy both of two decisions along it (they contradict each other on the same variable).
Dead vs unreachable codeUnreachable = control flow can never arrive there at all. Dead = control flow does arrive, the code runs, but it has no effect on any output (e.g. an assignment whose result is never used).
Watch out

"White-box is more thorough, so it's better than black-box" is not a defensible exam answer — the lecture frames them as complementary, testing different things (internal logic vs external behaviour), not as a hierarchy. Also: high coverage is evidence you exercised the code, never proof the code is correct — a statement can execute and still compute the wrong answer.

Quick self-test 1 · apply

A function has 3 independent decision points and no loops. One test set achieves 100% branch coverage using only 2 test cases. Does that also guarantee 100% path coverage?

Show answer

No. Branch coverage only requires each individual branch outcome (each True/False) to fire at least once somewhere across the test set — it says nothing about every combination of branches being exercised together. Path coverage needs up to \(2^3=8\) distinct combinations; 2 test cases can satisfy branch coverage while covering only 2 of those 8 paths.

Quick self-test 2 · recall

A line of code sits inside an `if (x > 10 && x < 5)` block. Is this dead code or unreachable code?

Show answer

Unreachable — no value of \(x\) can be simultaneously greater than 10 and less than 5, so control flow can never enter that block at all. (Dead code would be a line control flow does reach, that runs, but achieves nothing.)

Topic 04

Integration Testing

Individually-correct modules can still fail together — this level tests the seams.

Integration testing starts once modules pass unit testing on their own, and specifically targets the interfaces between them — data hand-off, call sequencing, shared state — not each module's internal logic again. Big Bang wires everything together at once and tests it as a whole (simple, but a failure could be anywhere, so it only really suits small systems). Incremental integration builds up gradually: Top-Down starts at the top module and works downward, using stubs (dummies standing in for not-yet-integrated lower modules) — this surfaces design/interface flaws early but leaves low-level logic untested until late. Bottom-Up starts at the lowest modules and works upward, using drivers (dummies standing in for not-yet-integrated higher, calling modules) — the mirror image trade-off: low-level logic is solid early, but real data flow between high-level modules isn't proven until late. Sandwich (hybrid) runs top-down and bottom-up simultaneously toward a middle target layer, at higher cost, and is the natural choice for large, multi-team systems where neither pure strategy's blind spot is acceptable.

Watch out

Don't memorise "stub → top-down, driver → bottom-up" as an arbitrary pairing — derive it instead: top-down testing is missing the lower modules it hasn't built yet, so it needs something to stand in for what's below (a stub); bottom-up is missing the higher modules that would normally call it, so it needs something to stand in for what's above (a driver).

Entry criteriaTest plan approved, test cases/data ready, unit testing complete, critical defects closed, environment ready.
Exit criteriaAll test cases executed, no open critical/P1/P2 defects, test report produced.
White box or black box?Both — depends on the seam: internal-knowledge-needed interfaces are tested white-box, pure behaviour-only interfaces are tested black-box.
Integration vs systemIntegration = a few modules' interfaces. System = the entire assembled product end-to-end.
Quick self-test 1 · apply

Two individually unit-tested modules pass their own tests perfectly, but when combined, one sends a date as "DD-MM-YYYY" and the other expects "MM-DD-YYYY". What level of testing was supposed to catch this, and why didn't unit testing catch it?

Show answer

Integration testing. Unit testing only verifies each module's internal logic in isolation against its own expectations; it has no visibility into another module's assumptions about data format. This is exactly the class of defect — an interface/data hand-off mismatch between two individually-correct modules — that integration testing exists to catch.

Quick self-test 2 · recall

Why would a large, multi-team project choose Sandwich integration over pure Top-Down or pure Bottom-Up?

Show answer

Because each pure strategy leaves a different blind spot late in the process (Top-Down: low-level logic; Bottom-Up: high-level data flow/interfaces), and a large system can't afford to discover either class of defect near the end. Sandwich attacks from both ends toward the middle simultaneously, at the cost of needing more stubs, drivers, and coordination across teams.

Topic 05

Acceptance Testing

The last gate before release — and the one testing level defined by who is checking, not just what.

Acceptance testing asks a different question than every level before it: not "does this work correctly" but "does this satisfy what was actually agreed or needed." UAT (User Acceptance Testing) has real end users verify the software meets their needs in realistic scenarios; OAT (Operational Acceptance Testing) has ops/IT staff verify the system is production-ready — backups, disaster recovery, maintainability. The other four types each add a different lens: Contract Acceptance checks against a signed contract's exact specs; Regulation Acceptance checks against external laws/standards (healthcare, finance, aviation); Alpha Testing is internal staff testing at the developer's site before outsiders see it; Beta Testing hands the software to external volunteer users in the real world to surface what internal testing missed.

5-step processPlanning → Testing → Recording → Comparing → Result Evaluation. Recording is neutral documentation; Comparing is the judgment step against acceptance criteria — don't merge these two.
The two stats88% of professionals call UAT critical for quality; yet 29% say poor-quality software still reaches UAT anyway — the lecture's own illustration of why UAT is necessary but not sufficient on its own.
Writing an acceptance testNeeds an ID, Title, Procedure (steps), and Expected Result — flowing from Requirement Analysis → Test Plan → Design → Execute → Confirm Results.
Watch out

Alpha, Beta, and UAT are the trio students mix up because all three "involve users." The distinguishing question is who and where: Alpha = internal staff, developer's site, early. Beta = external volunteers, real environment, later. UAT = the actual client/end-users, checking against their own real requirements, right before sign-off.

Quick self-test 1 · recall

A hospital's new patient-records system must be checked against HIPAA-equivalent data-privacy law before go-live. Which type of acceptance testing is this?

Show answer

Regulation Acceptance Testing — verification against external laws/standards, distinct from checking it against a contract (Contract Acceptance) or against end-user needs (UAT).

Quick self-test 2 · apply

All planned acceptance test cases pass with zero open defects. Is the exit criteria automatically satisfied?

Show answer

Not quite — exit criteria also require stakeholders to explicitly confirm the system is deployment-ready. "All tests passed" is necessary but the sign-off/confirmation step is a separate, required condition, echoing the absence-of-errors fallacy from Testing Fundamentals: passing tests isn't automatically the same as "ready and accepted."

Topic 06 · Lecture 16

Specification-Based Testing

State Transition Testing and Use-Case-Based Testing — picking the technique that matches the kind of logic you're facing.

Watch out — the concept you were unsure of

What a state-transition test case actually verifies, built from zero: picture a login form that locks after 3 failed attempts — the system's behaviour depends not just on what you type, but on what already happened before. That "behaviour depends on history" is exactly what a finite state machine models: the system is always in exactly one state (e.g. "0 failures", "locked"), and a specific event (e.g. "wrong password entered") moves it to a specific next state. A state-transition test case checks one such move directly: put the system in state \(X\), fire event \(E\), and confirm it lands in the correct state \(Y\) — and, just as importantly, confirm that events which should be rejected in state \(X\) really are rejected (e.g. no "admin reset" event available to a regular locked-out user).

Login-Security example: S0 (Logged Out) → one failure → S1 → another failure → S2 → another → S3 (Locked). A valid password from S0, S1, or S2 jumps straight to S4 (Logged In); S4 + Logout returns to S0; S3 needs an Admin Reset to return to S0. Coverage targets escalate in strength: state coverage (visit every state at least once) → transition coverage (fire every valid transition at least once) → transition-pair coverage (consecutive pairs) → invalid-transition coverage (sample some of the disallowed moves too, since a robust system must reject them correctly).

Use-case-based testing works from a different structure entirely: a use case's Actor, Goal, Preconditions, Trigger, Main Flow, Alternate Flow(s), Exception Flow(s), and Postconditions. Each flow becomes its own test scenario — one use case reliably produces multiple test cases, one per meaningful path through it, as shown in the "Purchase a Product" example (main flow = successful purchase; alternates = e.g. applying a discount code; exceptions = e.g. payment declined).

Choosing the techniqueInput validation → Equivalence Partitioning/Boundary Value Analysis. Multiple conditions → Decision Table. Logical dependency between conditions → Cause-Effect Graph. State-dependent behaviour → State Transition. User interaction workflows → Use-Case-Based. Unexpected/unscripted situations → Error Guessing.
Golden ruleExpected results always come from the written specification — never from the tester's own assumption of what "should" happen.
Quick self-test 1 · recall

A requirement says "the shopping cart behaves differently depending on whether the user is a guest or a logged-in member." Which specification-based technique is the natural first choice, and why?

Show answer

State Transition Testing — "behaves differently depending on a prior condition/history" is exactly the state-dependent-behaviour signal the choosing table flags for this technique, since "guest" and "logged-in member" function as two distinct states the system moves between.

Quick self-test 2 · apply

From a single use case "Withdraw Cash from ATM," would you expect exactly one test case, or several? Why?

Show answer

Several. The main flow (successful withdrawal) is one test case, but each alternate flow (e.g. "cancel transaction mid-way") and each exception flow (e.g. "insufficient funds," "card retained after wrong PIN") becomes its own separate test case — one use case reliably expands into multiple test scenarios, one per meaningful flow.

Topic 07 · Lecture 21

Regression Testing

Two jobs after a change, not one repeated: prove the fix works, and prove nothing else broke.

Watch out — correcting the exact mix-up you made

You described it as: "retesting means testing again, regression testing might mean testing again and again till the issue is properly fixed." Neither half of that is the actual distinction. Here it is precisely: Retesting (confirmation testing) re-runs the one specific test case that previously failed, to confirm that the fix actually resolved it — one test, run again, after a fix. Regression testing re-runs other, previously-passing tests unrelated to the fix, to confirm the change didn't break something else — different tests, checking for new damage, not confirming the original fix at all. They answer two completely different questions and you typically do both after any change, not one repeated in a loop.

The SeatReleaseService example frames how far a change's effects can ripple: direct impact is the changed code itself plus the test that originally failed; dependency impact is every caller, callee, or shared API/database the change touches; business impact is whether any critical user journey or high-value transaction runs through the changed area. Smoke testing and sanity testing are both quick sanity-checks but at different moments and different widths: smoke is wide-but-shallow, run right after a new build/deployment, asking "is this build even stable enough to test further?"; sanity is narrow-but-focused, run after a small patch to an already-stable build, asking "does this specific change work?" Neither replaces a full regression pass.

Prioritizing what enters the regression suite
\[ \text{Risk score} = \text{Impact} \times \text{Likelihood}, \quad \text{each scored } 1\text{–}3 \]

Selection itself follows a simple rule: the originally-changed code/test is always included; dependent interfaces are usually included; critical business journeys are included on a risk basis. This is backed by a 7-step change impact analysis process that walks from understanding the change through to finalizing the retest scope.

Quick self-test 1 · recall — targets the misconception

A developer fixes bug #482, re-runs test case TC-482 (the one that originally caught it) three times until it passes cleanly. Is this regression testing?

Show answer

No — this is retesting (confirmation testing), however many times it's repeated. Running the same originally-failed test case again and again is still just confirming the fix, not checking for new damage elsewhere. Regression testing would mean running other tests, on parts of the system TC-482 doesn't touch, to make sure fixing #482 didn't break something unrelated.

Quick self-test 2 · apply

A one-line config change has a small blast radius (Impact = 1) but touches the checkout payment path used by nearly every transaction (Likelihood of being exercised = 3). What's the risk score, and should it be in the regression suite?

Show answer

Risk score \( = 1 \times 3 = 3 \). Even with low technical impact, the high likelihood of that path being exercised by real users pulls the score up — and because it's a critical business journey (checkout), the business-impact lens on its own would argue for inclusion regardless of the numeric score. Include it.

Topic 08

Syntax Testing

Testing whether input matches the required format — nothing more, nothing less.

Syntax testing checks input against a formally-defined grammar, written in BNF (Backus-Naur Form): ::= means "is defined as," | means "or" between alternatives, and anything in <angle brackets> is a non-terminal still waiting to be substituted, while bare literal characters are terminals that end up in the final string. The methodology is three steps: identify the language/format the input must obey, define it formally in BNF, then test both the normal condition (a set of valid strings covering the grammar's different paths) and the garbage condition (invalid strings, each deliberately violating exactly one rule, to check the system correctly rejects it).

The framing to hold onto: the software under test is a recognizer — it accepts or rejects strings — and the tester acts as a generator, producing both valid and invalid strings to throw at it. There are exactly two ways a recognizer can fail: it wrongly rejects a string that was actually valid, or it wrongly accepts a string that was actually invalid — neither is automatically the "worse" bug.

The lecture's grammar
<command> ::= <command type> <file name> to <file name>
<command type> ::= copy | rename
<file name> ::= <letter> | <letter><letter>
<letter> ::= a | b

Four test commands — copy a to b, copy aa to bb, rename b to a, copy bb to aa — together cover every one of the 23 numbered nodes in the grammar's derivation tree; the first two alone don't touch the rename branch or every letter/length combination, which is exactly why the extra two exist.

Watch out

Syntax testing only ever checks format. A string like copy a to a is perfectly valid syntax (a legal file name, "to" another legal file name) even though copying a file onto itself is nonsensical — that's a semantic/logic bug, and syntax testing structurally cannot catch it. Don't credit syntax testing with catching bugs outside its own job description.

Quick self-test 1 · apply

Is copy ab to c a valid string under the lecture's grammar? Justify from the rules directly.

Show answer

Yes. "copy" satisfies <command type>; "ab" satisfies <file name> as <letter><letter> with both letters valid (a, b); "c" fails — <letter> only allows a or b, so "c" is not a valid <file name>. Correction: this string is actually invalid — "c" violates the <letter> rule. (If you answered "valid," re-check every terminal against its rule individually — this is the exact trap the grammar is built to test.)

Quick self-test 2 · recall

What's the difference between the "generator" and the "recognizer" in syntax testing?

Show answer

The generator is the tester (or a tool acting on the tester's behalf) — it produces candidate strings, both valid and deliberately invalid. The recognizer is the software under test — it's the thing that has to correctly accept the valid ones and reject the invalid ones.

Final check

Mixed final drill

Eight questions, one per topic, in random order — because the exam won't tell you which lecture a question is testing.

Drill Q1 · Regression Testing

Your team fixes a bug in the shipping-cost calculator. Name one test you'd run as retesting, and one you'd run as regression testing.

Show answer

Retesting: re-run the original test case that caught the shipping-cost bug, to confirm it's now fixed. Regression: re-run unrelated tests — e.g. checkout total calculation, tax calculation, order confirmation email — that don't touch the bug directly but share code paths or data with the shipping module, to confirm the fix didn't break them.

Drill Q2 · White-Box Testing

A function has one decision point. One test case exercises the True branch only. What's the branch coverage, and what's missing?

Show answer

50% branch coverage (1 of 2 branch outcomes exercised). Missing: a test case that drives the decision's False outcome.

Drill Q3 · Acceptance Testing

External volunteer users trial a nearly-finished mobile app in their own homes before public launch. What type of testing is this?

Show answer

Beta Testing — external users, real-world environment, feedback used to catch what internal testing missed.

Drill Q4 · Cause-Effect Graphing

You draw a constraint saying causes \(C_1\) and \(C_2\) can never both be 0 at once. What is this notation called?

Show answer

An Inclusive-style constraint (at least one must be true) — distinct from the Exclusive constraint used in the Print Message example, which forbids both being 1 at once. (If your lecture only formally named "Exclusive," describe this one in plain language and note the parallel — the mechanism, forbidding one specific joint combination, is what matters.)

Drill Q5 · Testing Fundamentals

A test suite passes 100% for a year straight. A senior engineer says "great, we can stop writing new tests." What principle is being violated, and how would you push back?

Show answer

The pesticide paradox. Push back: a static suite passing consistently only proves the specific defects it targets are still fixed — it says nothing about new code paths added over that year. The suite needs to be actively refreshed with new test cases, not treated as "done" because its pass rate looks good.

Drill Q6 · Integration Testing

You're integrating from the bottom of the module tree upward. The higher-level module that will eventually call your lowest-level module hasn't been built yet. What do you use to keep testing, and what's it called?

Show answer

A driver — a dummy that stands in for the not-yet-built calling (higher) module, feeding inputs to the module under test.

Drill Q7 · Specification-Based Testing

A requirement reads: "A user can cancel their subscription either immediately or at the end of the billing cycle, and may optionally leave feedback." How many test cases would you expect from this as a use case, at minimum, and why?

Show answer

At least 2–3: one for the main flow (cancel immediately), one for the alternate flow (cancel at end of cycle), and optionally one more for the "with feedback" variant if it's treated as its own flow — each distinct flow through a use case becomes its own test case.

Drill Q8 · Syntax Testing

A grammar defines \(\langle digit\rangle ::= 0\,|\,1\,|\,2\). What's the fastest way to construct a garbage-condition test string for it?

Show answer

Pick any value the rule doesn't list — e.g. "3" or "a" — as the <digit>, deliberately violating that one rule while leaving everything else in the surrounding grammar valid, so the failure (if any) is isolated to exactly that rule.
