Cause-Effect Graphing

Course: CSE430 — Software Testing and Quality Assurance (East West University) Based on: Cause-Effect Graphing (Dr. Shamim Hasnat Ripon) Exam: ~25 Aug 2026 (mixed format)
Topic 01

What Cause-Effect Graphing Is, and Why It Exists

A black-box technique for turning a paragraph of requirements into the smallest set of test cases that still covers every combination that matters.

Picture a wall of light switches wired to a few light bulbs. Some bulbs are wired to just one switch. Some only turn on when any of several switches is flipped. Some only turn on when every one of several switches is flipped. Some turn on precisely when a switch is off. And sometimes two switches are wired so that flipping one physically locks out the other — they can never both be on at once. If someone handed you the wiring diagram, you could read off, for every bulb, exactly which switch-patterns light it — and you'd know exactly which patterns to try to prove the wiring is correct.

Cause-effect graphing is that wiring diagram, drawn from plain English requirements instead of from actual wires. A cause is a distinct input condition the requirement talks about — something that is simply true or false (1 or 0) for a given test, like "the first character is A." An effect is a distinct output or result the requirement describes, like "the file is updated." The technique reads the requirement text, pulls out every cause and every effect, draws the boolean logic connecting them as a graph, mechanically turns that graph into a table of legal input combinations (a decision table), and then reads one test case straight off each column of that table.

Key idea

Cause-effect graphing is a black-box technique — it never looks at code, only at requirements text — that models how multiple input conditions combine to produce each output, so you can derive the minimum number of test cases that still gives maximum coverage of those combinations.

This matters because most of the techniques you meet earlier in the course (equivalence partitioning, boundary value analysis) look at one input at a time. They tell you which values of a single variable are worth testing, but they have no systematic way of deciding which combinations of several variables you actually need to try. Real requirements are full of exactly this kind of combinational logic — "do X only if A and B", "do Y unless C" — and if you only vary one input at a time you can walk right past the specific combination that breaks the system, or waste effort testing combinations that can never legitimately occur.

The lecture also emphasises a second, less obvious benefit: cause-effect graphing doubles as a requirements-quality check. Because the technique forces you to state, precisely, which causes drive which effects, trying to build the graph exposes gaps, ambiguities and inconsistencies in the requirement itself — if a clean graph won't come together, that's the graph telling you the requirement is incomplete, not that you're doing it wrong.

Watch out

Stay black-box. A cause is an input condition stated in the requirement, something a tester can set up before running a test — never a variable you noticed by reading the implementation. If it isn't in the spec, it isn't a cause.

Topic 02

The Five Notations

Four of these compute a value; the fifth restricts which cause-values are even allowed to occur together.

In every diagram below, c (or c1, c2, c3…) stands for a cause and e stands for an effect — the letters the lecture itself uses. The first four notations sit between causes and an effect and compute the effect's value from the cause values. The fifth, Exclusive, is different in kind: it is a constraint drawn between causes, and it never feeds an effect directly.

1 · Identity

The simplest possible wiring: one cause drives one effect with no transformation at all.

Rule (lecturer's wording): if c is 1, then e is 1. Else e is 0.

Micro-example: a "subscribe" checkbox (cause) directly triggers "send confirmation email" (effect) — checked ⇒ email sent, unchecked ⇒ no email.

2 · OR

Rule: if c1 or c2 or c3 is 1, then e is 1. Else e is 0.

Micro-example: "the submit button is enabled if the username is filled in OR guest checkout is selected."

3 · NOT

Rule: if c is 1, then e is 0. Else e is 1.

Micro-example: "an error banner shows if the uploaded file is NOT a supported format."

4 · AND

Rule: if both c1 and c2 and c3 is 1, then e is 1. Else e is 0.

Micro-example: "the account is created if the email is valid AND the terms are accepted AND the user is 18+."

5 · Exclusive (a constraint, not a gate)

Rule: exists between causes. States that either c1 or c2 can be 1 — i.e. c1 and c2 cannot be 1 simultaneously.

Micro-example: a form field holds either a "PERCENT" code or a "FLAT" code — never both, because it's one text box.

Watch out — the "E" trap

The lecture labels the Exclusive symbol itself E in the diagram, and it also labels effects E1, E2, E3…. They are unrelated: the Exclusive E is a dashed constraint node between two causes and never feeds a numbered effect. Don't let the shared letter make you think an Exclusive constraint is "an effect" — it restricts which raw (c1, c2) rows are legal to test in the first place; it does not compute anything.

Topic 03

The Technique: From Requirement to Test Cases

The lecture's own pipeline, in the exact order it names the stages.

  1. Identify Causes & Effects. Read the requirement and pin down every distinct input condition (cause) and every distinct output/result (effect) it mentions.
  2. Build the Graph. Wire each effect to the causes that determine it, using Identity, OR, NOT, and AND as needed.
  3. Add Constraints. Layer in any real-world restrictions between causes — most commonly Exclusive — that some combinations of cause values can never physically occur.
  4. Convert to Decision Table, then Derive Test Cases. Enumerate every combination of cause values that the constraints allow, compute what each effect does for that combination (this is the decision table), and write one test case per column.
Key idea

The lecture's own diagram actually draws this as five connected stages (Identify → Build the Graph → Add Constraints → Convert to Decision Table → Derive Test Cases) with an arrow running straight through all of them. Some textbooks fold the last two into one step ("build the decision table and read off the tests") — which is why you may also see this called a "4-step" technique. Either way it's the same pipeline; know it by its stages, not by a magic number.

Watch out

Constraints (step 3) come after the graph is built, not before. You draw the OR/AND/NOT logic first, based purely on what the requirement says an effect depends on — then you separately note which combinations of causes are physically impossible and cross those columns out of the decision table in step 4.

Topic 04

Worked Example: "Print Message"

The lecture's fully worked example — reconstructed step by step exactly as taught.

The requirement, as given

"Print message" is software that reads two characters and, depending on their values, prints a message.

  • The first character must be an "A" or a "B".
  • The second character must be a digit.
  • If the first character is an "A" or "B" and the second character is a digit, then the file must be updated.
  • If the first character is incorrect (not an "A" or "B"), the message X must be printed.
  • If the second character is incorrect (not a digit), the message Y must be printed.

Step 1 — Identify causes and effects

Three distinct input conditions are mentioned, so there are three causes; three distinct outcomes are mentioned, so there are three effects:

Causes
C1 — first character is "A"  ·  C2 — first character is "B"  ·  C3 — second character is a digit
Effects
E1 — update the file  ·  E2 — print message "X"  ·  E3 — print message "Y"

Step 2 & 3 — Build the graph and add the constraint

Work out each effect in plain language first, exactly as the lecture phrases it, then translate to notation:

  • E1 fires when: the first character is "A" and the second is a digit, or the first character is "B" and the second is a digit — and the first character can be "A" or "B" but never both. That "either, not both" is an Exclusive constraint between C1 and C2, so the OR of C1 and C2 behaves like an exclusive-or here — the lecture writes this combined value as C1 ⊕ C2. E1 is that value AND-ed with C3.
  • E2 (print X) fires when the first character is neither "A" nor "B" — i.e. NOT(C1 OR C2).
  • E3 (print Y) fires when the second character is not a digit — i.e. NOT C3.
Boolean expressions (lecturer's notation)
\[ E_1 = (C_1 \oplus C_2) \wedge C_3 \qquad E_2 = \lnot(C_1 \vee C_2) \qquad E_3 = \lnot C_3 \]

Drawing it: C1 and C2 feed an OR node (their combined value is labelled C1⊕C2 because the Exclusive constraint between them means "at least one" and "exactly one" coincide). A dashed Exclusive link joins C1 and C2 directly, marking that (C1=1, C2=1) can never be a real input. That same OR node's output branches two ways: through an AND with C3 to reach E1, and through a NOT to reach E2. Separately, C3 connects through its own NOT straight to E3.

Watch out

(C1=1, C2=1) — first character is somehow both "A" and "B" — is forbidden by the Exclusive constraint. It never appears as a decision table column and must never become a test case.

Step 4 — Decision table and test cases

List every combination of (C1, C2, C3), drop the two that the Exclusive constraint forbids, and compute E1, E2, E3 for each of the six that remain. This is a mechanical evaluation of the three boxed expressions above — walk it line by line for the first row, and the rest follow the same pattern:

  1. Row: C1=1, C2=0, C3=1

    First combination to check: first char is "A", second is a digit.

  2. \( C_1 \oplus C_2 = 1 \oplus 0 = 1 \)

    Exactly one of C1, C2 is 1, so the OR/exclusive-or node outputs 1.

  3. \( E_1 = 1 \wedge C_3 = 1 \wedge 1 = 1 \)

    Apply E1's formula: AND the node's value with C3.

  4. \( E_2 = \lnot(C_1 \vee C_2) = \lnot(1) = 0,\qquad E_3 = \lnot C_3 = \lnot 1 = 0 \)

    Apply E2 and E3's formulas directly to the same row.

Topic 05

Practice Questions

Warm-ups first, then full graph-to-test-case derivations, then two stretch/theory questions.

Question 1 · easy

"Whenever the user ticks the 'remember me' box, a long-lived cookie is set." Which of the five notations connects cause to effect here?

Show answer

Identity — one cause maps straight through to one effect with no combination or negation involved: box ticked ⇒ cookie set, box unticked ⇒ no cookie.

Question 2 · easy

"The submit button is enabled if the username is filled in OR the guest-checkout box is ticked." Which notation connects the two causes to the effect?

Show answer

OR — either single condition is enough on its own to enable the button, the defining signature of an OR gate (any one input being 1 is enough).

Question 3 · easy

"An error banner appears if the uploaded file is NOT a supported format." Which notation connects cause to effect?

Show answer

NOT — the effect fires exactly when the cause is false, the defining signature of a NOT gate.

Question 4 · easy

"A late-fee is charged if the return date is after the due date AND no extension was granted." Which notation connects the two causes to the effect?

Show answer

AND — the fee needs both conditions true together, the defining signature of an AND gate (all inputs must be 1).

Question 5 · easy/medium

"A shipping method can be typed as 'standard' or 'express' — never both, since it's one dropdown." Which of the five notations describes the relationship between the two causes here, and why is it not one of the other four?

Show answer

Exclusive. It's not Identity/OR/NOT/AND because those four all compute an effect's value from cause values; this sentence isn't describing an effect at all — it's declaring that two cause values ("standard" selected, "express" selected) can never both be 1 at the same time. That's a restriction on causes, which is exactly what the Exclusive constraint notation is for.

Question 6 · medium (twist on the lecture example)

The Print Message requirement is revised: the software now also accepts a third valid first character, "C", which updates the file under the same rule as "A" and "B" (i.e. the file updates when the first character is "A", "B", or "C" and the second character is a digit). Message X should now print only when the first character is none of "A", "B", "C".

Introduce a new cause C4 = "first character is C" (keep C1, C2, C3 as before). (a) How many Exclusive constraints are now needed, and between which causes? (b) Rewrite E1 and E2. (c) How many valid rows does the decision table now have, compared to the original 6?

Show worked solution

  1. Causes now: C1 = first is "A", C2 = first is "B", C4 = first is "C", C3 = second is a digit.

    Same method as step 1 of the original example: one new stated input condition ("C" is now valid) becomes one new cause.

  2. Exclusive constraints needed: (C1,C2), (C1,C4), (C2,C4) — three pairwise links.

    Exclusive is pairwise: the lecture's notation only draws a constraint between two causes at a time, so "at most one of three can be true" needs one dashed link for every pair.

  3. \( E_1 = (C_1 \vee C_2 \vee C_4) \wedge C_3 \qquad E_2 = \lnot(C_1 \vee C_2 \vee C_4) \)

    Extend the OR node to three inputs. With all three pairwise-exclusive, at most one of C1, C2, C4 is ever 1, so the plain OR is enough — there's no need to write an explicit three-way XOR-style symbol.

  4. Valid (C1, C2, C4) states: exactly one of the three is 1 (3 ways), or all three are 0 (1 way) = 4 valid states.

    Count legal combinations: the three pairwise-exclusive constraints together forbid any state with two or more of C1, C2, C4 equal to 1.

  5. Total valid decision-table rows \(= 4 \times 2 = 8\) (four first-character states × two states of C3), versus 6 originally.

    Multiply by C3: C3 is independent of the first-character causes, exactly as in the original example, so it simply doubles whatever count the first-character causes produce.

Answer

Three pairwise Exclusive constraints; \(E_1=(C_1\vee C_2\vee C_4)\wedge C_3\), \(E_2=\lnot(C_1\vee C_2\vee C_4)\); 8 valid test cases instead of 6.

If the username field is empty, the system shows "Username is required", regardless of the password. If the password is shorter than 8 characters, the system shows "Password too short", regardless of the username. (Both messages can appear together.)

  3. \( E_2 = \lnot C_1 \qquad E_3 = \lnot C_2 \)

  4. No Exclusive constraint needed.

    Step 3: nothing in the requirement says C1 and C2 can't both be true or both be false — they're independent fields, so all 4 raw combinations are physically possible.

Question 8 · medium/core (new scenario)
New requirement — coupon code field

A cart's coupon field holds exactly one code, "PERCENT" or "FLAT" — never both, since it's a single text box. If a "PERCENT" code is entered and the subtotal is over $50, a percentage discount is applied. If a "FLAT" code is entered and the subtotal is over $50, a flat-rate discount is applied. If a valid code is entered but the subtotal is $50 or under, the system shows "Add more to qualify for a discount." If neither code is entered, the system shows "No valid code applied."

Derive causes, effects, the graph (including any constraint), the decision table, and the test cases.

Show worked solution

  1. Causes: C1 = code is "PERCENT", C2 = code is "FLAT", C3 = subtotal > $50. Effects: E1 = discount applied, E2 = "No valid code applied", E3 = "Add more to qualify."

    Step 1, same method as Print Message — this scenario is deliberately built on the same shape so you can pattern-match the method, not the numbers.

  2. \( E_1 = (C_1 \oplus C_2) \wedge C_3 \qquad E_2 = \lnot(C_1 \vee C_2) \qquad E_3 = (C_1 \vee C_2) \wedge \lnot C_3 \)

    Step 2: E1 and E2 mirror Print Message exactly (OR-node gated by exclusivity, AND'd with C3 / negated). E3 is new: "valid code entered, but subtotal not over $50" is (C1 OR C2) AND NOT C3 — an AND of the same OR-node with a NOT of C3, a combination the lecture didn't show but built from the same four notations.

  3. Exclusive constraint between C1 and C2 (a single text field can't hold both codes).

    Step 3, exactly as in Print Message: forbids the (C1=1, C2=1) rows.

  4. Valid rows: (1,0,1)→(1,0,0); (1,0,0)→(0,0,1); (0,1,1)→(1,0,0); (0,1,0)→(0,0,1); (0,0,1)→(0,1,0); (0,0,0)→(0,1,0)

  5. Notice (0,0,1) and (0,0,0) give the identical effect pattern (0,1,0).

    Redundancy check: when no code is entered, C3 (the subtotal) never gets a chance to matter — E1 and E3 both need a code present. Both rows are still legal decision-table columns, but a tester could reasonably argue one of the two test cases is redundant for coverage purposes.

Question 9 · hard (stretch — combines AND-of-three with a downstream XOR-gated AND)
New requirement — signup with promo pricing

A signup form requires: (1) a valid email format, (2) the Terms & Conditions checkbox ticked, (3) age 18 or over. An account is created only when all three hold. If the Terms checkbox is not ticked, the system shows "You must accept the terms", regardless of the other two fields. Separately, an optional promo field accepts either "STUDENT" or "STAFF" — never both, since it's one field. If the account is created and the user typed one of the two promo codes, a discounted price is shown.

Define all causes and effects, and write the boolean expression for the discounted-price effect. Then — assuming account creation (causes C1, C2, C3 all true) is already covered by other test cases — list the minimal test cases needed just to check the discount effect's behaviour across the valid promo-code states.

  1. Causes: C1 = email valid, C2 = terms accepted, C3 = age ≥ 18, C4 = code is "STUDENT", C5 = code is "STAFF". Effects: E1 = account created, E2 = "must accept terms" shown, E3 = discounted price shown.

    Step 1: five stated input conditions, three stated outcomes.

  2. \( E_1 = C_1 \wedge C_2 \wedge C_3 \qquad E_2 = \lnot C_2 \)

    Step 2, three-input AND: "only when all three hold" — the same three-input AND notation used for OR/AND in Section 2, just with AND instead of OR.

    This is the "combine two ideas" step: E3's graph doesn't wire straight from raw causes — it reuses the already-built E1 node as one input to a further AND, gated by the same OR+Exclusive "exactly one" trick from Print Message applied to C4/C5. Question 10 · short answer

Why do we need cause-effect graphing when we already have equivalence partitioning?

Show model answer
What this tests & where it comes from This tests whether you understand the gap equivalence partitioning leaves open — a technique from elsewhere in this course that classes the values of one variable — versus what this lecture's opening slide claims cause-effect graphing adds: modelling combinations of multiple input conditions, and catching weak requirements as a side effect.

Equivalence partitioning splits the value range of one input variable into classes and picks one representative from each, on the assumption that inputs largely don't interact. But many real requirements — like this lecture's Print Message example — only produce a particular result when several distinct conditions combine in a specific logical way: the file only updates when a character condition AND a digit condition both hold at once. Equivalence partitioning has no systematic method for choosing which combinations of classes across multiple variables to test, so it can silently miss the exact combination that matters, or force a tester to guess. Cause-effect graphing fixes this directly: it extracts the logical relationships between causes and effects from the requirement text, and mechanically produces the decision table that tells you exactly which combinations are worth a test case — giving, as the lecture states, the minimum number of tests for maximum coverage of those combinations. It also does something equivalence partitioning doesn't: if you can't build a clean graph, that failure itself tells you the requirement is ambiguous or incomplete.

Question 11 · short answer

What does it mean, practically, if while doing cause-effect graphing you find you cannot draw a clean graph for a set of requirements?

Show model answer
What this tests & where it comes from This directly tests the lecture's introduction bullet: "Inability to create a clear cause-effect graph indicates weak or incomplete requirements." It's a distinctive, professor-emphasised point, not a generic textbook line — a strong exam short-answer target.

It means the fault is in the requirements document, not in you. If an effect is mentioned but no cause is ever stated that determines it, or two stated rules contradict each other for the same input combination, or some combination of causes is simply never addressed by any rule, then there is no correct graph to draw — the specification itself has a gap, an ambiguity, or an inconsistency. The right response is to flag it back to whoever owns the requirements rather than guessing at intended behaviour. This is precisely why the lecture treats cause-effect graphing as more than a test-design technique: attempting to build the graph is itself a requirements-quality check, independent of whichever test cases eventually come out of it.

Question 12 · short answer

Explain the difference between the Exclusive constraint and the OR notation, using C1 and C2 from the Print Message example, and explain why that example needs both together to correctly compute E1.

Show model answer
What this tests & where it comes from This tests the distinction drawn in Section 2 between the four computing notations (Identity/OR/NOT/AND) and the one restricting notation (Exclusive) — a common point of confusion since both are drawn as lines converging on a node, and both notations in this specific example connect to the very same two causes, C1 and C2.

OR is computational: it takes cause values as input and produces a derived boolean value, 1 if at least one input is 1. Exclusive is not computational at all — it is a restriction declared directly between two causes, stating that a certain combination of their values (both 1 at once) can never legitimately occur as a test input, because it would contradict a real-world fact (a single character can't be both "A" and "B"). In the Print Message example, C1 and C2 feed an OR node used by both E1 and E2 — but without the accompanying Exclusive constraint, a tester deriving the decision table would have no reason to exclude the (C1=1, C2=1) row, and would either waste a test case on an input that can never happen in reality, or misread the OR node's value as a plain OR when the lecture is really relying on it behaving like an exclusive-or (⊕). The Exclusive constraint is exactly what licenses writing \(C_1 \oplus C_2\) for that node's value in the first place: it shrinks the 4 raw (C1, C2) combinations down to the 3 that are actually legal, which is what the decision table in Section 4 is built from.

Last-minute revision

Identity

c=1 ⇒ e=1, else e=0. One cause, straight through.

OR

Any one of c1, c2, c3 = 1 ⇒ e=1, else e=0.

NOT

c=1 ⇒ e=0, else e=1. Fires when the cause is false.

AND

All of c1, c2, c3 = 1 ⇒ e=1, else e=0.

Exclusive

Between causes, not an effect gate: c1 and c2 can never both be 1. Dashed link, labelled "E" — don't confuse with an effect E.

The technique (checklist)

1 Identify causes & effects → 2 Build the graph → 3 Add constraints → 4 Convert to decision table & derive one test case per legal column.

Print Message — general form

\( E_1=(C_1\oplus C_2)\wedge C_3 \)  \( E_2=\lnot(C_1\vee C_2) \)  \( E_3=\lnot C_3 \)
C1/C2 exclusive ⇒ 6 valid test cases (TC1–TC6), not 8.

Exam trap

Two causes can produce the same effect value and still need separate test cases (TC1 and TC2 both give E1=1) — a decision table is per legal cause-combination, not per distinct effect.
