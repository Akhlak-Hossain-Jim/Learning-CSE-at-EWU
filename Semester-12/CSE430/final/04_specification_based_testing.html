Topic 01

Overview: specification-based (black-box) testing

Same family as equivalence partitioning and decision tables — but this lecture is about the two workhorse techniques for anything with "steps" or "modes": state transition testing and use-case-based testing.

Every technique you've met so far in this course — equivalence partitioning, boundary value analysis, decision tables, cause-effect graphs — starts from the specification (what the system is supposed to do) rather than the source code (how it actually does it). That's why the whole family is called specification-based testing, and it's also known by a second name you'll see in the same breath: black-box testing, because the tester treats the system as a sealed box and only looks at inputs and outputs, never the code inside.

The pipeline is always the same three-step shape:

The specification-based pipeline
Requirements  →  Test Cases  →  Expected Results

Instead of asking "is this code correct?" — a white-box question — the tester asks "does the software behave exactly as the specification requires?". That reframing is why these techniques can be designed before a single line of code is written, are independent of the programming language used, and are exactly what an independent QA team (who may never see the source) is equipped to do.

Key idea

Black-box techniques differ in what part of the specification they attack. Input values → equivalence partitioning / boundary value analysis. Combinations of conditions → decision tables. Chains of cause and effect → cause-effect graphs. Behaviour that changes depending on what has already happened → state transition testing. A user working toward a goal through the system → use-case-based testing. And "what would a tester's gut instinct catch that a formal technique might miss?" → error guessing.

Choosing the right technique

The lecture gives this mapping table directly — it is a favourite source for a quick "which technique would you use here?" exam question, so memorise the right-hand column, not just the left.

Requirement typeSuitable technique
Input validationEquivalence Partitioning, Boundary Value Analysis
Multiple conditionsDecision Table Testing
Logical dependencyCause-Effect Graphing
State-dependent behaviourState Transition Testing
User interactionUse-Case-Based Testing
Unexpected situationsError Guessing

Different specifications need different testing techniques, and the effectiveness of your testing effort depends on picking the technique that actually matches the shape of the requirement in front of you — using a decision table on something that is really a sequence of states just makes the model needlessly awkward.

Watch out

"State-dependent behaviour" is the trigger phrase for state transition testing: the same input produces different results depending on what happened before it. If a question describes a system where "entering the same value twice gives two different outcomes," that is your signal to reach for a state diagram, not a decision table.

Topic 02

State transition testing: concepts and notation

Built from scratch — this is the section to read slowly if state machines are new to you.

Why care: the traffic light picture

Picture an ordinary traffic light. It only ever shows one colour at a time, and which colour comes next is not a free choice — it depends entirely on which colour is showing right now. If the light is red, the timer expiring turns it green. If the light is green, the same "timer expires" event turns it yellow instead. The light can never jump straight from red to yellow; it always has to pass through green first. Notice what's going on: the exact same event (the timer running out) produces a different result depending on the light's current condition. That "current condition" is what testers call a state, and any system that behaves like this — where history matters and the same input can lead to different outcomes — is a natural candidate for state transition testing.

A login-lockout mechanism works the same way. Type a wrong password once and you get a warning; type the very same wrong password again after the system has already logged two failures, and instead of a warning your account gets locked. The password you typed didn't change — the system's memory of what already happened did. State transition testing is the technique built specifically to test systems like this: ATM PIN entry, account lockouts, online order processing, elevator controllers, traffic lights, and document-approval workflows are the lecture's own list of examples.

Key idea — what a state-transition test case actually verifies

A state-transition test case is not just "give the system an input and check the output." It verifies something more specific: starting from a named state, triggering a named event moves the system to the correct next state and produces the correct action — and, just as importantly, that an event which is not allowed in the current state is correctly rejected or ignored rather than silently accepted. Every test case in this technique is really answering one question: "from here, does this event take me to the right place — or, if it shouldn't be allowed at all, does the system correctly refuse to move?"

Core concepts

Five terms make up the whole vocabulary. Learn them in this order, because each one is defined using only the term before it:

State

The current condition of the system — e.g. "Logged Out," "One Failed Attempt," "Locked." A system in state transition testing has a small, countable list of these.

Event

An input or occurrence that may cause the system to change what state it's in — e.g. "user enters a password," "timer expires."

Transition

The actual movement from one state to another, triggered by an event.

Action

The output or operation the system performs as a result of the transition — e.g. "display warning," "lock the account."

Guard

An optional extra condition that must also be true for the transition to fire (e.g. "only if this is the third consecutive failure").

Formal notation

Once you have those five words, the lecture's general notation for a single transition reads naturally left to right:

General notation
Current State  +  Event [Guard]  /  Action  →  Next State

Read it as a sentence: "While in [Current State], if [Event] happens (and [Guard] holds), then do [Action] and move to [Next State]." The worked example from the slides:

Worked instance
Two Failed Attempts + Invalid Password / Lock Account → Locked

Here, "Two Failed Attempts" is the current state, "Invalid Password" is the event, there is no extra guard, "Lock Account" is the action, and "Locked" is the next state. The lecture's own takeaway on this diagram is worth memorising word for word: the same event may lead to different next states or actions depending on the current state and guard conditions — that single sentence is the entire justification for why this technique exists.

When should you reach for it?

Use state transition testing when the system you're looking at has all of these fingerprints: a finite, nameable number of states; events that change which state it's in; rules that depend on the sequence of events, not just the latest one; a mix of valid and invalid state changes; and — the giveaway — different responses to the exact same event depending on where the system currently stands.

From state model to test cases

Turning a state diagram into an actual test suite follows a fixed six-step recipe: identify all possible states → identify the events that can affect each state → determine which transitions are valid → identify the transitions that are prohibited or simply undefined → write down the expected action for every transition → assemble event sequences with their expected results. Coverage is then judged against four increasingly strict targets:

  • State coverage — every state gets visited by at least one test at least once.
  • Transition coverage — every valid transition arrow gets executed by at least one test.
  • Transition-pair coverage — every pair of consecutive transitions (an N-switch) is exercised, not just each transition alone.
  • Invalid-transition coverage — a deliberately chosen set of prohibited transitions is tried anyway, to confirm the system rejects them correctly.
Watch out

Transition coverage is not the same thing as testing every possible path through the diagram — with loops (like the lockout cycle looping back to "Logged Out"), the number of paths is effectively unbounded. The exam-safe answer is "cover every state and every valid transition at least once, plus a sample of the invalid ones" — not "test every possible sequence."

Benefits and limitations

Benefits

Represents state-dependent behaviour clearly; tests event sequences systematically; identifies missing and invalid transitions; supports both positive and negative testing; improves coverage of workflow-oriented systems.

Limitations

Models can become complex with many states; requires a clear and complete specification to build the model from; state combinations can grow rapidly; less suitable for stateless functions; does not directly exercise internal code structure.

Topic 04

Use-case-based testing

A different lens on the same specification: instead of "what state is the system in," ask "what is the user trying to accomplish, and what could happen along the way?"

A use case is simply a written description of how a user (or another system) achieves a goal by interacting with the software — "customer purchases a product," "student registers for a course," "user withdraws cash from an ATM," "patient books an appointment." Use-case-based testing is the specification-based technique that derives test cases directly from that description: from the user's goal, from the actor-system interactions, from the normal ("main") success scenario, and from the alternate and exception paths that branch off it. The core idea in one sentence, straight from the lecture: a use case describes how a user achieves a goal, and testing verifies whether every relevant path through that description actually works correctly.

This technique earns its keep on interactive applications, business workflows, web and mobile apps, systems with multiple actors, and acceptance/system-level testing — anywhere the thing being validated is really an end-to-end journey rather than a single function call.

Elements of a use case

Eight components make up a complete use case in this lecture's framework:

1. Actor

The person or external system interacting with the software.

2. Goal

What the actor wants to achieve.

3. Preconditions

Conditions that must already be true before the use case can start.

4. Trigger

The event that starts the use case.

5. Main flow

The normal, successful sequence of steps — the "happy path."

6. Alternate flow

A valid variation of the main sequence (still succeeds, just takes a different route).

7. Exception flow

An error or failure path.

8. Postconditions

What is true about the system's state once the use case finishes.

Key idea

Each of the three flow types — main, alternate, exception — can generate one or more test scenarios of its own. That's why a single use case routinely produces multiple test cases: one for the happy path, and at least one per meaningfully different branch off it.

From use case to executable test cases

The pipeline has six stages, and it's worth being able to name all six because a theory question may ask you to walk through it generically, without any specific example attached:

1. Use Case→ 2. Actors & Preconditions→ 3. Main / Alternate / Exception Flows→ 4. Test Scenarios→ 5. Test Data & Expected Results→ 6. Executable Test Cases

Concretely: the use case defines the goal and scope; identifying actors and preconditions tells you who is involved and what must be true first; splitting the interaction into main, alternate, and exception flows describes every possible path; converting each flow into a test scenario states, in one sentence, what that particular test is trying to prove; attaching concrete test data and expected outcomes to each scenario makes it checkable; and the final transformation into executable test cases is what a tester actually runs. Good coverage means touching all of: the main flow, the alternate flows, the exception flows, precondition failures, and the important combinations of paths — not just the happy path.

Watch out

The lecture stresses this explicitly: expected results must be derived from the specification, not assumed by the tester. "Payment declined → order not confirmed" is only a valid expected result because the spec says so; never invent what "should" happen based on intuition about how a similar app behaves elsewhere.

Topic 06

Error guessing (brief)

Listed by this lecture as the fourth pillar of specification-based testing, alongside input-focused, rule-focused, and behaviour-focused techniques — but treated as a short mention here, not a full worked technique.

The lecture's overview diagram places error guessing under its own "experience-based technique" category, distinct from the three formal, model-driven techniques above it. Its role in the choosing-the-right-technique table is specific: it is the technique to reach for when the requirement type is "unexpected situations." Rather than deriving tests mechanically from a diagram or table, the tester draws on prior experience, intuition, and knowledge of where systems typically break — empty inputs, null values, boundary-adjacent timing, simultaneous requests — to guess at defects a formal model wouldn't systematically surface.

Watch out

Because this lecture treats error guessing briefly (as the fourth entry in the technique overview and the choosing table, without its own worked example), do not expect a full multi-slide worked scenario for it on the exam the way there is for state transition testing and use-case-based testing. A short-answer question ("what is error guessing and when would you use it?") is more likely than a worked problem.

Topic 07

Practice questions

Ordered easiest to hardest. Try each one yourself before opening the solution.

Question 1 · short answer

In your own words: what does a state-transition test case actually verify? Why is "give it an input and check the output" not a complete description?

Show model answer
What this tests & where it comes from This is the core conceptual question of the whole lecture — it checks whether you understand the difference between an ordinary input/output test and a state-transition test. It draws on the "Core Concepts" slide and the general notation Current State + Event [Guard] / Action → Next State.

An ordinary test just checks "input X produces output Y." A state-transition test case checks something one level richer: starting from a specific state, does a specific event move the system to the correct next state and trigger the correct action — and, for events that are not permitted in that state, does the system correctly refuse to move (reject or ignore the event) instead of silently accepting it? This matters because in a stateful system the exact same input can be correct in one state and a security bug in another — e.g. entering a valid password is correct when the account is in "Logged Out," but the identical input should be rejected when the account is in "Locked." A test that only checks "valid password → access granted" without also checking "valid password while Locked → access still denied" has not actually verified the state machine at all.

Question 2 · easy

Given the transition Two Failed Attempts + Invalid Password / Lock Account → Locked, identify the state, the event, the action, and the next state. Then write the general notation template it is an instance of.

Show worked solution

  1. Current state = Two Failed Attempts

    This is where the system is standing before the event happens — it appears immediately before the "+" in the notation.

  2. Event = Invalid Password

    The occurrence that triggers the transition — it appears right after the "+" and before "/".

  3. Guard = none present

    A guard would appear in square brackets after the event; there isn't one here, so the transition fires unconditionally whenever the event occurs in this state.

  4. Action = Lock Account

    The operation performed as a result — it sits after the "/" symbol.

  5. Next state = Locked

    Where the system ends up — it appears after the "→" arrow.

  6. Template: Current State + Event [Guard] / Action → Next State

    Slotting the five parts back into the lecture's general notation confirms the instance matches the template exactly, with the optional guard simply omitted.

  2. Event 1: Invalid password → S1

Question 4 · medium

Explain why "Locked + Valid Password" is tested as an invalid-transition test case rather than a valid one, and state what defect it would reveal if the system got it wrong.

Show worked solution

  1. Check the transition table for a row starting "S3: Locked + Valid password"

    The state transition table only lists valid password as a defined transition from S0, S1, or S2 — never from S3.

  2. Conclude: no such transition is defined

    An event with no listed transition out of the current state is, by definition, an invalid/prohibited transition in this model.

  3. Expected behaviour: access denied; remain locked

    This exact row appears in the lecture's "Testing Invalid Transitions" table — a locked account must stay locked regardless of what password is entered, correct or not.

  4. Defect if this test failed: an authentication bypass / security hole

    If entering the correct password on a locked account granted access anyway, the lockout mechanism would be completely defeated — exactly the class of defect ("unauthorized state changes," "security weaknesses") the lecture lists as the reason invalid-transition testing exists.

Question 5 · medium — in-class exercise, fully solved

Online Order Status. An online order may be in the states Created → Paid → Shipped → Delivered. Additional rules: a created order can be cancelled; a paid order can be refunded; a shipped order cannot be cancelled; a delivered order can be returned. Task: identify all states and events, and draw the state transition diagram.

Show worked solution

  1. States: Created, Paid, Shipped, Delivered, Cancelled, Refunded, Returned — 7 total

    Read directly off the requirement: the four "main line" states plus the three end-states each branch rule introduces (cancel, refund, return).

  2. Events: Pay, Ship, Deliver, Cancel, Refund, Return

    One event per verb in the requirement — each rule ("can be cancelled," "can be refunded," "can be returned") names an event as well as a resulting state.

  3. Valid transitions: Created→Paid (Pay), Paid→Shipped (Ship), Shipped→Delivered (Deliver), Created→Cancelled (Cancel), Paid→Refunded (Refund), Delivered→Returned (Return)

    Each transition pairs a state named in the main flow (or a branch state) with the event that leads there.

  4. Explicitly prohibited: Shipped→Cancelled (Cancel)

    The requirement states directly: "a shipped order cannot be cancelled" — this is the one prohibition given by name, so it must appear on the diagram as a crossed-out / dashed invalid edge.

Solid teal/ochre = valid transitions. Dashed red = the one transition the requirement explicitly forbids.

Question 8 · medium — new scenario

For the ATM PIN-entry lockout of Question 7, write three valid-transition test cases and two invalid-transition test cases with their expected behaviour.

Show worked solution

  1. Valid TC1: Correct PIN → S4

    Simplest happy path; expected result: customer authenticated immediately, no warnings shown.

  2. Valid TC2: Wrong, Wrong, Correct → S4

    Uses up both warnings and still recovers; expected result: two warnings shown, then access granted, counter reset.

  3. Valid TC3: Wrong, Wrong, Wrong → S3

    Exhausts all three attempts; expected result: card retained, "contact your bank" message, machine returns to accepting a new card (not this customer's).

  4. Invalid #1: S3 (card retained) + Correct PIN

    No transition is defined out of S3 by any customer action — mirrors "Locked + Valid password" in the login example; expected behaviour: access still denied, card remains retained.

  5. Invalid #2: S0 (no card inserted / idle) + Complete Transaction

    There is no active session to complete when the machine is idle; expected behaviour: request ignored, machine stays idle — a real ATM must not crash or eject a nonexistent card.

Question 9 · medium — new scenario

A simple traffic light cycles Red → Green → Yellow → Red under a fixed timer. On a power failure, the light immediately switches to a safety mode, Flashing Red, regardless of what colour was showing. When power is restored, the cycle resumes from Red. Draw the state diagram and give one valid and two invalid transition test cases.

Show worked solution

Teal solid = normal timer-driven cycle. Dashed red = power failure (from any state). Purple = power restored (returns to Red only).

  1. Valid TC: Red —Timer→ Green —Timer→ Yellow —Timer→ Red

    Exercises one full normal cycle; expected result: light changes colour exactly in that order, never skipping a colour.

  2. Invalid #1: Red + Timer Expires → Yellow (direct)

    No transition from Red straight to Yellow exists in the model; expected behaviour: this jump must never occur — the light always passes through Green first. If it did happen, it would be a serious safety defect.

  3. Invalid #2: Flashing Red + Timer Expires

    The timer event has no defined effect while in the safety mode — only "Power Restored" gets the light out of Flashing Red; expected behaviour: the light keeps flashing red and ignores the timer until power actually returns.

Question 11 · short answer

Describe, generically, how you derive test cases from a use case. Why does one use case usually generate several test cases rather than just one?

Show model answer
What this tests & where it comes from This tests the six-stage pipeline on the "From Use Case to Test Cases" slide, and asks you to connect it to the "one use case, multiple test cases" observation repeated on the "Alternate and Exception Tests" slide.

Start from the use case, which defines the goal and scope of the interaction. Identify the actors and preconditions — who is involved, and what must already be true. Split the interaction into its main flow, alternate flows, and exception flows — this describes every meaningfully different path through the use case. Convert each flow into a test scenario, i.e. one sentence stating what that particular path is meant to prove. Attach concrete test data and the expected result (taken from the specification, never assumed) to each scenario. Finally, transform each scenario-plus-data pairing into an executable test case a tester can actually run. One use case generates several test cases because each flow — main, each alternate, each exception — is a genuinely different path through the system, and good coverage means exercising all of them, not only the happy path.

Question 12 · hard — in-class exercise, fully solved

Course Registration. A student logs in, selects a course, and the system checks the prerequisite, then seat availability, then whether the student is already registered, before registering the student and updating their schedule. Identify the actor and goal, write the main success flow, find the alternate/exception flows, derive three test cases, and state the expected results.

Show worked solution

  1. Actor: Student. Goal: successfully register for a course.

    The actor is whoever initiates the interaction toward a goal — here the student, who wants a seat in the course, not the system itself.

  2. Precondition: student has a valid account and is eligible to register. Trigger: student selects a course to register for.

    These must hold, or be triggered, before the main flow can even begin — matching the "Preconditions" and "Trigger" elements of a use case.

  3. Main success flow: Login → Select Course → Check Prerequisite (met) → Check Seat Availability (available) → Register (not already registered) → Update Schedule → Registration Successful

    This traces the "Yes" branch at every decision diamond in the exercise's flow diagram — the path where nothing goes wrong.

  4. Exception flow A: Check Prerequisite → "No" → Prerequisite Not Met

    The diagram's first decision diamond has a "No" arrow leading to a distinct, named failure outcome — that is exactly the definition of an exception flow.

  5. Exception flow B: Check Seat Availability → "No" → Course Full

    Same reasoning at the second decision point: seats unavailable is a different failure path from a failed prerequisite, so it gets its own flow and its own test case.

  6. Exception flow C: Already Registered? → "Yes" → Duplicate Registration Blocked

    Note the branch direction is reversed here — "Yes" (already registered) is the failure path, "No" continues to Update Schedule — so read each diamond's labels carefully rather than assuming "No" always means failure.

  7. Test case 1 (main flow): student meets the prerequisite, a seat is open, and they are not already registered → expected result: registration succeeds, schedule updated

    Directly executes the happy path identified in step 3.

  8. Test case 2 (exception A): student has not completed the prerequisite → expected result: registration blocked, "prerequisite not met" message, schedule unchanged

  9. Test case 3 (exception B): prerequisite met, but the course has zero open seats → expected result: registration blocked, "course full" message, schedule unchanged

Question 13 · hard — compare/contrast

Compare state transition testing and use-case-based testing. When would you choose one over the other, and could a real system need both?

Show model answer
What this tests & where it comes from This tests whether you can tell the two behaviour/workflow-focused techniques apart, using the "Choosing the Right Technique" table (state-dependent behaviour vs. user interaction) plus what each technique's worked example actually modelled.

State transition testing models the system's internal condition over time — it asks "what state is the system in, and what happens when this event occurs while it's in that state?" It is the right tool when the same input can legitimately produce different outcomes depending on history, as in the login-lockout example (a valid password behaves differently in "Logged Out" versus "Locked"). Use-case-based testing instead models a user's end-to-end journey toward a goal — it asks "does every path an actor might take through this interaction (main, alternate, exception) actually work?" It is the right tool for validating a business workflow like "purchase a product," where the concern is covering branches in a scenario, not tracking a persistent internal condition.

They are not mutually exclusive, and a real system commonly needs both at once: the "Purchase a Product" use case, for instance, moves an order through states behind the scenes (Created → Paid → Shipped → Delivered from Question 5) even while the customer-facing interaction is best specified as a use case. A thorough test plan would use use-case-based testing to make sure every user-facing path (main flow, apply a coupon, payment declined, session expires) is covered, and state transition testing to make sure the order's internal lifecycle can't skip a step or get stuck in an invalid state — the two techniques attack the same system from complementary angles rather than competing for the same job.

Question 14 · hard — stretch

The "Purchase a Product" use case's checkout step can itself be modelled as a small state machine: Cart → Checkout Started → Payment Pending → (Confirmed or Payment Failed). Sketch this mini state machine and explain which parts of the original use case are better captured by this state view versus the original flow-based view.

Show worked solution

  1. States: Cart, Checkout Started, Payment Pending, Confirmed, Payment Failed

    Each is a distinct condition the order sits in during checkout, exactly the granularity used for Created/Paid/Shipped/Delivered earlier.

  2. Cart —Proceed to Checkout→ Checkout Started —Submit Payment→ Payment Pending

    These transitions correspond to main-flow steps 3–6 of the original use case (proceed to checkout, enter details, select payment, system authorizes payment).

  3. Payment Pending —Authorization succeeds→ Confirmed; Payment Pending —Authorization fails→ Payment Failed

    This is the exact fork the use case's "Exception: Payment is declined" row describes — as a state machine, it becomes an explicit branch out of one named state instead of a bullet in an exceptions table.

  4. Payment Failed —Retry with new details→ Checkout Started (re-enter the state machine)

    A state view naturally shows that a failed payment can loop back and retry, which is easy to miss when exception flows are listed as one-off rows rather than drawn as a cycle.

Which view suits what

The state view is better for questions about what the order's payment status can and cannot do next — e.g. "can a Confirmed order be re-charged?" (no defined transition, so: invalid). The use-case view is better for questions about the customer's whole experience — actor, goal, what the customer sees at each screen, and where things like "apply a coupon" or "choose cash on delivery" fit in, which never map cleanly onto a state at all since they're variations of a step, not conditions of the order. In practice you would keep the use case as the primary specification for tester walkthroughs and pull out a state machine only for the sub-parts (like payment status) that genuinely behave like a state machine.

Last-minute revision

State transition testing, in one line

Checks that a specific event, fired while the system is in a specific state, moves it to the correct next state (and that disallowed events are correctly rejected).

Notation legend

Current State + Event [Guard] / Action → Next State. Guard is optional; the same event can lead to different next states/actions depending on the current state.

Login-Security states

S0 Logged Out → S1 One Failure → S2 Two Failures → S3 Locked (red arrows, Invalid Password). Any of S0/S1/S2 + Valid Password → S4 Logged In. S4 + Logout → S0. S3 + Admin Reset → S0.

Coverage targets

State coverage (visit every state) · Transition coverage (fire every valid transition) · Transition-pair coverage (consecutive pairs) · Invalid-transition coverage (sample the prohibited ones).

Use-case elements checklist

Actor · Goal · Preconditions · Trigger · Main flow · Alternate flow · Exception flow · Postconditions. One use case → multiple test cases (one per meaningful flow).

Use case → test case pipeline

Use Case → Actors & Preconditions → Main/Alternate/Exception Flows → Test Scenarios → Test Data & Expected Results → Executable Test Cases.

Choosing the right technique

Input validation → EP/BVA. Multiple conditions → Decision Table. Logical dependency → Cause-Effect Graph. State-dependent behaviour → State Transition. User interaction → Use-Case. Unexpected situations → Error Guessing.

Golden rule

Expected results must come from the specification, never from the tester's assumption of what "should" happen.
