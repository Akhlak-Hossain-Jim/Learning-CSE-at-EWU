Topic 01

What is regression testing, and why isn't "retest the fix" enough?

The single question every regression question on the exam is really asking.

Software never stands still. Someone fixes a bug, adds a feature, refactors a messy function, wires two components together, or just bumps a library version. Every one of those changes is a small edit in a system that used to work — and the danger isn't that the edited part breaks (you'll usually notice that immediately). The danger is that the edit quietly damages some other part of the system that nobody touched and nobody was watching.

Picture a Jenga tower. You pull one block out to fix it — maybe it was warped — and slot a better one back in. The tower still looks fine. But pulling that block shifted weight onto three others, and one of them is now a hair's breadth from toppling. You didn't touch those three blocks. You still broke them, indirectly, by changing something they were quietly depending on. Regression testing is the discipline of going around the whole tower after every change and checking that nothing else has shifted.

Key idea

Regression testing is change-related testing performed to detect whether a modification has introduced or uncovered defects in unchanged or previously working areas of the software. The one question behind it: "did this change break anything that was working correctly before?"

Note what that definition is not asking. It is not asking "does the fix work?" — that's a different, narrower question the lecture handles separately (Topic 2). Regression testing only cares about collateral damage.

What triggers it, and what it normally has to cover

Per the lecture, regression testing may be triggered by any of these:

  • A defect correction
  • A new or modified feature
  • Code refactoring
  • Integration of components
  • Configuration or environment changes

And it normally has to cover:

  • Existing behaviour connected to the change
  • Upstream and downstream components
  • Shared APIs, databases, files, or services
  • Critical end-to-end business workflows
  • Other high-risk areas that may be indirectly affected

Change-related testing has two obligations, not one

Whenever a change lands — fix, feature, refactor, config tweak — the lecture frames what happens next as a small pipeline with two parallel obligations that both have to be discharged before anyone can trust the change:

  1. Retesting / confirmation testing — prove that the intended correction actually works.
  2. Regression testing — detect unintended side effects in previously working behaviour.

The workflow the slides draw is: Change → Impact analysis → (Confirmation testing and Regression testing, run alongside each other) → Evaluate evidence → Pass (confidence to continue) or Fail (report and correct). Two more terms worth locking in now, because later topics build directly on them: selection decides what goes into the test run; prioritization decides what runs first. They are different decisions, made in that order.

Watch out

A very common exam trap is treating "regression testing" as some kind of loop — "keep testing until the bug is gone." That's not what either term means, and it's exactly the mix-up the next topic exists to fix, in detail.

Topic 02

Retesting vs regression testing: two different jobs, not one repeated

This exact distinction is worth marks on its own — get it precise, not approximate.

These two terms get blurred together constantly because both involve "running a test again." But which test, and why you're rerunning it, are completely different in each case — and that difference is the whole point.

Watch out — correcting a specific mix-up

What was said: "retesting means testing again, regression testing might mean testing again and again till the issue is properly fixed."

That description treats both terms as variations of "keep testing the same bug until it's gone" — which is not what either one means, and would cost marks on this exam. Here is the corrected picture, side by side:

AspectRetesting / confirmation testingRegression testing
What you rerunThe exact same test case that previously failed, on the fixed system.Other tests that were already passing before the change — unrelated to the bug that was fixed.
Why you rerun itTo confirm the specific defect is actually gone — a one-time check, done once, not a loop.To make sure the change didn't silently damage behaviour that used to be fine.
If it failsThe fix didn't work — go back and fix the original defect again (this is not "regression testing" — it's still confirmation testing, just failing).The change had a side effect elsewhere — a new, separate defect has been found.

So: retesting is narrow and backward-looking — one specific test, checked once, to confirm one specific fix. Regression testing is broad and forward-looking — a set of unrelated, previously-green tests, checked to guard against collateral damage. Neither one is "testing again and again until it's fixed" — that description belongs to neither term.

The lecture also gives retesting a second name worth remembering: confirmation testing. If you see either word on the exam, they mean the same thing. Classify any given test by asking one question — what is its primary objective?

Comparison aspectRetesting / confirmationRegression testingCourse-registration example
QuestionWas the original defect fixed?Did the change damage existing behaviour?Fix seat release; protect enrolment flows
Test basisPreviously failed test, plus fix-specific casesPreviously passing tests in affected areasFailed-payment case vs success/retry cases
ScopeNarrow: corrected behaviourBroader: affected, unchanged behaviourSeat release vs payment, inventory and retry
Typical orderRun first, to confirm the correctionRun after or alongside confirmationConfirm the fix, then explore ripple effects
One-line version to memorize

Retesting re-checks the one test that used to fail, to prove the fix works. Regression testing re-checks other tests that used to pass, to prove the fix didn't break anything else. Same change, two different audiences of tests.

Topic 03

A change creates direct and ripple effects — the SeatReleaseService example

The faculty's running example for the whole lecture. Learn this one scenario well; it comes back repeatedly.

Once you know a change needs both confirmation and regression testing, the next question is: regression testing where, exactly? A change doesn't just affect the code it touches — it fans out along three different kinds of exposure. Think of dropping a stone in a pond: there's the splash where the stone lands (direct), the ripples spreading outward and touching other things floating nearby (dependency), and — if someone's boat is moored at the edge — the rocking that reaches all the way to a person who never even saw the stone (business impact).

  • Direct impact — the changed code, requirement, configuration, and the test that originally failed. This is the epicentre of the change.
  • Dependency impact — callers, callees, APIs, shared databases, messages, files, and common services that sit next to the changed component. This is the ripple.
  • Business impact — critical end-to-end journeys, high-value transactions, and severe failure outcomes for real users. This is who actually gets hurt if the ripple reaches them.

The scenario: a patch to SeatReleaseService

The lecture's example: a university course-registration system has a component called SeatReleaseService. Its job is to release a seat that was being held for a student whose payment then failed, so someone else can take it. The team patches this component — and that one patch fans out into four distinct test items, spread across all three impact categories:

TestImpact categoryWhat's exposedPurpose of the test
T1Direct impactThe patched payment-failure path itselfA payment failure releases the held seat within 30 seconds
T2Dependency impactShared seat-inventory countSeat inventory is correctly restored
T3Dependency impact (ripple)Retry logic touching the same shared dataA retry after release creates no duplicate enrolment
T4Business impactThe next student's booking journeyThe next student can successfully reserve the freed seat
Key idea

One small patch to one component produced four test items across three impact categories. That's the concrete reason "just retest the bug" (T1 alone) is never sufficient — T2, T3, and T4 are all real exposure that a narrow retest would never touch.

Watch out

Don't conflate dependency impact with business impact — they answer different questions. Dependency impact is a technical question: "what else reads/writes the same data or calls the same interface?" Business impact is a consequence question: "if this breaks, who is hurt and how badly?" A test can matter for either reason, or both — T3 matters because of shared data (dependency), T4 matters because a real student's registration is on the line (business).

Topic 04

Smoke testing vs sanity testing

Two fast, cheap confidence checks — neither one is a substitute for regression testing.

Full regression suites can take hours to run. Nobody wants to burn that time on a build that's fundamentally broken, or a patch that obviously didn't work. So teams run a quick check first. There are two flavours of "quick check," and the exam wants you to be able to tell them apart.

Think of it like cooking a big meal. Smoke testing is walking into the kitchen and checking that the oven turns on, the tap runs, and the fridge is cold — a wide sweep across everything, but shallow, just "is anything obviously off?" Sanity testing is different: you changed one recipe's seasoning, so you taste that one dish and check the two or three ingredients you touched — narrow, but you actually dig into the specific thing that changed.

 Smoke testingSanity testing
CharacterWide and shallowNarrow and focused
Question askedIs the build stable enough for deeper testing?Should focused regression continue?
What it runsCritical end-to-end checks across the whole system, after a new build or deploymentA minor patch and its close dependencies, in an otherwise stable build

How they relate: neither replaces full regression testing. If a new build happens to also contain a focused patch, the practical order is smoke first (is the build even standing?), then sanity (does this specific change behave?), then the real regression suite behind it.

Comparing them by trigger, scope, and outcome

Comparison aspectSmoke testingSanity testingPractical rule
Main questionIs the build stable enough for deeper testing?Does the focused change behave reasonably?Breadth vs focused confidence
ScopeWide and shallow: critical flows across the systemNarrow and deeper: changed area and close dependenciesDo not treat either as full regression
Typical triggerNew build, deployment, or broad integrationMinor patch in an otherwise stable buildUse the build context to decide
OutcomePass allows detailed testing to continuePass allows focused regression to continueFailure sends the build/change back
Rule of thumb

Brand-new build or deployment → smoke (is anything on fire?). Small, isolated patch dropped into an already-stable build → sanity (does this one change make sense?).

Topic 05

Selection decides what enters the regression suite

You can never rerun every test ever written — so what earns a spot?

A mature product can accumulate thousands of tests. Rerunning all of them after every single change is too slow and too expensive to be practical. So the lecture gives a rule: include a test in the regression suite when the evidence shows direct exposure, dependency exposure, or unacceptable business risk — and be able to say, for every inclusion or exclusion, exactly which of those three justified the decision.

Selection signalInclude?ReasonExample
Original failed testAlwaysConfirms the correctionFailed payment releases the seat
Changed requirement / code / API / configAlwaysDirect change exposurePayment callback or timeout rule
Dependent interface or shared dataUsuallyRipple-effect riskInventory DB, retry, confirmation
Critical journey or defect-prone areaRisk-basedFailure cost is highSuccessful course enrolment

Notice the pattern from Topic 3 showing up again: row 1 is the retest, row 2 is direct impact, row 3 is dependency impact, row 4 is business impact. The selection table is the direct/dependency/business framework turned into an actionable checklist.

Watch out

"Usually" and "risk-based" are not "always" — the exam may test whether you know that dependency-exposed and business-critical tests get judgement calls, not automatic inclusion, unlike the original failed test and the directly-changed code, which are non-negotiable.

Topic 06

The 7-step change impact analysis process

Turns "which tests should we run?" from a gut feeling into a defensible, traceable decision.

Selection (Topic 5) tells you the rule for what to include. Change impact analysis is the process that generates the evidence the rule needs — so that when someone later asks "why was this test in the suite (or left out)?", there's a documented answer rather than a shrug. The lecture lays it out as seven steps:

  1. Understand the change request and reproduce the original defect — you can't analyse an impact you haven't pinned down.
  2. Trace changed requirements, code, APIs, data, configuration, and environment — everything the change actually touched.
  3. Map upstream, downstream, and shared-resource dependencies — everything that sits next to what the change touched.
  4. Link affected items to existing tests and the traceability matrix — find out what already covers this territory.
  5. Add missing tests for new behaviour or uncovered interfaces — close the gaps step 4 exposed.
  6. Label tests: confirmation, regression, smoke, or sanity — every test gets a role, not just a name.
  7. Record the reason for every important inclusion or exclusion — this is what makes the suite defensible later.

Read as a pipeline, steps 1–2 gather the change evidence, step 3 builds the dependency map, steps 4–5 do the test trace and gap analysis, and steps 6–7 classify and record — producing a defensible suite that's traceable, complete, and justified.

Key idea

The order matters: you cannot select or prioritize tests (Topics 5 and 7) before you've done steps 1–4 here — selection and prioritization consume the output of change impact analysis, they don't replace it.

Topic 07

Prioritizing by risk: Impact × Likelihood

Selection says what's in the suite. This says what runs first.

Even after selection trims the universe of tests down to a defensible suite, that suite might still be too large to run all at once, or the team needs to know which failures to look at first. The lecture's classroom rule for ordering the suite is a simple risk score:

Risk-based prioritization
\[ \text{Risk score} = \text{Impact} \times \text{Likelihood} \]

Both Impact and Likelihood are scored on a 1–3 scale (1 = low, 3 = high). Impact asks: how bad is it if this behaviour actually breaks? Likelihood asks: how probable is it that this specific change actually reached this test's territory? Ties are broken using change proximity, defect history, and feedback speed.

Candidate signalImpactLikelihoodPriority interpretation
Original failed test33Risk 9 — run first, as confirmation/retest
Direct dependency + critical path32Risk 6 — high: strong exposure and high loss
Indirect dependency / shared data22Risk 4 — medium: run after direct dependencies
Unrelated, low-risk behaviour11Risk 1 — later, or exclude when evidence permits

Worked micro-example, reading the second row: a test on a directly dependent component sitting on a critical business path scores Impact 3 (a real transaction breaks) and Likelihood 2 (it's one hop away from the change, so plausible but not certain). \(3 \times 2 = 6\) — high priority, but run after the confirmation test at risk 9.

Watch out

Impact and Likelihood answer different questions — don't collapse them into one gut-feel "how worried am I" number, or you lose the tie-breaking power of the formula. A test can be high-impact but low-likelihood (a catastrophic but very indirect dependency) or the reverse (a trivial feature the change is nearly guaranteed to touch) — the multiplication is what lets both factors pull their weight.

Topic 08

Worked case: select and prioritize the tests

The lecture's full T1–T5 example, method end to end. Try the reasoning yourself before revealing it.

Patch: a failed payment must release the held seat within 30 seconds. Five candidate tests exist. Task: classify T1, select the regression tests, rank everything by risk, and decide whether smoke or sanity testing applies.

TestChange link and riskPurpose
T1Direct; \(3 \times 3 = 9\)Payment failure releases the seat within 30 s
T2Same service; \(3 \times 2 = 6\)Successful payment still confirms enrolment
T3Shared data; \(3 \times 3 = 9\)Retry after release creates no duplicate enrolment
T4Downstream; \(3 \times 2 = 6\)Another student can reserve the released seat
T5Unrelated; \(1 \times 1 = 1\)Student updates a profile photo
Work through it yourself first · then reveal

Before reading on: which test is the retest? Which of T2–T5 belong in the regression suite? What order should they run in? Is this a smoke or a sanity scenario?

Show the lecture's model reasoning

  1. T1 is retesting / confirmation.

    It directly reproduces the failed condition (a payment failure) and checks the exact requirement that was broken and fixed — the 30-second release rule. That is precisely the definition of retesting: rerun the previously failed test to confirm the correction.

  2. Select T2, T3, and T4 as regression tests; exclude T5.

    T2, T3, and T4 all sit on direct or dependency exposure from Topic 3 (they cover the success path, the shared enrolment data, and downstream seat availability — all things the SeatReleaseService patch could plausibly ripple into). T5 has no plausible link to a payment/seat-release patch — a profile-photo update — and its risk score (\(1\times1=1\)) confirms it belongs in the "exclude" tier of the priority table.

  3. Priority order: \(T1 \to T3 \to T2/T4\).

    By risk score: T1 and T3 tie at 9, T2 and T4 tie at 6. T1 runs first because confirming the fix itself takes precedence per the "typical order" rule from Topic 2. T3 follows as the highest-risk regression item (shared data — a duplicate enrolment is a serious, high-likelihood failure mode). T2 and T4 are an equally-ranked pair; either may run first, provided the choice is backed by a stated tie-breaker (change proximity, defect history, or feedback speed).

Answer

Retest = T1. Regression suite = {T2, T3, T4}, T5 excluded. Order: \(T1 \to T3 \to T2/T4\). Because this is a stable, focused patch to one service (not a new build), the appropriate fast check beforehand is sanity testing, not smoke.

Quick checks — recall and the retesting/regression mix-up

Question 1 · easy · recall

In one or two sentences, state the central question regression testing is trying to answer, and name two things that can trigger a round of regression testing.

Show model answer
What this tests The core definition from the opening of the lecture — this is the kind of one-line definitional question that opens a mixed-format paper.

Regression testing asks: "did this change break anything that was working correctly before?" It can be triggered by, for example, a defect correction and code refactoring (also acceptable: a new/modified feature, integration of components, or a configuration/environment change).

Question 2 · easy–medium · classify

QA fixes a bug where the login page accepted a blank password. To verify the fix, they re-run the exact test case that previously failed — submitting the same blank-password input — against the patched system. Is this retesting or regression testing? Justify in one sentence.

Show model answer

Retesting (confirmation testing). It reruns the exact test case that previously failed, on the fixed system, to confirm that the specific defect is actually gone — that is the defining feature of retesting, not regression testing.

Question 3 · easy–medium · classify

After that same login fix, QA also re-runs the checkout flow and the profile-update tests, both of which had nothing to do with the password bug and were already passing before the fix. Is this retesting or regression testing? Justify in one sentence.

Show model answer

Regression testing. It reruns other, previously-passing tests that are unrelated to the specific fix, to check that the change didn't damage behaviour elsewhere — the defining feature of regression testing, distinct from confirming the fix itself.

Question 4 · easy · recall

Change-related testing carries "two obligations." Name both, and state in one clause what each one proves.

Show model answer

(1) Retesting / confirmation testing — proves the intended correction actually works. (2) Regression testing — proves the change did not introduce unintended side effects in previously working behaviour.

Recall the SeatReleaseService patch (T1: seat released within 30s after payment failure; T2: seat inventory restored; T3: retry creates no duplicate enrolment; T4: next student can reserve the seat). Classify each test into direct, dependency, or business impact.

Show model answer

  • T2 — dependency impact. It exercises the shared seat-inventory count that SeatReleaseService writes to.
  • T3 — dependency impact (ripple). It exercises retry logic touching the same shared data, one step further out.
  • T4 — business impact. It exercises the real-world consequence for the next student's registration journey.
Question 6 · medium · theory

A team fixes a bug in a shipping-cost calculator used at checkout. Using the lecture's own terms, state precisely what retesting must check and what regression testing must check for this specific change.

Show model answer
What this tests & where it comes from This checks whether you can transplant the retesting/regression distinction (Topic 2) onto a scenario the lecture never explicitly worked, the way the course-registration example in the comparison table does for SeatReleaseService.

Retesting must re-run the specific test case that previously failed — e.g. the exact order that produced the wrong shipping cost — against the fixed calculator, to confirm the calculation is now correct. Regression testing must re-run other, previously-passing tests connected to the calculator's dependency footprint: other shipping rules that share the same pricing engine, the order-total display that consumes its output, and the checkout completion flow — none of which were themselves broken, but all of which could be silently damaged by the fix.

Question 7 · medium · classify

Decide smoke or sanity testing for each scenario, and justify in one line each: (a) a completely new mobile-app build is deployed to the QA environment overnight; (b) a one-line date-format bug is patched in an otherwise stable, already-deployed production build.

Show model answer

(a) Smoke testing. A brand-new build is the classic smoke trigger — a wide, shallow sweep across critical flows to check the build is stable enough for deeper testing at all.

(b) Sanity testing. A minor, isolated patch dropped into an already-stable build is the classic sanity trigger — a narrow, focused check on the date-format logic and its close dependencies.

Question 8 · medium–hard · apply

A team refactors an internal utility function (no functional change intended) that is called by both a tax calculator and a discount calculator; the shared database table it reads is untouched. Four candidate tests are proposed: (i) the tax calculator's existing correctness test, (ii) the discount calculator's existing correctness test, (iii) the full checkout journey (which calls the tax calculator), (iv) a UI test that only checks the theme colour of an unrelated settings page. Using the selection-decision table, decide include/exclude for each, with a reason.

Show model answer
  • (i) Include — always. The tax calculator directly calls the changed utility function; this is direct change exposure.
  • (ii) Include — always. The discount calculator also directly calls the changed function; same signal as (i).
  • (iii) Include — risk-based. Checkout is a critical business journey depending on the tax calculator's output; failure cost is high even though the exposure is one step removed.
  • (iv) Exclude. No plausible dependency on the changed utility function or the shared table — a low-risk, unrelated behaviour, matching the "later or exclude" tier of the priority table.
Question 9 · medium · sequence

The seven steps of change impact analysis are shuffled below. Put them back in order, and explain why step order matters for at least one adjacent pair. (a) Add missing tests for new/uncovered behaviour. (b) Record the reason for every inclusion/exclusion. (c) Understand the change request and reproduce the original defect. (d) Map upstream, downstream, and shared-resource dependencies. (e) Label tests as confirmation, regression, smoke, or sanity. (f) Trace changed requirements, code, APIs, data, configuration, and environment. (g) Link affected items to existing tests and the traceability matrix.

Show model answer

Correct order: c → f → d → g → a → e → b (i.e. understand the change, trace what it touched, map dependencies, link to existing tests, add missing tests, label them, record the reasons).

Order matters between (d) and (g): you cannot sensibly link affected items to existing tests until you know what those items are — which only exists once the dependency map (d) is built. Doing (g) before (d) would mean guessing at what's affected, defeating the purpose of a traceable, defensible suite.

Risk-based prioritization — a fresh scenario

Question 10 · medium–hard · compute

An e-commerce team fixes a bug where an expired coupon code was incorrectly being accepted at checkout; the patch makes the system correctly reject expired coupons. Four candidate tests, with Impact and Likelihood already assessed (1 = low, 3 = high):

TestDescriptionImpactLikelihood
ASubmit an expired coupon — expect rejection (the fix itself)33
BSubmit a valid, non-expired coupon — expect discount applied32
CCart total recalculates correctly after a coupon is rejected22
DUser changes their shipping address (unrelated feature)11

Compute each risk score, rank the four tests, and state which one is the retest rather than a regression test.

Show worked solution

  1. Risk(A) = \(3 \times 3 = 9\)

    Test A directly reproduces the corrected condition (an expired coupon) — this is the retest, and its risk score is computed the same way as any other candidate.

  2. Risk(B) = \(3 \times 2 = 6\)

    Test B exercises the same coupon-validation logic on its untouched, previously-passing path (valid coupons) — direct dependency, high impact if broken, but slightly less likely to be affected than the exact line that was changed.

  3. Risk(C) = \(2 \times 2 = 4\)

    Test C is one step further downstream (the cart total, which depends on the coupon outcome) — moderate impact, moderate likelihood, since it only breaks if the rejection logic also corrupts the total calculation.

  4. Risk(D) = \(1 \times 1 = 1\)

    Test D (shipping address) has no plausible link to coupon validation — lowest possible score on both factors.

  5. Rank: A (9) → B (6) → C (4) → D (1)

    Sort by risk score, descending; ties would be broken by change proximity, defect history, or feedback speed, but none occur here.

Answer

Test A is the retest (it reproduces the exact corrected defect). B, C, and D are regression candidates, run in the order B → C → D, with D a strong candidate for exclusion given its minimal risk score of 1.

Theory and synthesis

Question 11 · hard · theory

Explain why regression testing tends to become more expensive as a project moves later into its software development life cycle (SDLC), using the concepts taught in this lecture.

Show model answer
What this tests & where it comes from The slides don't state a cost curve directly, but the reasoning follows straight from three ideas taught here: the direct/dependency/business impact fan-out (Topic 3), the growing set of existing tests that selection has to sweep over (Topic 5), and the tracing work the 7-step process demands (Topic 6). The examiner wants you to connect these three, not recite a memorized fact.

Early in a project, a component has few callers, few shared dependencies, and few business workflows resting on it — so a change has a small direct-impact footprint and almost no dependency or business impact to trace. As the system matures, the same component accumulates more callers, more shared APIs and databases, and more critical end-to-end journeys depending on it (Topic 3's dependency and business impact categories both grow). Change impact analysis (Topic 6) then has more to trace and map in steps 2–4, and the existing regression suite that selection (Topic 5) has to consider keeping or adding to is larger too. More dependency exposure, more business exposure, and a bigger existing suite to reconcile all push up both the analysis effort and the number of tests that legitimately belong in the regression run — which is exactly why the same category of change costs more to regression-test late in a project's life than it did early on.

Question 12 · medium · theory

Why doesn't passing a smoke test, or passing a sanity test, mean the team can skip regression testing?

Show model answer

Smoke testing is deliberately wide but shallow — it only checks that critical flows aren't obviously broken, not that every affected behaviour still works correctly. Sanity testing is deliberately narrow — it only checks the changed area and its closest dependencies, not the fuller dependency and business-impact fan-out a change can produce. Both exist purely as fast gatekeepers deciding whether it's worth continuing to deeper testing; the lecture is explicit that "neither replaces full regression."

Question 13 · hard · stretch / essay

A team refactors the payment-gateway integration used by SeatReleaseService, with no intended behaviour change. Using the two obligations, the direct/dependency/business impact model, and the 7-step change impact analysis process, describe the full plan you would follow from the moment the change lands to deciding what runs first.

Show model answer
What this tests A synthesis question combining Topics 1, 3, 6, and 7 — exactly the kind of question a mixed-format exam uses to check you can operate the whole pipeline, not just recall each piece.

Because this is a refactor (no intended behaviour change), there is no failed test to retest — the "confirmation" obligation is satisfied differently: confirm the refactor did not change observable behaviour, using the previously-passing payment tests themselves as the confirmation basis. The regression obligation is the main concern here. I would run the 7-step change impact analysis: (1) understand exactly what the refactor touched inside the payment integration; (2) trace the changed code, its API contract, and any configuration; (3) map dependencies — SeatReleaseService as a direct caller, plus any other service sharing the same payment gateway client; (4) link those to existing tests via the traceability matrix; (5) add tests for any interface the refactor exposed that wasn't previously covered; (6) label each test confirmation, regression, smoke, or sanity; (7) record why each was included or excluded. Using the direct/dependency/business model: direct impact is the payment-gateway code itself; dependency impact is SeatReleaseService and any sibling caller of the gateway client; business impact is the seat-release and enrolment journeys that ultimately depend on a working payment path. I would then score each selected test as Impact × Likelihood, run the highest-risk, most-direct tests first, and — since this is a focused, isolated change to one integration rather than a new build — use sanity testing as the fast gatekeeper before the full regression run.

Question 14 · hard · 5 marks

Scenario: a stable-build patch changes course-registration prerequisite checking so that equivalent prerequisites are now accepted (previously, only the exact prerequisite course was accepted).

TestChange relationshipImpactLikelihood

Show full worked solution

Assumption stated up front: "equivalent prerequisite" and "regular (exact) prerequisite" are both evaluated by the same underlying prerequisite-acceptance rule that the patch modifies — this is why the table gives both Impact 3, and it is the basis for treating T2 as a dependency-exposed regression candidate rather than an unrelated test.

  1. Step 1 — identify the retest: T1.

    T1 reproduces the exact corrected defect (submitting an equivalent, not exact, prerequisite) — matching the definition of retesting from Topic 2: rerun the previously failed test case to confirm the fix. It is not a regression test, because it is not "previously passing" — it is the specific case that used to fail.

  2. Step 2 — include T2 as a regression test.

    T2 (a regular/exact prerequisite still accepted) exercises the same validation rule the patch modified, on a path that was already passing. Per the selection-decision table (Topic 5), a dependent interface or shared logic path is "usually" included — a change to acceptance logic risks silently breaking the exact-match case even though nobody intended to touch it.

Last-minute revision

Retesting vs regression

Retesting reruns the one test that used to fail to prove the fix works. Regression reruns other tests that used to pass to prove nothing else broke. Never "testing again and again until it's fixed" — that describes neither term.

Smoke vs sanity

Smoke = wide + shallow, after a new build/deployment, asks "is the build stable?" Sanity = narrow + focused, after a minor patch to a stable build, asks "does this change work?" Neither replaces full regression.

Risk-score formula

\( \text{Risk} = \text{Impact} \times \text{Likelihood} \), each scored 1 (low) to 3 (high). Break ties with change proximity, defect history, feedback speed.

Impact fan-out

Direct = changed code + the originally failed test. Dependency = callers/callees, shared APIs/DB. Business = critical journeys, high-value transactions.

Selection rule

Include when there is direct exposure, dependency exposure, or unacceptable business risk. Original failed test and changed code/API/config: always. Dependent interfaces: usually. Critical journeys: risk-based.

The 7-step checklist

  1. Understand the change; reproduce the defect
  2. Trace what changed
  3. Map dependencies
  4. Link to existing tests
  5. Add missing tests
  6. Label: confirmation / regression / smoke / sanity
  7. Record the reason for every call
