How to use this guide

Class 12 — Virtualization & Server Consolidation. Velete Ch.12 (all), Lamb Ch.6 (all). Course outcome CO3.

Class 11 dealt with the building. Class 12 deals with what runs inside it. The faculty made the connection explicit in the opening, and it is the sentence that frames the whole topic: "even the greenest Tier IV data centre with a 1.15 PUE is inherently wasteful if its underlying servers sit idle at 10% utilisation."

The one-sentence version of Class 12

An idle server still draws 50–70% of its peak power, so a data centre running at 10–15% CPU utilisation is burning most of its electricity on nothing — and virtualisation fixes this by collapsing many workloads onto fewer physical hosts so the surplus machines can be switched off entirely.

The numerical work here is straightforward but there are five distinct calculation types, and the exam is likely to combine two of them in a single question. Make sure you can do each on its own before you try them combined: power before/after consolidation, the non-linear power curve, consolidation ratio and host count, the PUE multiplier, and annual energy from continuous power.

Topic 01

Virtualisation fundamentals and server sprawl

What the problem was before virtualisation existed, and why it was so wasteful.

Before virtualisation, the enterprise standard was one application per physical server. The reason was isolation: if two applications share a machine and one crashes it or hogs the CPU, the other suffers. Giving each application its own hardware guaranteed safety, and for a long time that was worth the cost.

The cost turned out to be enormous. Applications rarely need a whole server, so this practice produced server sprawl — racks of machines running at 5% to 15% average CPU utilisation, drawing large base electrical power 24 hours a day to do very little.

Key idea — the virtualisation promise

Virtualisation introduces a software abstraction layer between the hardware and the operating systems. By running multiple Virtual Machines (VMs) on a single physical host, hardware resources — CPU, RAM, storage, NICs — are pooled and dynamically shared, transforming idle capacity into active compute. The isolation that justified one-app-per-server is preserved, but it now happens in software rather than by owning separate metal.

The four utilisation figures from Class 12

10–15% — typical legacy physical server utilisation.
65–80% — target utilisation for a well-consolidated virtualised host cluster.
50–70% — average reduction in physical server hardware footprint after virtualisation.
3:1 to 15:1 — typical VM-to-physical-host consolidation ratios in enterprise environments (10:1 is the figure the faculty used as "typical").

The bare-metal trap (legacy)The virtualised paradigm (modern)
1 application = 1 physical serverN applications isolated safely on 1 physical host
Power consumed primarily by idle baseline overheadPower consumption scales proportionally with actual work
High capital cost (CapEx) and floor space consumptionDrastic reduction in power, cooling and rack footprint
Complex disaster recovery, slow provisioning (weeks)Rapid VM provisioning (minutes), live migration capability
Topic 02

Hypervisors — Type 1 vs Type 2

A comparison table the faculty presented in full. Expect a direct question on it.

The hypervisor — also called the Virtual Machine Monitor or VMM — is the core software engine that manages hardware resources and isolates VMs from one another. Where it sits in the software stack determines its efficiency, and that architectural placement is the entire basis of the Type 1 / Type 2 distinction.

Picture two stacks. In Type 1, the hypervisor sits directly on the hardware, and the guest operating systems sit on the hypervisor. In Type 2, there is a full host operating system on the hardware first, the hypervisor runs as an application on top of that, and the guest operating systems sit on the hypervisor. Type 2 therefore has one extra complete OS in the path between every guest and the physical CPU.

FeatureType 1 (Bare-Metal)Type 2 (Hosted)
ArchitectureRuns directly on bare-metal hardwareRuns on top of a host operating system
Performance overheadNear-zero (~1–3%)Moderate to high (~10–20%)
Energy efficiencyOptimal — full control of hardware CPU statesSuboptimal — wasted OS overhead layer
Security isolationHigh — thin attack surfaceLower — vulnerable to host OS exploits
Typical examplesVMware ESXi, KVM, Microsoft Hyper-V, XenOracle VirtualBox, VMware Workstation
Target deploymentEnterprise data centres & cloud infrastructureDeveloper workstations, testing, client desktops
The Green IT rule for virtualisation architecture

Always deploy Type 1 (bare-metal) hypervisors in enterprise environments. The faculty gave three specific reasons, and the third is the one most students miss: Type 2 hypervisors (1) duplicate OS overhead, (2) waste CPU cycles on host system kernel calls, and (3) prevent direct CPU low-power state adjustments (C-states / P-states), creating unnecessary thermal and power overhead. That third point is why this is a green computing question and not just a performance one.

Watch out — the C-states / P-states point

If asked why Type 2 is energy-inefficient, "it is slower" is a weak answer. The specific mechanism is that the host OS sits between the hypervisor and the hardware, so the hypervisor cannot directly manage the CPU's low-power states. C-states are idle states (how deeply the core sleeps when doing nothing) and P-states are performance states (voltage and frequency scaling under load). Losing direct control of those means the CPU cannot drop into its most efficient states even when the workload would allow it.

▶ What is a Hypervisor? Why it helps: the Type 1 / Type 2 difference is fundamentally a picture of where a layer sits in a stack. Watching someone draw the two stacks side by side fixes it far better than reading the comparison table, and the table then becomes easy to reconstruct.

Topic 03

Server consolidation and the power curve

The single most important idea in Class 12. Everything numerical follows from it.

Here is the fact that makes virtualisation a green computing topic rather than merely an operations one: server power draw is not linear. If you halve a server's workload, its power consumption does not halve. It barely moves.

The idle power fact

An idle physical server consumes roughly 50% to 70% of its maximum power draw. That baseline is paid continuously, regardless of utilisation.

The consequence is the whole argument for consolidation. A server at 10% utilisation is not using 10% of its energy budget — it is using perhaps 60%. So ten servers at 10% load consume roughly six times more power than one server at 100% load doing the same total work. The waste is not in the computing; it is in the existing.

Since power scales so weakly with load, the only way to make a real saving is to eliminate physical machines entirely — not to run them more gently. This is why the goal of consolidation is decommissioning hosts, and why Dynamic Power Management (below) puts idle hosts fully to sleep rather than just idling them.

The faculty's three-state worked example

StateConfigurationPowerResult
Unconsolidated sprawl 10 physical servers, each running 1 light workload at 10% load 10 × 140 W = 1,400 W Extremely wasteful — 90% of the electricity powers idle silicon
Static consolidation Workloads combined onto 2 active hosts at 50% load; 8 decommissioned 2 × 180 W = 360 W 74% power reduction versus the unconsolidated baseline
Dynamic (DPM) Live migration shifts VMs by load; off-peak = 1 host at 70%, others in deep ACPI sleep 200 W off-peak Up to 85% off-peak savings while fully maintaining SLA guarantees
Watch out — read the power figures carefully

Notice that the consolidated hosts draw more per machine (180 W at 50% load versus 140 W at 10% load). That is the non-linear curve at work: a busier server does use more power. The saving comes entirely from there being two machines instead of ten, not from each machine using less. If a question tries to catch you by noting that the surviving hosts draw more, this is the answer.

The linear-interpolation formula for power at a given load

Several problems ask for a server's power draw at some utilisation. The faculty's convention treats the dynamic portion as linear above the idle baseline:

Power at a given CPU load
\[ P = P_{\text{idle}} + \text{Load}\% \times \left( P_{\max} - P_{\text{idle}} \right) \]

The bracketed term \( P_{\max} - P_{\text{idle}} \) is the dynamic power range — the only part of the budget that responds to workload at all.

Topic 04

Live migration and dynamic resource management

Three technologies with three distinct jobs. Do not blur them together.

Virtualisation is not static. Once workloads are decoupled from specific hardware, they can be moved while running — and that capability is what turns consolidation from a one-off exercise into a continuous optimisation.

  • Live VM Migration (VMware vMotion, KVM Live Migration) — transfers a running VM's memory state, CPU execution context and network bindings across hosts over dedicated network links, without dropping client connections. This is the enabling primitive; the other two are built on it.
  • Dynamic Resource Scheduler (DRS) — continuously monitors CPU and RAM demand across a host cluster and migrates VMs to eliminate hot spots and maintain application performance SLAs. Its objective is performance.
  • Distributed Power Management (DPM) — when cluster demand drops, say at night, DPM consolidates VMs onto a minimal subset of hosts and uses IPMI / iLO to place the idle hosts into deep standby (S5 / Wake-on-LAN). When demand spikes, hosts wake automatically. Its objective is energy.
Watch out — the live migration energy trade-off

The faculty flagged this explicitly and it is a good analytical question. Live migration itself consumes network bandwidth and temporary CPU overhead on both the source and the destination host during state transfer. Migrating VMs too frequently can produce an overall energy net-loss — you spend more moving workloads around than you save by powering hosts down. The fix named in the lecture is that DRS and DPM algorithms must enforce threshold hysteresis before triggering migrations: the load must cross a boundary by a meaningful margin, and stay there, before a move is authorised. Otherwise the cluster oscillates.

The distinction to state cleanly

DRS optimises for performance — it moves VMs away from congested hosts. DPM optimises for power — it moves VMs together so hosts can be switched off. They pull in opposite directions, which is why they run as a coordinated pair with thresholds rather than independently.

Topic 05

The Bangladesh context

A locally specific benefit that has nothing to do with electricity bills.

In Bangladesh, virtualisation serves a dual purpose: besides cutting long-term operational costs, it directly mitigates local infrastructure challenges — generator fuel expense and UPS battery wear.

  • Prolonging UPS runtime. This is the distinctive local point. During grid load-shedding, reducing the server load extends UPS battery autonomy. The faculty's formulation: halving IT power consumption through VM consolidation effectively doubles the backup runtime available on battery banks. That is a survival benefit, not just a cost benefit.
  • Bank compliance and private cloud. Bangladesh Bank regulatory circulars require strict isolation and high availability for core banking software (CBS). Hypervisor HA clusters let local financial institutions achieve that compliance without duplicate hardware sprawl.
  • Legacy application support. Virtualisation encapsulates an old 32-bit OS inside a VM, letting legacy software run on efficient modern high-density hardware — which removes the need to keep power-hungry legacy physical servers alive purely to host one application.
Practice A

Numerical practice — worked line by line

These extend the faculty's own five math-practice cards. All five calculation types appear here.

Question 1 · easy · warm-up

An enterprise has 80 physical servers drawing an average of 150 W each. After virtualisation, the workloads run on 8 hosts drawing 250 W each. (a) Total power saved in kW? (b) Percentage reduction?

Show worked solution

  1. \( P_{\text{orig}} = 80 \times 150 = 12{,}000\ \text{W} \)

    Count × per-unit power gives the fleet's total draw before consolidation.

  2. \( P_{\text{new}} = 8 \times 250 = 2{,}000\ \text{W} \)

    Same pattern after consolidation. Note the per-host figure rose from 150 W to 250 W — the surviving hosts work harder, which is the non-linear power curve in action.

  3. \( \Delta P = 12{,}000 - 2{,}000 = 10{,}000\ \text{W} \)

    Difference of the two totals is the saving. Both are in watts so no conversion is needed yet.

  4. \( \Delta P = 10\ \text{kW} \)

    Convert W to kW (÷1,000), as the question asks for kW.

  5. \( \dfrac{10{,}000}{12{,}000} \times 100\% = 83.3\% \)

    Saving as a percentage of the original — always divide by the before figure, not the after.

Answer

(a) 10 kW saved · (b) 83.3% reduction.

Point worth adding for marks: this is the direct electrical reduction only. The cooling savings that follow are not counted here — and via the PUE multiplier they add roughly another 50% on top in a typical facility. Sanity check: 72 of 80 servers were removed (90%), and the saving is 83%, slightly less than 90% because the surviving hosts each draw more. That relationship is the expected shape of the answer.

Question 2 · easy · warm-up

A server has a maximum load power of 300 W and an idle power of 180 W (60% of max). Assuming power rises linearly with CPU load above idle, what is its draw at 70% CPU load? What is the dynamic power range?

Show worked solution

  1. \( P_{\max} = 300\ \text{W},\quad P_{\text{idle}} = 180\ \text{W} \)

    The two endpoints of the power curve. Everything between them is interpolated.

  2. \( P = P_{\text{idle}} + \text{Load}\% \times (P_{\max} - P_{\text{idle}}) \)

    The linear interpolation formula. The idle power is paid unconditionally; only the range above it responds to load.

  3. \( P_{\max} - P_{\text{idle}} = 300 - 180 = 120\ \text{W} \)

    Compute the dynamic power range first — this is the portion of the budget that workload can actually influence.

  4. \( P = 180 + 0.70 \times 120 \)

    Substitute, converting 70% to the decimal 0.70 so it can multiply.

  5. \( P = 180 + 84 = 264\ \text{W} \)

    Multiply then add. The result must lie between 180 W and 300 W — it does, which is the check.

Answer

264 W at 70% load. The dynamic power range is only 120 W.

The interpretation is the important half: 180 W is drawn continuously regardless of utilisation. So going from 0% to 70% CPU load — a very large change in useful work — raises power by only 84 W, or 47%. This is precisely why running servers "more gently" saves almost nothing and why the only real lever is switching machines off. Note also that a server at 0% load still draws 60% of peak, which is where the "10 servers at 10% load waste 90% of their energy" claim comes from.

Question 3 · medium · core

A data centre consolidates 120 physical workloads into a cluster with a consolidation ratio of 12:1. (a) How many physical hosts are needed? (b) How many servers are decommissioned? (c) If the ratio were only 8:1, how many additional hosts would be required?

Show worked solution

  1. \( V = 120\ \text{workloads},\quad R = 12 \)

    Total VMs and the consolidation ratio. "12:1" means twelve VMs per physical host.

  2. \( H = \dfrac{V}{R} = \dfrac{120}{12} = 10\ \text{hosts} \)

    Hosts = total VMs ÷ ratio. Check it divides cleanly — if it did not, you would round up, since a partial host cannot exist.

  3. \( D = V - H = 120 - 10 = 110\ \text{servers} \)

    Decommissioned = original count − new host count. This assumes each original workload occupied one physical server, which is the pre-virtualisation "one app per server" model.

  4. \( H' = \dfrac{120}{8} = 15\ \text{hosts} \)

    Same division with the lower ratio. A lower ratio packs fewer VMs per host, so more hosts are needed.

  5. \( H' - H = 15 - 10 = 5\ \text{additional hosts} \)

    Difference of the two host counts answers the comparative part.

Answer

(a) 10 hosts · (b) 110 servers decommissioned · (c) 5 additional hosts at 8:1.

Both ratios sit inside the lecture's stated enterprise range of 3:1 to 15:1, so both are realistic. Add for marks: decommissioning 110 physical units cuts far more than electricity — it reduces floor space, switch port consumption and maintenance cost, and it defers the embodied carbon of future replacements for all 110 machines. Sanity check: doubling the ratio should roughly halve the host count, and 12:1 versus 8:1 (a factor of 1.5) gives 10 versus 15 (also a factor of 1.5), which is consistent.

Question 4 · medium · core

Decommissioning 20 idle servers saves 3 kW of continuous IT load. The data centre has a PUE of 1.5. (a) What is the total facility power reduction including cooling? (b) Over a year at $0.13/kWh, what does that save? (c) Explain why the facility saving exceeds the IT saving.

Show worked solution

  1. \( \Delta P_{\text{IT}} = 3\ \text{kW},\quad \text{PUE} = 1.5 \)

    The IT-layer saving and the facility's efficiency ratio.

  2. \( P_{\text{facility}} = P_{\text{IT}} \times \text{PUE} \)

    Rearranged PUE definition (PUE = total ÷ IT). It applies to a change in load just as it does to a total, because the relationship is proportional.

  3. \( \Delta P_{\text{facility}} = 3 \times 1.5 = 4.5\ \text{kW} \)

    Multiply. The result must exceed the IT figure since PUE > 1 — that is the check.

  4. \( E = 4.5 \times 8{,}760 = 39{,}420\ \text{kWh/yr} \)

    Energy = power × time, with 8,760 hours for continuous annual operation.

  5. \( C = 39{,}420 \times \$0.13 = \$5{,}124.60 \)

    Energy × tariff = cost. kWh × $/kWh leaves dollars.

Answer

(a) 4.5 kW total facility reduction · (b) ≈ $5,125/year.

(c) The explanation, which is the conceptual half: every watt consumed by IT equipment becomes heat, and that heat must be removed by the cooling system, which itself draws power. A PUE of 1.5 means the facility draws 1.5 W for every 1 W reaching IT. So eliminating 1 W of IT load eliminates that watt and the 0.5 W of cooling and distribution overhead it was generating. Every watt saved at the IT layer is multiplied by the PUE.

This is the strategic point of the whole class: IT-layer interventions are inherently more valuable than facility-layer ones, because facility improvements reduce only the multiplier while IT improvements reduce the base and get the multiplier applied to the saving.

Question 5 · medium · core

A virtualised cluster saves 15 kW of continuous power. (a) How many kWh are saved over a full year? (b) At $0.10/kWh, what is the annual monetary saving? (c) At a grid intensity of 0.6 kg CO₂e/kWh, how many tonnes of CO₂e are avoided?

Show worked solution

  1. \( P = 15\ \text{kW},\quad t = 8{,}760\ \text{h} \)

    Continuous power and the hours in a year (365 × 24). Any "continuous" or "24/7" problem uses 8,760.

  2. \( E = P \times t = 15 \times 8{,}760 = 131{,}400\ \text{kWh} \)

    Energy = power × time. Units: kW × h = kWh, which is what was asked for.

  3. \( C = 131{,}400 \times \$0.10 = \$13{,}140 \)

    Energy × tariff. kWh cancels, leaving dollars.

  4. \( m = 131{,}400 \times 0.6 = 78{,}840\ \text{kg CO}_2\text{e} \)

    Energy × grid carbon intensity converts electricity into emissions. Units: kWh × kg/kWh = kg.

  5. \( m = \dfrac{78{,}840}{1{,}000} = 78.8\ \text{tonnes} \)

    Convert kg to metric tonnes (÷1,000) — the reporting convention for corporate carbon disclosure.

Answer

(a) 131,400 kWh/year · (b) $13,140/year · (c) ≈ 78.8 tonnes CO₂e/year.

The faculty's own note on this problem: a simple consolidation initiative generating $13,140 in annual utility savings is the kind of figure that gets a project approved. The carbon figure is what goes into Scope 2 reporting. Sanity check: 15 kW is roughly the draw of 100 idle legacy servers, and 131,400 kWh is about the annual consumption of 30 average households — plausible for a mid-sized consolidation.

Question 6 · hard · stretch

A Dhaka company runs 60 legacy servers, each drawing 145 W at their typical 12% utilisation. They virtualise at a 10:1 ratio onto new hosts with \(P_{\max}\) = 400 W and \(P_{\text{idle}}\) = 240 W, running at 70% utilisation. Facility PUE is 1.6, electricity is $0.14/kWh, and the six new hosts cost $54,000.

(a) IT power before and after. (b) Facility power saving. (c) Annual money saved. (d) Simple payback period. (e) Their UPS bank supported 20 minutes of runtime at the old load — estimate the new runtime and explain why this matters in Dhaka.

Show worked solution

  1. \( P_{\text{IT,before}} = 60 \times 145 = 8{,}700\ \text{W} = 8.7\ \text{kW} \)

    Count × per-unit power. The 12% utilisation is given as context — the 145 W already accounts for it, so do not apply the load formula again here.

  2. \( H = \dfrac{60}{10} = 6\ \text{hosts} \)

    Workloads ÷ consolidation ratio gives the new host count, consistent with the six hosts costed in the problem.

  3. \( P_{\text{host}} = 240 + 0.70 \times (400 - 240) \)

    Linear interpolation formula from Topic 03. The new hosts run at a stated utilisation, so their draw must be computed rather than assumed.

  4. \( = 240 + 0.70 \times 160 = 240 + 112 = 352\ \text{W} \)

    Dynamic range is 160 W; 70% of it is 112 W, added to the 240 W idle baseline.

  5. \( P_{\text{IT,after}} = 6 \times 352 = 2{,}112\ \text{W} = 2.112\ \text{kW} \)

    Per-host draw × host count gives the new IT total.

  6. \( \Delta P_{\text{IT}} = 8.7 - 2.112 = 6.588\ \text{kW} \)

    Difference of before and after at the IT layer.

  7. \( \Delta P_{\text{facility}} = 6.588 \times 1.6 = 10.54\ \text{kW} \)

    Apply the PUE multiplier — each IT watt removed also removes its share of cooling and distribution overhead.

  8. \( E = 10.54 \times 8{,}760 = 92{,}331\ \text{kWh/yr} \)

    Energy = power × time over a full continuous year.

  9. \( C = 92{,}331 \times \$0.14 = \$12{,}926/\text{yr} \)

    Energy × tariff = annual saving.

  10. \( \text{Payback} = \dfrac{54{,}000}{12{,}926} \approx 4.2\ \text{years} \)

    Simple payback = CapEx ÷ annual saving. Units: $ ÷ ($/yr) = yr.

  11. \( t_{\text{new}} \approx 20 \times \dfrac{8.7}{2.112} \approx 82\ \text{min} \)

    UPS runtime is approximately inversely proportional to load — halve the draw and the battery lasts roughly twice as long. Scale the old runtime by the ratio of old load to new load.

Answer

(a) 8.7 kW → 2.112 kW IT · (b) ≈ 10.54 kW facility saving · (c) ≈ $12,926/year · (d) ≈ 4.2 years payback · (e) UPS runtime rises from 20 min to roughly 80 minutes.

Why (e) matters in Dhaka, which is the analytical half: the lecture's own framing is that halving IT power through consolidation effectively doubles UPS backup runtime. Here the load falls by more than a factor of four, so runtime rises correspondingly. During grid load-shedding, the lower discharge rate gives diesel generators enough time to start and stabilise without dropping the load, and it reduces battery wear from deep discharge cycles. For a Motijheel enterprise facing frequent 30-minute power cuts, moving from 20 minutes to 80 minutes of autonomy is the difference between riding out an outage and losing service — a resilience benefit that does not appear anywhere in the payback calculation.

A caveat worth stating: the inverse-proportionality used in step 11 is an approximation. Real batteries deliver less total energy at higher discharge rates (the Peukert effect), so the actual improvement is usually somewhat better than the simple ratio suggests. Note it as an estimate and you protect the mark.

Sanity check on the payback: 4.2 years is longer than the 2-year figure the lecture calls "excellent", which is realistic — this project buys hardware, whereas software-only initiatives like power management policies pay back much faster. It still sits inside a normal 5-year refresh cycle, so it is a defensible investment.

Practice B

Analytical questions

Question 7 · short answer

Why does a physical server drawing 200 W at peak still consume around 120 W when doing zero active processing? Explain the implication for green computing strategy.

Show model answer
What this tests & where it comes from This is the faculty's own opening discussion question from Section 1, which makes it a strong exam candidate. It tests Topic 03 (the power curve). The examiner wants both halves: the mechanism (why the baseline exists) and the strategic consequence (what you should therefore do about it).

The mechanism. A server's power consumption is dominated by a fixed baseline that is paid whenever the machine is powered on, independent of workload. That baseline covers the CPU maintaining its operating voltage and clock domains, RAM refresh cycles (DRAM must be continuously refreshed to retain data whether or not it is being read), spinning disks or idling SSD controllers, network interface cards remaining link-active, cooling fans, and power-supply conversion losses which themselves are worst at low load. The lecture's figure is that an idle server draws 50–70% of its maximum — here 120 W out of 200 W is exactly 60%.

Only the remainder — the dynamic power range, 80 W in this example — actually responds to workload. So the relationship between useful work and power is deeply non-linear: going from zero to full utilisation only raises consumption by 67%, while increasing useful output infinitely.

The strategic implication. Because power scales so weakly with load, running servers more gently saves almost nothing. A fleet at 10–15% utilisation — the legacy enterprise norm — is spending roughly 90% of its electricity on idle silicon. Reducing that utilisation further would barely change the bill.

The only effective intervention is therefore to eliminate physical machines entirely. That is precisely what consolidation does: pack workloads onto fewer hosts, accept that those hosts will each draw more power because they are busier, and decommission the rest. The lecture's worked example makes the arithmetic plain — ten hosts at 140 W is 1,400 W, while two busier hosts at 180 W is 360 W, a 74% reduction even though every surviving machine uses more power than before.

It also explains why Distributed Power Management puts idle hosts into deep ACPI sleep (S5) rather than merely leaving them idle — an idle host is nearly as expensive as a busy one, so only full shutdown captures the saving. And it explains the multiplier effect: since every eliminated IT watt also eliminates its cooling overhead, the facility saving is the IT saving times the PUE.

Question 8 · short answer

Compare Type 1 and Type 2 hypervisors, and justify the Green IT rule that Type 1 should always be used in enterprise environments.

Show model answer
What this tests & where it comes from Topic 02, straight from the faculty's comparison table. The word "justify" means the examiner wants the energy reasoning, not just the table reproduced — and the distinctive point they taught is the C-states / P-states one. Reproduce the table quickly, then spend the answer on the mechanism.

The architectural difference. A Type 1 (bare-metal) hypervisor runs directly on the hardware, with guest operating systems above it. A Type 2 (hosted) hypervisor runs as an application on top of a full host operating system, so there is an entire extra OS in the path between every guest and the physical CPU.

The measurable consequences the lecture gives: performance overhead of ~1–3% for Type 1 against ~10–20% for Type 2; high security isolation with a thin attack surface for Type 1 against lower isolation and exposure to host OS exploits for Type 2. Typical Type 1 products are VMware ESXi, KVM, Microsoft Hyper-V and Xen; typical Type 2 products are Oracle VirtualBox and VMware Workstation, and their target deployment is developer workstations and testing rather than data centres.

The energy justification — three distinct mechanisms, per the lecture:

  • Duplicated OS overhead. The host operating system consumes CPU, memory and I/O resources purely to exist, and none of that work serves any guest workload.
  • Wasted cycles on host kernel calls. Guest I/O and privileged operations must traverse the host OS kernel rather than reaching hardware directly, spending CPU cycles on translation.
  • Loss of direct CPU power-state control. This is the decisive one for green computing. A Type 1 hypervisor manages the CPU's C-states (idle states — how deeply a core sleeps when unused) and P-states (performance states — voltage and frequency scaling under load) directly. A Type 2 hypervisor cannot, because the host OS owns that relationship. The result is that cores cannot enter their most efficient states even when the workload would permit it, producing unnecessary thermal and power overhead.

Why this compounds at scale. A 10–20% performance overhead means more physical hosts are needed for the same workload, which raises both operational power and the embodied carbon of the additional hardware. Combined with the lost power-state management, the penalty is paid on every host, continuously, and is then multiplied by the facility PUE. In a single-workstation context the difference is negligible, which is why Type 2 remains appropriate for development and testing — but in an enterprise cluster it is a structural inefficiency, hence the rule.

Question 9 · short answer

Distinguish between live migration, DRS and DPM. Explain the energy trade-off inherent in live migration and how it is managed.

Show model answer
What this tests & where it comes from Topic 04. Three terms that sit together and are easily blurred. The examiner wants clean separation — and the trade-off question is the faculty's own "watch out", which means they consider it the non-obvious part.

Live VM Migration (VMware vMotion, KVM Live Migration) is the underlying capability: transferring a running VM's memory state, CPU execution context and network bindings from one physical host to another over dedicated network links, without dropping client connections. It is a mechanism, not a policy — it moves a VM when told to.

DRS (Dynamic Resource Scheduler) is a performance policy built on that mechanism. It continuously monitors CPU and RAM demand across a host cluster and migrates VMs to eliminate hot spots and maintain application performance SLAs. Its instinct is to spread workloads out.

DPM (Distributed Power Management) is an energy policy on the same mechanism. When cluster demand drops — typically overnight — DPM consolidates VMs onto a minimal subset of hosts and uses IPMI / iLO to place the now-idle hosts into deep standby (S5 / Wake-on-LAN), waking them automatically when demand rises. Its instinct is to pack workloads together.

The key relationship: DRS and DPM optimise for opposing objectives on the same cluster, which is why they run as a coordinated pair rather than independently. DPM is only able to power hosts down within whatever headroom DRS's SLA constraints allow.

The energy trade-off in live migration. Migration is not free. Transferring a VM's memory state consumes network bandwidth and imposes temporary CPU overhead on both the source and the destination host. Each migration therefore has an energy cost, paid up front, against a saving that accrues only while the host stays powered down.

If migrations are triggered too readily, the cluster can end up in an overall energy net-loss — continually shuffling workloads and waking and sleeping hosts, spending more on movement than it recovers. The pathological case is oscillation: load crosses a threshold, DPM consolidates and sleeps a host, load rises slightly, the host wakes, load falls again, and the cycle repeats.

How it is managed: DRS and DPM algorithms enforce threshold hysteresis before triggering migrations. Load must cross a boundary by a meaningful margin and remain there for a sustained period before a move is authorised, and the thresholds for consolidating and for expanding are deliberately set apart so the two do not trip against each other. This trades a little theoretical efficiency for stability, which nets out positive.

Question 10 · long answer

A local enterprise in Motijheel suffers frequent 30-minute power cuts and its UPS battery bank is degrading. Explain how virtualisation improves their emergency resilience, and set out what you would recommend.

Show model answer
What this tests & where it comes from The faculty's Dhaka data centre scenario from Section 7. It tests whether you can connect Topic 03 (the power curve) to Topic 05 (the Bangladesh context) — that is, whether you understand that consolidation buys resilience, not only cost savings. Note that the question says "emergency survival", so the electricity bill is the secondary argument here, not the primary one.

The mechanism. UPS runtime is governed by battery capacity against discharge rate. Reduce the load and the same battery bank sustains it for proportionally longer. The lecture's formulation is direct: halving IT power consumption through VM consolidation effectively doubles the backup runtime available on battery banks.

Virtualisation reduces that load substantially because of the non-linear power curve (Topic 03). Legacy servers at 10–15% utilisation each draw 50–70% of their peak power while doing almost nothing. Consolidating those workloads onto a small number of well-utilised hosts and decommissioning the rest removes their idle baselines entirely. The faculty's answer to this scenario puts it as consolidating onto roughly 30% of the host fleet, which significantly drops overall rack draw.

Why this is decisive during load-shedding. The lower discharge rate extends UPS autonomy, which gives the diesel generators sufficient time to start and stabilise without dropping the load. A generator start-and-transfer sequence has to complete inside the UPS window; if the batteries are degraded and the load is high, that window may be shorter than the transfer takes, and the site goes dark despite having a generator. Extending runtime turns a marginal situation into a comfortable one.

There is a second-order benefit worth stating: a lower discharge rate means shallower discharge cycles, which reduces battery wear and extends the life of the bank. Since the bank is already degrading, consolidation slows the degradation as well as compensating for it.

Recommendations, in order:

  1. Audit current utilisation across the physical fleet. If it sits in the typical 10–15% legacy band, the consolidation opportunity is large and should be quantified before any battery spend is committed.
  2. Consolidate onto Type 1 (bare-metal) hypervisors — ESXi, KVM or Hyper-V — targeting the 65–80% utilisation band, at a consolidation ratio within the realistic 3:1 to 15:1 range. Type 2 would be wrong here for the reasons in Topic 02, particularly the loss of CPU power-state control.
  3. Physically decommission the surplus hosts. Powering them off is not enough — they must leave the rack, or they will be quietly re-energised.
  4. Enable DPM so off-peak demand consolidates further and idle hosts enter deep standby, with threshold hysteresis configured to prevent migration oscillation.
  5. Then reassess the UPS. The bank may still need replacement, but it should be sized against the new, lower load — which may well mean a smaller and cheaper bank than a like-for-like replacement.
  6. Use hypervisor HA clustering for availability. This matters if the enterprise has any Bangladesh Bank compliance exposure, since BB circulars require strict isolation and high availability for core banking software, and HA clusters deliver that without duplicate hardware sprawl.

The framing to close on. The financial case (lower bills, deferred hardware) and the resilience case (longer autonomy, less battery wear) point the same way, but in a Motijheel context with frequent cuts, resilience is the argument that should lead. Consolidation is being proposed as an availability measure that happens to also cut cost.

Question 11 · long answer

A government ministry depends on an old 32-bit legacy tax accounting application that cannot run directly on modern 64-bit server hardware. The vendor no longer exists. Explain how virtualisation resolves this sustainably, and what risks remain.

Show model answer
What this tests & where it comes from The faculty's legacy application scenario from Section 7. It tests Topic 01 (hardware abstraction) applied to a problem that is not about power at first glance — the green benefit is indirect, and the examiner wants you to trace it. The "risks that remain" part invites you to show judgement rather than just recite the benefit.

The problem. Without virtualisation, the ministry has to keep old physical hardware alive purely because the software will not run on anything else. That means maintaining power-hungry legacy servers running at very low utilisation, sourcing spare parts for hardware long out of production, and accepting escalating failure risk on machines well past their design life.

How virtualisation resolves it. The hypervisor provides a software abstraction layer between the hardware and the operating system (Topic 01). Virtualisation encapsulates the legacy 32-bit OS inside a Virtual Machine, which presents the guest with the virtual hardware environment it expects. The application continues to believe it is running on its original platform while the VM in fact executes on modern, efficient, high-density hardware.

Why this is the sustainable answer. Several benefits chain together:

  • Eliminates the legacy physical servers and their idle baseline power — the direct energy saving, amplified by the facility PUE.
  • Avoids embodied carbon. The alternative — rewriting or replacing the application — is expensive and slow; the alternative of buying more legacy-compatible hardware is often impossible. Virtualisation avoids new procurement entirely for this workload.
  • Consolidates alongside other workloads. The legacy VM occupies a slice of a shared host rather than a whole machine, so its marginal power cost is small.
  • Improves resilience. The VM can be snapshotted, backed up as a file, and restored or migrated to different hardware — which is dramatically better disaster recovery than a single irreplaceable physical machine. The lecture contrasts legacy "complex disaster recovery, slow provisioning in weeks" with virtualised "rapid provisioning in minutes and live migration".
  • Decouples the software's lifespan from any specific hardware generation, so future hardware refreshes no longer threaten the application.

Risks that remain — and this is where the answer earns its top marks, because virtualisation solves the hardware problem and nothing else:

  • Security. An unsupported 32-bit OS receives no patches. Encapsulating it does not make it safe; it makes it portable. The VM must be network-segmented, firewalled, and access-controlled, since it is a permanently unpatched host inside the estate.
  • Compliance and data protection. A tax system holds sensitive citizen data on an OS that cannot be patched — a real exposure under any data protection regime.
  • Skills and knowledge decay. With the vendor gone, nobody can modify the application. Virtualisation removes the pressure to address that, which is a double-edged benefit: it can entrench the dependency indefinitely.
  • Performance and driver limitations. Legacy guests may not support modern paravirtualised drivers, so I/O performance can be poor and the VM may not benefit from the host's efficiency features.

Recommendation. Virtualise it — this is clearly the right immediate move, and it is both the sustainable and the pragmatic answer. But treat it explicitly as a containment measure that buys time, not a permanent solution, and pair it with a funded plan to replace or rewrite the application on a defined timeline. Otherwise the ministry has converted an urgent hardware problem into a comfortable, invisible, and permanent security problem.

Question 12 · long answer · stretch

An organisation has spent heavily on a facility retrofit that improved PUE from 1.9 to 1.3, but its servers still run at 11% average utilisation. The board asks whether further sustainability investment is worthwhile. Advise them, comparing the facility layer and the IT layer as investment targets.

Show model answer
What this tests & where it comes from This is the Class 11 → Class 12 bridge the faculty built deliberately in the opening of this lecture. It joins PUE (Class 11, Topic 04) to the power curve and consolidation (Topic 03), and asks you to reason about where the next marginal dollar should go. The examiner wants the multiplier argument.

Short answer: yes, and the remaining opportunity is larger than the one already captured.

What the retrofit achieved. Moving PUE from 1.9 to 1.3 is a substantial facility improvement — the overhead multiplier fell by roughly a third, and DCiE rose from about 53% to 77%. Every watt of IT load now costs 1.3 W of facility power instead of 1.9 W. That work was worth doing and should not be disparaged.

What it did not address. PUE is a ratio, and it measures only how efficiently power is delivered to the IT equipment. It says nothing about whether the IT equipment is doing anything useful with it. At 11% average utilisation the servers are drawing roughly 50–70% of their peak power to perform almost no work (Topic 03). The organisation has become highly efficient at delivering electricity to machines that are mostly idle. The faculty's framing applies exactly: even the greenest facility with a 1.15 PUE is inherently wasteful if its servers sit idle at 10% utilisation.

Why the IT layer is now the better investment — the multiplier argument. This is the decisive point. Facility improvements reduce the multiplier; IT improvements reduce the base, and the saving is then multiplied by the PUE on top. Concretely: eliminating 1 kW of IT load in this facility removes 1.3 kW of total facility draw. Meanwhile, further PUE improvement faces diminishing returns — going from 1.3 to 1.2 is technically much harder and more expensive than the 1.9 to 1.3 move already made, and it can only ever reclaim the shrinking overhead fraction, never the IT base itself.

The consolidation opportunity, by contrast, is barely touched. At 11% utilisation and a realistic consolidation ratio of 10:1 toward a 65–80% target, the physical fleet could plausibly shrink by 50–70% — the range the lecture gives for hardware footprint reduction after virtualisation. The faculty's worked example shows a 74% power reduction from static consolidation alone, rising toward 85% off-peak with DPM. No facility retrofit available to them can produce a saving of that magnitude.

The sequencing error to name. The organisation optimised in the wrong order. The correct sequence is reduce the IT load first, then size and optimise the facility around it. Having retrofitted first, they have now sized cooling and power infrastructure for an IT load that consolidation is about to shrink substantially — which means the plant will run at partial load, and partial-load operation is itself less efficient, so some of the PUE gain will erode. This is a version of the over-build trap from Class 11.

Recommendation to the board. Proceed with a virtualisation and consolidation programme: audit utilisation, deploy Type 1 hypervisors, consolidate toward 65–80% utilisation, physically decommission surplus hosts, and enable DRS and DPM with hysteresis thresholds. Present the case on total cost of ownership — direct electricity, multiplied by PUE, plus deferred hardware replacement, reduced floor space, fewer switch ports and lower maintenance. Expect the payback to be shorter than the facility retrofit's, because consolidation removes capital as well as consuming it. And after consolidation, revisit the facility: the plant may now be oversized, and rebalancing it is the second phase, not a competing project.

Last-minute revision — Class 12

The core fact

An idle server draws 50–70% of peak power. So running servers gently saves nothing — you must switch machines OFF.

Power at a given load

\( P = P_{\text{idle}} + \text{Load}\% \times (P_{\max}-P_{\text{idle}}) \). The bracket is the dynamic power range.

Utilisation figures

Legacy 10–15% → virtualised target 65–80%. Hardware footprint falls 50–70%. Ratios 3:1 to 15:1.

Consolidation maths

Hosts = VMs ÷ ratio (round UP). Decommissioned = original − hosts.

PUE multiplier

Facility saving = IT saving × PUE. Every IT watt removed also removes its cooling overhead. IT layer > facility layer.

Annual energy

\( E = P_{\text{kW}} \times 8{,}760 \) kWh. Cost = E × tariff. CO₂ tonnes = (E × factor) ÷ 1,000.

Type 1 (bare-metal)

Runs directly on hardware. Overhead ~1–3%. High isolation. ESXi, KVM, Hyper-V, Xen. Enterprise.

Type 2 (hosted)

Runs on a host OS. Overhead ~10–20%. Lower isolation. VirtualBox, VMware Workstation. Dev/test only.

Why Type 2 wastes energy

(1) Duplicated OS overhead (2) Wasted cycles on host kernel calls (3) Cannot control CPU C-states/P-states.

The 3-state example

10 × 140 W = 1,400 W → 2 × 180 W = 360 W (74% cut) → DPM off-peak 200 W (up to 85%).

Live migration

Moves memory state + CPU context + network bindings across hosts with zero downtime. vMotion, KVM Live Migration.

DRS vs DPM

DRS = performance — spreads VMs out, kills hot spots, holds SLAs. DPM = power — packs VMs together, sleeps hosts via IPMI/iLO.

Migration trade-off

Migration costs bandwidth + CPU on BOTH hosts. Too frequent = energy net-loss. Fix: threshold hysteresis.

Bangladesh — UPS

Halving IT power ≈ doubles UPS runtime. Buys time for gensets to stabilise during load-shedding. Less battery wear.

Bangladesh — banking

BB circulars require isolation + HA for core banking software. Hypervisor HA clusters deliver it without duplicate hardware.

Bangladesh — legacy

Encapsulate a 32-bit legacy OS in a VM → runs on modern hardware, kills the power-hungry legacy physical box.

The Class 11 bridge

PUE measures DELIVERY efficiency, not utilisation. Fix the IT load first, then the facility — the saving multiplies, not the reverse.
