CH 01

ARP & RARP

What is ARP and Why Do We Need It?

You're in class and want to pass a note to "Ali." You know Ali's name (= IP address) but need to know which seat Ali sits in (= MAC address). You shout: "Who is Ali? Raise your hand!" Everyone hears it, Ali raises hand. That's ARP.

In a network, IP address = logical address used for routing. MAC address = physical address used for actual delivery on the local network. ARP converts IP → MAC so Ethernet can deliver the frame.

The ARP Process

Step 1 — Check ARP Cache
Host A checks its local cache for a mapping of 192.168.1.2 → MAC. If found (RESOLVED state) → use it directly. If not found → proceed to broadcast.
Step 2 — Broadcast ARP Request
A sends ARP request to FF:FF:FF:FF:FF:FF (all hosts). Packet says: "Who has 192.168.1.2? Tell 192.168.1.1." The Target HW Address field = 00:00:00:00:00:00 (unknown).
Step 3 — Target Recognizes Its IP
All hosts receive the broadcast. Only Host B (192.168.1.2) says "That's me!" Everyone else ignores it.
Step 4 — Unicast ARP Reply
B sends a unicast reply only to A: "192.168.1.2 is at BB:BB:BB:BB:BB:BB." A caches this mapping (State: RESOLVED, TTL starts).
Golden Rule: ARP Request = BROADCAST  |  ARP Reply = UNICAST

ARP Cache — The Memory System

To avoid repeated broadcasts, devices cache IP→MAC mappings. Each entry has one of three states:

StateMeaningHas TTL?Has Attempt#?
R ResolvedMAC is known, mapping is valid✅ Yes — decrements over timeNo
P PendingARP request sent, waiting for replyNo✅ Yes — increments each retry
F FreeEmpty slot, available for new entryNoNo
Cache-Control Module runs periodically:
  • RESOLVED entries: TTL decremented. TTL → 0 means entry becomes FREE
  • PENDING entries: Attempt counter incremented, new ARP sent. Max attempts exceeded → FREE

Four Cases Where ARP is Used

CASE 1

Sender & receiver on same network. ARP finds receiver's MAC directly.

CASE 2

Receiver on another network. ARP finds the default router's MAC (gateway).

CASE 3

Router forwards packet. Target IP = next hop router's IP (from routing table).

CASE 4

Router delivers to final host. Target IP = destination host's IP on local network.

Proxy ARP

You ask someone: "Does Ali live here?" A neighbor (the proxy router) who knows Ali says: "Yes, send your mail to ME and I'll pass it along." You never know Ali's real address — you just trust the neighbor.

When a new subnetwork is added, hosts on the main network can't ARP across routers (routers don't forward broadcasts). The Proxy ARP router replies on behalf of the unreachable hosts using its OWN MAC address.

Host P broadcasts: "Who has 192.168.1.21?"
Proxy ARP Router sees this → knows 192.168.1.21 is behind it
Router replies: "192.168.1.21 is at [ROUTER's MAC]"  ← uses its OWN MAC!
Host P caches: 192.168.1.21 → Router's MAC
Host P sends data → Router forwards to actual host 192.168.1.21 ✓
Host P never knows a router is involved (transparent)

RARP — Reverse ARP

You know your employee ID (MAC) but forgot which desk you were assigned (IP). You broadcast: "I'm employee #12345, what desk is mine?" HR (RARP server) looks up the table and tells you.

RARP does the opposite of ARP: MAC → IP. Used by diskless workstations that know their hardware address but not their IP address.

Golden Rule: RARP Request = BROADCAST  |  RARP Reply = UNICAST (sent by RARP Server)

⭐ Key Points for Exam — ARP & RARP

  • ARP: IP → MAC (broadcast request, unicast reply)
  • RARP: MAC → IP (broadcast request, unicast reply)
  • ARP Operation: 1=Req, 2=Reply  |  RARP: 3=Req, 4=Reply
  • Ethernet type: ARP=0x0806, RARP=0x8035
  • Target HW Addr in ARP REQUEST = 00:00:00:00:00:00
  • ARP Cache states: R=Resolved, P=Pending, F=Free
  • Proxy ARP: router answers ARP using its OWN MAC on behalf of another host
  • ARP packet total = 28 bytes
CH 02

Routing Protocols

What is Routing?

Sending a package from Dhaka to London — it goes through intermediaries (post offices, airports, customs). Each stop decides the next destination. Routing is how routers make those decisions.

Intradomain Routing

Routing inside one Autonomous System (AS). Protocols: RIP (Distance Vector), OSPF (Link State)

Interdomain Routing

Routing between different AS's. Protocol: BGP (Path Vector)

Distance Vector Routing

Ask a friend for directions: "How far is the market from your place?" They say 2km. You know your friend is 1km away. So: market = 3km from you. You trust what neighbors tell you — no map needed.

Each router maintains a table of (Destination, Cost, Next Hop). Routers share their tables only with immediate neighbors periodically and when there is a change.

The Update Formula (Bellman-Ford)

If: (link cost to neighbor N) + (N's cost to destination D) < my current cost to D
→ UPDATE my cost to D, and set Next Hop = N

Example — A receives update from C (A-C link cost = 1)

Network: A-B=3, A-C=1, C-B=1, C-D=5

DestC's value+ link cost A-C (1)A's old costNew costChanged?
A1200 (no change)—
B1232 via C✅ YES
C0111 (no change)—
D56∞6 via C✅ YES
Rule: In distance vector routing, each node shares its routing table with its immediate neighbors periodically and when there is a change.

Instability Problems

Two-Node Instability (Count-to-Infinity)

Setup: X–2–A–4–B. X is reachable: A=2 (direct), B=6 (via A). X fails.

EventA's cost to XB's cost to X
X fails, A updates∞6 (stale — doesn't know yet)
A receives B's stale update (6). A thinks: 6+4=1010 via B6
B receives A's update (10). B thinks: 10+4=141014 via A
Keeps growing…↑↑
Final (RIP max=16)16 (∞)16 (∞)

Solution: Split Horizon + Poison Reverse

Split Horizon

Don't advertise a route back to the neighbor you learned it from. "B learned X from A → B does NOT advertise X to A."

Poison Reverse

Instead of silence, advertise it with cost=16 (∞). Faster convergence. "B tells A: X=16 (unreachable through me)."

Three-Node Instability

X fails. A sends update to B and C, but the packet to C gets lost. C still thinks X is reachable at cost 5 (via A). C's stale info feeds back into A, causing A→B→A loop. Three nodes perpetuate false information. Same fix: Split Horizon + Poison Reverse.

Link State Routing

Instead of asking friends for directions, you get a complete city map. Every router broadcasts its own connections to EVERYONE — then every router independently calculates the best route using the full map.

The 5-Step Process

1. Neighbor Discovery
Routers send HELLO packets. Neighbors reply → router learns who is directly connected and link costs.
2. Create Link State Packet (LSP)
Each router creates an LSP with: its own ID, list of direct neighbors + costs, Sequence Number (freshness), TTL.
3. Flood the LSP
Each router sends its LSP to ALL other routers (not just neighbors). Each router forwards received LSPs on all ports except where it arrived. Sequence# prevents loops; TTL prevents eternal circulation.
4. Build Full Topology Map
After flooding, every router has the same complete picture of the entire network.
5. Run Dijkstra
Each router independently runs Dijkstra's algorithm to find the shortest path to every other router.

Link-State Table (what each node broadcasts)

Node (sender)Sequence #TTLNeighbors (direct links + costs)
A540B:2, D:4
B8—A:2, C:3, D:1
D748A:4, B:1, E:3

Higher sequence number = more recent. If a router receives an LSP with an older sequence# than stored, it discards it.

Dijkstra's Algorithm

Finds shortest path from source to all other nodes. Always picks the minimum unvisited node next.

Algorithm:
1. Source = 0, all others = ∞
2. Pick unvisited node with smallest distance → visit it
3. For each neighbor: if (dist[current] + edge) < dist[neighbor] → UPDATE
4. Mark as visited. Repeat until all visited.

Worked Example: A-B=2, A-D=4, B-C=3, B-D=1, C-E=2, C-F=5, D-E=3, E-F=1

Orange = updated this round. Green row = visited (locked in). Shortest path A→F = 7 via A→B→D→E→F (verify: 2+1+3+1=7 ✓)

Step 2 detail: When visiting B (cost=2), neighbor D is updated from 4(via A) to 3(via B) because 2+1=3 < 4. Always check if the new path is shorter!

⭐ Key Points for Exam — Routing

  • DV: share routing table with NEIGHBORS only | LS: flood LSP to EVERYONE
  • Count-to-infinity: DV problem | Fix: Split Horizon + Poison Reverse
  • RIP: UDP port 520, max 15 hops (16=∞), 25-35s periodic update
  • RIP Timers: Periodic(25-35s), Expiration(180s), Garbage Collection(120s)
  • Dijkstra: always pick MINIMUM unvisited → update all its neighbors
  • Link State: Seq# tracks freshness, TTL prevents infinite flooding
CH 03

Congestion Control

Overview

Rush hour highway — too many cars for 4 lanes. Cars slow, some take shortcuts, creating more chaos. Eventually everyone stops. Same happens in networks when too many packets overload routers.

Open Loop (Prevention)

Policies designed before congestion happens. Stop it before it starts. Handled by sender, receiver, or router statically.

Closed Loop (Removal)

Detect congestion after it happens and take action to remove it. Uses feedback — network signals the sender to slow down.

Open-Loop Congestion Control (5 Policies)

1. Retransmission Policy

Retransmitting too quickly floods the network. TCP uses adaptive RTO (exponential backoff) — wait longer before retransmitting if no ACK. Prevents "panic retransmission" that worsens congestion.

2. Window Policy

Go-Back-N: one lost packet → retransmit many (N) packets. Selective Repeat: only the lost packet is resent → fewer redundant packets → less congestion. Using Selective Repeat is the better window policy.

3. Acknowledgment Policy

ACKs are packets too. Delayed ACKs: acknowledge multiple packets at once instead of one ACK per packet. Fewer ACK packets = less network load = helps prevent congestion.

4. Discarding Policy

When buffer fills, drop least important packets first. E.g., in audio streaming, drop low-priority audio frames. Sound quality degrades slightly but stream continues — better than dropping everything.

5. Admission Policy

Before a new flow joins, check if the network can handle it. If congested → deny new connection. Like a bouncer: "Sorry, capacity full." Used in virtual-circuit networks (ATM).

Closed-Loop Congestion Control (4 Methods)

1. Backpressure

Congested node tells its immediate upstream neighbor to slow down. That neighbor may become congested → tells its upstream neighbor. Signal propagates backward, hop by hop, to the source.

Source → I → II → III(CONGESTED) → IV → Dest
◄ backpressure propagates hop-by-hop backward
Source ← I ← II ←slow— III       (each node involved)

Works only in virtual-circuit networks. Slow to reach source. Intermediate nodes are affected.

2. Choke Packet

Congested node sends warning directly to the SOURCE, bypassing intermediate nodes.

Source → I → II → III(CONGESTED) → IV → Dest
  ↑________________|
  CHOKE PACKET (direct, Node I and II NOT warned)

3. Implicit Signaling

No explicit signal. Source guesses congestion from symptoms: Timeout (no ACK → packet dropped → congestion assumed) or 3 Duplicate ACKs (packet lost but network still working). Source reduces rate on its own. TCP uses this.

4. Explicit Signaling

Backward: Congested node sets a bit in ACK packets flowing toward source. Source sees the bit → slows down.
Forward: Congested node sets a bit in data packets going toward destination. Destination slows ACKs → source slows down.

TCP Congestion Policy

TCP uses three phases: Slow Start, Congestion Avoidance, Congestion Detection. The congestion window (cwnd) controls how many segments can be sent without acknowledgment.

Phase 1: Slow Start (Exponential Increase)

cwnd starts at 1 MSS. Doubles each round (×2). Continues until cwnd reaches ssthresh (slow-start threshold). Despite the name "slow," it grows exponentially — 1→2→4→8→16...

Phase 2: Congestion Avoidance (Additive Increase)

When cwnd = ssthresh, slow start stops. Now cwnd increases by +1 MSS per round (linear). Careful growth to avoid overloading the network.

Phase 3: Congestion Detection (Multiplicative Decrease)

Timeout (severe)

ssthresh = cwnd/2
cwnd = 1 MSS (hard reset)
→ Restart Slow Start

3 Dup ACKs (mild)

ssthresh = cwnd/2
cwnd = ssthresh (soft reset)
→ Skip to Cong. Avoidance

Full Example: cwnd=1, ssthresh=8

Actual window size = minimum(cwnd, rwnd)
rwnd = receiver-advertised window. The network (cwnd) AND the receiver (rwnd) both limit the sender.

⭐ Key Points for Exam — Congestion Control

  • Open Loop = PREVENT (before) | Closed Loop = REMOVE (after)
  • Backpressure: hop-by-hop backward, intermediate nodes warned
  • Choke Packet: directly to source, intermediate nodes NOT warned
  • Implicit: source guesses from timeout/3 dup ACKs (TCP)
  • Slow Start: cwnd ×2 per round (below ssthresh)
  • Congestion Avoidance: cwnd +1 per round (at/above ssthresh)
  • Timeout → ssthresh=cwnd/2, cwnd=1 | 3 dup ACKs → ssthresh=cwnd/2, cwnd=ssthresh

Quality of Service

The Four Flow Characteristics

CharacteristicWhat it MeansCritical forLess Important for
ReliabilityEvery packet must arrive correctlyEmail, file transfer, bankingVoIP, live video (some loss OK)
DelayTime for packet to travel source→destVoIP, video conference, gamingEmail, file download
JitterVariation in delay between packetsAudio/video (consistent timing needed)Email, FTP (doesn't matter)
BandwidthData per unit time (Mbps/Gbps)4K video, large file transferVoIP, text messaging
Jitter analogy: A bus supposed to come every 10 min. Arrives at 10, 10, 10 min → low jitter (good for real-time). Arrives at 8, 15, 3 min → high jitter (terrible for audio/video — choppy!).

Leaky Bucket Algorithm

A bucket with a hole at the bottom. Water (data) pours in at bursty rates. Water drips out at a CONSTANT rate (determined by hole size). Too much input → bucket overflows → data dropped.

Leaky Bucket

Output always constant rate. Drops packets on overflow. Does NOT reward idle time. "You can only go 60 km/h — always."

Token Bucket

Tokens accumulate during idle time → allows controlled bursting. "Save up speed credits, burst later."

Key Property: Leaky bucket shapes bursty traffic into fixed-rate traffic by averaging the data rate. It may drop packets if the bucket is full.

TCP — Three-Way Handshaking

Phase 1: Connection Establishment

Phone call: Ali: "Can you hear me?" Sara: "Yes! Can you hear me?" Ali: "Yes! Let's talk." Both sides confirm they can communicate — three messages total.
Host A (192.168.1.2)                         Server B (203.0.113.1)
         |                                               |
         |  ─── Segment 1: SYN ──────────────────────►  |
         |  SYN=1, ACK=0, seq=8000                      | [B enters SYN_RECEIVED]
         |  (no data, but CONSUMES 1 sequence number)   |
         |                                               |
         |  ◄── Segment 2: SYN+ACK ───────────────────  |
         |  SYN=1, ACK=1                                |
         |  seq=15000, ack=8001  ← "got seq 8000, want 8001 next"
         |  (consumes 1 sequence number for B's SYN)   |
         |                                               |
         |  ─── Segment 3: ACK ──────────────────────►  | Connection
         |  SYN=0, ACK=1                                | ESTABLISHED ✓
         |  seq=8001, ack=15001 ← "got seq 15000, want 15001 next"
         |  (pure ACK — consumes NO sequence number)   |

Sequence Number Rules

ACK formula: ack = (received seq) + 1 for SYN/FIN  |  ack = (received seq) + (bytes received) for DATA

Phase 2: Data Transfer

After handshake: A's next seq=8001, B's next seq=15001. A sends 2000 bytes (two segments of 1000). B sends 2000 bytes (one segment).

A ─── DATA (1000 bytes): seq=8001, ack=15001 ─────────────────► B
A ─── DATA (1000 bytes): seq=9001, ack=15001 ─────────────────► B
A ◄── DATA (2000 bytes)+ACK: seq=15001, ack=10001 ─────────── B
       (B says: got bytes 8001-10000, next expected=10001)
A ─── ACK: seq=10001, ack=17001 ──────────────────────────────► B
       (A says: got bytes 15001-17000, next expected=17001)
PSH flag: When set, receiver must deliver data to application immediately — don't buffer. Used for interactive apps. ACKs can be piggybacked inside data segments.

Half-Close & SYN Flooding

Half-Close

TCP allows closing ONE direction while keeping the OTHER open. Use case: sorting service — client sends all data (closes sending), server sorts and sends results back (server's direction stays open).

Client ─── FIN ──────────────────────────────────────────────► Server
           [Client stops SENDING, but still RECEIVES]
Client ◄── ACK ──────────────────────────────────────────────── Server
           [Data still flows from Server to Client]
Client ◄── sorted results ──────────────────────────────────── Server
Client ─── ACKs ────────────────────────────────────────────► Server
Client ◄── FIN ──────────────────────────────────────────────── Server
Client ─── ACK ──────────────────────────────────────────────► Server  DONE ✓

SYN Flooding Attack & SYN Cookie Defense

SYN Flooding Attack

  1. Attacker sends 1000s of SYNs with fake source IPs
  2. Server allocates resources for each, sends SYN+ACK to fake IPs
  3. No real ACK ever comes back
  4. Server's connection table fills up
  5. Legitimate users denied → DoS attack ✓

SYN Cookie Defense

  1. Server does NOT allocate resources on SYN
  2. Encodes connection info as a cryptographic cookie in SYN+ACK's seq#
  3. Only when real ACK arrives with cookie+1 → server allocates resources
  4. Spoofed SYNs never complete → no resources wasted ✓

⭐ Key Points for Exam — TCP

  • Three-way handshake: SYN → SYN+ACK → ACK
  • SYN, SYN+ACK, FIN: each consumes 1 sequence number
  • Pure ACK with no data: consumes 0 sequence numbers
  • DATA: consumes N sequence numbers (N = bytes sent)
  • ack number = (last received byte seq) + 1 for SYN/FIN; last seq + bytes for DATA
  • Termination: FIN+ACK → FIN+ACK → ACK
  • Half-close: one direction closed, other still open (e.g., sorting service)
  • SYN flooding: fake SYNs exhaust resources | Fix: SYN Cookies

SYN Flooding Attack

  1. Send 1000s of SYNs with fake source IPs
  2. Server allocates memory, timers for each

  4. Server's connection table fills completely
  5. Legitimate users denied = DoS attack

SYN Cookie Defense

  1. Server does NOT allocate resources on SYN
  2. Encodes info as cryptographic hash ("cookie") in SYN+ACK's seq#

  4. Spoofed SYNs can't complete → no waste ✓

T14

[Half-Close] Explain the TCP Half-Close mechanism. Why is it needed? Give a real-world example (sorting service) and draw the complete sequence of segments showing which directions are open/closed at each stage.

▶ View Solution›

What is half-close: TCP allows ONE side to close its SENDING direction while keeping its RECEIVING direction open. This is called a half-close.

Why needed (sorting service): Server needs ALL records from client before sorting can begin. If client closes the full connection → server can't send sorted results back. Solution: client closes only the C→S direction, keeps S→C open to receive results.

Client                                         Server
  | ─── DATA (all records to sort) ────────────► |
  | ─── FIN (close C→S direction only) ─────────► |  ← Half-close!
  | ◄── ACK ─────────────────────────────────────  |  C can still RECEIVE
  |    [Client can NO LONGER SEND]                |  [Server still CAN send]
  |    [Client can still RECEIVE]                 |  [Server sorts data...]
  | ◄── DATA (sorted results from S to C) ──────  |
  | ─── ACKs ────────────────────────────────────► |
  | ◄── FIN (S closes S→C direction) ─────────── |  Full close
  | ─── ACK ─────────────────────────────────────► |  DONE ✓
