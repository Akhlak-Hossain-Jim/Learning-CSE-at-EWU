White Box Testing Structure-based testing

1. Control Flow Graph (CFG)

A directed graph representing all paths of execution through a program.

Key Elements

Node (Basic Block): Sequence of statements with one entry and one exit. No branches inside.
Edge: Control flow transfer between nodes.
Entry Node: Start of program.
Exit Node: End of program.
Predicate Node: A node with 2+ outgoing edges (decision point — IF, WHILE, SWITCH).

Key Formulas

V(G) = E − N + 2P
V(G) = P + 1 (P = # predicate nodes)
V(G) = # independent paths

E = edges, N = nodes, P = connected components (usually 1)

CFG Example — if-else

V(G) = 5 edges − 4 nodes + 2 = 3

2. Data Flow Graph (DD Graph / Def-Use)

Tracks where variables are defined (assigned) and used (read/referenced) across nodes.

Concepts

def(v): Variable v is assigned a value (defined) at this node.
use(v): Variable v is read/used at this node.
p-use: Predicate use — variable used in a condition (affects branching).
c-use: Computational use — used in calculation.
du-pair: (def node d, use node u) where v reaches u without re-definition.
du-path: Path from def to use with no re-definition of v in between.

Coverage Criteria

All-defs: each def reaches at least one use
All-uses: each du-pair is covered
All-du-paths: every du-path is covered

DD Graph Example

Node 1: x = 5        ← def(x)
Node 2: y = x + 1   ← use(x), def(y)
Node 3: if (y > 3)  ← p-use(y)
Node 4: z = y * 2   ← c-use(y), def(z)
Node 5: print(z)    ← use(z)
DU Pairs for x:
(1,2) — x defined at 1, used at 2 ✓

DU Pairs for y:
(2,3) — p-use, (2,4) — c-use ✓

DU Pairs for z:
(4,5) ✓

3. Cyclomatic Complexity (CC)

A software metric that measures the number of linearly independent paths through a program's source code.

Three Equivalent Formulas

① V(G) = E − N + 2
② V(G) = P + 1 (P = predicate nodes)
③ V(G) = number of regions in CFG
E = number of edges in CFG
N = number of nodes in CFG
P = number of predicate (decision) nodes

Interpretation

CC ValueRisk Level
1 – 10Low — Simple, well structured
11 – 20Medium — Moderate complexity
21 – 50High — Complex, hard to test
> 50Very High — Untestable

CFG with Loop — CC Calculation

E=4 edges, N=4 nodes

V(G) = 4 − 4 + 2 = 2

Or: 1 predicate node + 1 = 2

Black Box Testing Specification-based testing

1. Decision Table Testing

A systematic way to represent complex business logic using combinations of conditions and actions.

Structure

Conditions (Inputs): Factors that affect the system behavior. Can be T/F or multi-valued.
Actions (Outputs): Results or behaviors that occur based on conditions.
Rules (Columns): Each column = one test case = a unique combination of conditions.
— (dash) = "Don't care" — condition irrelevant to action.
Max rules = 2^n (n = number of binary conditions)
Simplified table uses dashes to merge redundant rules (reduces test cases).

Example: Login System

Conditions: Valid User (VU), Valid Password (VP), Account Active (AA)

R1R2R3R4R5
Valid UserTTTTF
Valid PasswordTTFF—
Account ActiveTFTF—
✓ Login✓✗✗✗✗
⚠ Show Error—AAPWBothUser

Each column (R1–R5) is one test case.

2. Boundary Value Analysis (BVA)

Tests values at the edges of equivalence partitions, where bugs are most likely to occur.

BVC — Boundary Value Coverage

Tests exactly ON the boundary values.

For a range [a, b]: test a and b only.
BVC test points: min, max (2 per variable)

BVA — Boundary Value Analysis (3-point)

Tests ON, just-below, and just-above boundary.

For range [a, b]: test a-1, a, a+1, b-1, b, b+1
BVA test points: min-1, min, min+1, max-1, max, max+1 (6 per variable)

Equivalence Partitioning

Divide input into partitions where system behaves identically. Pick one representative from each:

Valid partition: values the system should accept
Invalid partition: values the system should reject

Visual: Age Input [18, 60]

BVC test values: 18, 60
BVA test values: 17, 18, 19, 59, 60, 61
Equivalence Partitions:
• Invalid: < 18 → test with e.g. 10
• Valid: 18–60 → test with e.g. 35
• Invalid: > 60 → test with e.g. 70
OOP Concepts Object-Oriented Programming

1. Inheritance

Mechanism where a class (child/subclass) acquires properties and behaviors of another class (parent/superclass).

Types of Inheritance

Single: Child → Parent (one parent)
Multilevel: GrandChild → Child → Parent (chain)
Hierarchical: Multiple children from one parent
Multiple: One child, multiple parents (C++ / interfaces)
Hybrid: Combination of above

Key Keywords

class Animal {
  String name;
  void eat() { ... }
}

class Dog extends Animal {
  void bark() { ... }
  // Inherits: name, eat()
  // Adds: bark()
}
super keyword accesses parent class methods/constructors.
is-a relationship: Dog is-a Animal ✓

Inheritance Hierarchy Diagram

Hierarchical (Animal→Dog/Cat) + Multilevel (Poodle→Dog→Animal)

2. Polymorphism

"Many forms" — the ability of different objects to respond to the same method call in different ways.

Compile-time (Static) — Overloading

Same method name, different parameter list. Resolved at compile time.
class Calculator {
  int add(int a, int b)
  double add(double a, double b)
  int add(int a, int b, int c)
  // Same name, diff signatures!
}

Runtime (Dynamic) — Overriding

Subclass redefines a parent method. Resolved at runtime via dynamic dispatch.
class Animal {
  void sound() { print("..."); }
}
class Dog extends Animal {
  @Override
  void sound() { print("Woof"); }
}
class Cat extends Animal {
  @Override
  void sound() { print("Meow"); }
}
// Animal a = new Dog();
// a.sound() → "Woof"

Polymorphism Diagram

Key difference: Overloading = same class, different params. Overriding = different class (parent/child), same signature.
Upcasting: Animal a = new Dog(); — always safe.

1. Singleton Pattern Creational

Ensures a class has only one instance and provides a global access point to it.

When to Use

Database connection pool
Logger / configuration manager
Thread pool, cache

Key Characteristics

Private constructor (can't use new)
Static instance variable
Static getInstance() method
Thread-safe (use synchronized/double-check locking)
class Singleton {
  private static Singleton instance;

  private Singleton() { }  // ← private!

  public static Singleton getInstance() {
    if (instance == null) {
      instance = new Singleton();
    }
    return instance;
  }
}

// Usage:
Singleton s1 = Singleton.getInstance();
Singleton s2 = Singleton.getInstance();
// s1 == s2  → TRUE (same object)

2. Adapter Pattern Structural

Converts the interface of a class into another interface that clients expect. Like a power plug adapter.

Participants

Target: Interface the client expects.
Adaptee: Existing class with incompatible interface.
Adapter: Wraps Adaptee, implements Target.
Client: Uses Target interface.
// Target interface
interface MediaPlayer {
  void play(String file);
}

// Adaptee (incompatible)
class VLCPlayer {
  void playVLC(String file) { ... }
}

// Adapter
class MediaAdapter implements MediaPlayer {
  VLCPlayer vlc = new VLCPlayer();

  public void play(String file) {
    vlc.playVLC(file);  // ← delegates
  }
}

// Client uses Target interface only
MediaPlayer mp = new MediaAdapter();
mp.play("video.mp4");  // works!

3. Bridge Pattern Structural

Separates an abstraction from its implementation so they can vary independently. Avoids "class explosion".

Problem Solved

Without Bridge: 2 shapes × 3 colors = 6 subclasses.
With Bridge: 2 + 3 = 5 classes total.

Participants

Abstraction: High-level control (Shape).
Implementation: Interface for implementations (Color).
Refined Abstraction: Extends Abstraction (Circle).
Concrete Impl: Implements Implementation (RedColor).
Key: Abstraction holds a reference to Implementation (composition, not inheritance). 
interface Color {
  String fill();
}
class Red implements Color {
  public String fill() { return "Red"; }
}
class Blue implements Color {
  public String fill() { return "Blue"; }
}

abstract class Shape {
  protected Color color;  // ← bridge!
  Shape(Color c) { this.color = c; }
  abstract void draw();
}
class Circle extends Shape {
  Circle(Color c) { super(c); }
  void draw() {
    print("Circle in " + color.fill());
  }
}

// Usage:
Shape s = new Circle(new Red());
s.draw(); // "Circle in Red"
// Add new color: just add class, no shape change!

4. Observer Pattern Behavioral

Defines a one-to-many dependency: when one object changes state, all dependents are notified automatically.

Participants

Subject (Observable): Maintains list of observers. Notifies on state change.
Observer: Interface with update() method.
ConcreteSubject: Actual source of data.
ConcreteObserver: Reacts to notifications.
Real-world examples: Event listeners in UI, stock price alerts, news feed subscriptions, pub-sub messaging. 
interface Observer {
  void update(String event);
}

class EventSource {
  List<Observer> observers = new ArrayList<>();

  void subscribe(Observer o) {
    observers.add(o);
  }
  void notifyAll(String event) {
    for (Observer o : observers)
      o.update(event);
  }
  void changeState(String newState) {
    // ... change state ...
    notifyAll(newState);  // auto-notify!
  }
}

class Logger implements Observer {
  public void update(String e) {
    print("LOG: " + e);
  }
}
class AlertSystem implements Observer {
  public void update(String e) {
    print("ALERT: " + e);
  }
}

EventSource src = new EventSource();
src.subscribe(new Logger());
src.subscribe(new AlertSystem());
src.changeState("PRICE_CHANGED");
// Both Logger + AlertSystem auto-notified!

3.   y = x * 2

▼

• N (nodes) = 7 (1, 2, 3/if-true, 4/if-false, merge, while, print)

Wait — let's be precise: N=8 nodes, E=9 edges

Formula 2 (P+1): 2 predicates (if + while) → 2+1 = 3

Design Patterns

Q7. In the Observer pattern, what is "loose coupling" and how does Observer achieve it? Give a real-world analogy.

▼
Loose Coupling: Objects interact through interfaces/abstractions rather than concrete classes, so they can change independently without breaking each other.

How Observer achieves it:
• Subject doesn't know the concrete type of its observers — it only knows they implement the Observer interface.
• Observers don't know about each other.
• You can add/remove observers at runtime without changing Subject code.

Real-world analogy: YouTube subscriptions.
• YouTube channel = Subject
• Subscribers = Observers
• When a new video is posted (state change), ALL subscribers are notified (update()).
• YouTube doesn't know what each subscriber does with the notification — they react independently.
Singleton

Q8. What problem does the Singleton pattern solve? Why must the constructor be private? What issue can arise in multi-threaded environments and how is it fixed?

▼
Problem solved: Ensures only one instance of a class is created (e.g., one DB connection, one config loader). Provides global access point.

Why private constructor: Prevents external code from calling new ClassName(), which would create multiple instances and break the pattern.

Multi-threading problem: Two threads could both pass the if (instance == null) check simultaneously and each create a new instance → two instances!

Fix — Double-Checked Locking: 
public static Singleton getInstance() {
  if (instance == null) {              // first check (no lock)
    synchronized (Singleton.class) {
      if (instance == null) {          // second check (with lock)
        instance = new Singleton();
      }
    }
  }
  return instance;
}
Also mark instance as volatile to ensure visibility across threads.

Polymorphism

SQ6. What is the output of the code below? Identify the type of polymorphism and explain why it works this way.

class Shape {
    void area() { System.out.println("Shape area"); }
}
class Circle extends Shape {
    void area() { System.out.println("Circle: πr²"); }
}
class Square extends Shape {
    void area() { System.out.println("Square: s²"); }
}

Shape s1 = new Circle();
Shape s2 = new Square();
Shape s3 = new Shape();
s1.area();
s2.area();
s3.area();
▼
Output:
"Circle: πr²"
"Square: s²"
"Shape area"

Type: Runtime polymorphism (method overriding / dynamic dispatch).

Why: All three references are declared as type Shape, but the JVM resolves which area() to call based on the actual object type at runtime — Circle, Square, or Shape. This is late binding. The compiler sees Shape; the JVM sees the real object.

Design Patterns

Singleton

SQ7. A developer writes the Singleton below. Identify two problems with this implementation and write the corrected version.

class Config {
    public static Config instance;

    public Config() { }     // loads settings

    public static Config get() {
        if (instance == null)
            instance = new Config();
        return instance;
    }
}
▼
Problem 1: Constructor is public — anyone can call new Config() and create multiple instances, breaking the pattern.

Problem 2: Not thread-safe — two threads can both pass instance == null simultaneously and each create a separate instance.

Corrected version: 
class Config {
    private static volatile Config instance; // volatile!

    private Config() { }           // ← private constructor

    public static Config get() {
        if (instance == null) {
            synchronized (Config.class) {
                if (instance == null)       // double-check
                    instance = new Config();
            }
        }
        return instance;
    }
}
Adapter Pattern

SQ8. You have a LegacyPrinter with method printOld(String text), but your system expects a Printer interface with print(String text). Write the Adapter and name all four participants.

▼ 
// Target (what client expects)
interface Printer {
    void print(String text);
}

// Adaptee (existing, incompatible class)
class LegacyPrinter {
    void printOld(String text) {
        System.out.println("[LEGACY] " + text);
    }
}

Bridge Pattern

SQ9. Without Bridge, a system has Triangle and Rectangle shapes, each in Red, Blue, Green variants. How many classes are needed without vs with Bridge? Sketch the Bridge solution.

▼
Without Bridge: 2 shapes × 3 colors = 6 subclasses (RedTriangle, BlueTriangle, GreenTriangle, RedRectangle…)

interface Color { String fill(); }

Observer Pattern

SQ10. A stock price tracker must notify a MobileApp and an EmailAlert whenever the price changes. Implement this using the Observer pattern. Label the Subject, Observer interface, and both ConcreteObservers.

▼ 
// Observer interface
interface Observer {
    void update(double newPrice);
}

// Subject (Observable)
class StockTracker {
    private List<Observer> observers = new ArrayList<>();
    private double price;

    void subscribe(Observer o)   { observers.add(o); }
    void unsubscribe(Observer o) { observers.remove(o); }

    void setPrice(double p) {
        this.price = p;
        notifyObservers();           // auto-notify on change
    }
    private void notifyObservers() {
        for (Observer o : observers) o.update(price);
    }
}

// ConcreteObserver 1
class MobileApp implements Observer {
    public void update(double p) {
        System.out.println("Mobile alert: price = " + p);
    }
}

// ConcreteObserver 2
class EmailAlert implements Observer {
    public void update(double p) {
        System.out.println("Email: stock changed to " + p);
    }
}

// Usage
StockTracker tracker = new StockTracker();
tracker.subscribe(new MobileApp());
tracker.subscribe(new EmailAlert());
tracker.setPrice(150.5);
// Both observers notified automatically!
Loose coupling: Subject only knows observers implement Observer — it never references MobileApp or EmailAlert directly. New observers can be added with zero changes to StockTracker.
