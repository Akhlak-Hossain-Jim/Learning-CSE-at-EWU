⬜ Section 1 · White Box Testing

White Box Testing

CFG · DD Graph · Cyclomatic Complexity — testing with full knowledge of internal code structure

📊

Control Flow Graph (CFG)

  • ▸Node — one or more sequential statements (circle)
  • ▸Edge — directed arrow, flow of control
  • ▸Decision node — >1 edge leaving (double circle)
  • ▸Junction node — >1 edge entering
  • ▸Region — bounded area incl. outer region
🗺️

Building a DD Graph — Steps

1
Number executable statements (skip uninitialised declarations)
2
Group sequential statements into one node
3
Draw directed edges; label T/F on decision branches
4
Label nodes alphabetically A, B, C…
5
For loops: condition node is both decision AND junction (back-edge from loop body)
🔢

Cyclomatic Complexity — 3 Formulas

V(G) = e – n + 2p
V(G) = Number of Regions
V(G) = Decision Nodes + 1

e = edges · n = nodes · p = components (usually 1)

⬛ Section 2 · Black Box Testing

Black Box Testing

Testing based purely on functional requirements — no code knowledge required

📋

Decision Table

  • ▸Condition Stub — list of input conditions (rows, top)
  • ▸Action Stub — resulting actions (rows, bottom)
  • ▸Condition Entry — T/F per rule column
  • ▸Action Entry — X marks action fired
  • ▸Don't-care (—) — condition doesn't affect outcome; collapses multiple rules into one
  • ▸n binary conditions → max 2ⁿ rules; 1 test case per rule
📏

Boundary Value Analysis

BVC — Boundary Value Checking
One variable at extreme, others at nominal. Values: Min, Min⁺, Nom, Max⁻, Max.
4n + 1 test cases
Robust Testing
Extends BVC — also tests just beyond valid boundaries (Min⁻, Max⁺).
6n + 1 test cases
Worst-Case Testing
All combos of boundary values — multiple variables at extreme simultaneously.
5ⁿ test cases

🔷 Section 3 · OOP

Object-Oriented Programming

The four pillars: Encapsulation · Abstraction · Inheritance · Polymorphism

🔒

Encapsulation

Bundle data & methods; restrict direct access to fields using private with public getters/setters.

class Account {
  private double balance;
  public double getBalance() {
    return balance;
  }
}
🎭

Abstraction

Hide complexity; show only what's necessary. Use abstract classes or interfaces.

abstract class Shape {
  abstract double area();
  void show() {
    print("Area:" + area());
  }
}
🧬

Inheritance

Child class acquires parent's properties. Promotes reuse. IS-A relationship.

class Dog extends Animal {
  void bark() {
    print("Woof!");
  }
  // inherits name, eat()
}
🎨

Polymorphism

Same method name → different behaviour. Overloading (compile-time) or Overriding (runtime).

Animal a = new Dog();
a.speak(); // "Woof!"
Animal b = new Cat();
b.speak(); // "Meow!"
Q5

OOP · Identify Which Pillar + Explain

For each snippet, name the OOP pillar demonstrated and explain why.

Snippet A
class Student {
  private int age; private String id;
  public int getAge() { return age; }
  public void setAge(int a) { if(a>0) age=a; }
}
Snippet B
abstract class Vehicle {
  abstract void startEngine();
  void refuel() { print("Refueling..."); }
}
class ElectricCar extends Vehicle {
  void startEngine() { print("Silent start"); }
}
Snippet C
class Manager extends Employee {
  Manager(String name, int id) { super(name,id); }
  void addToTeam(Employee e) { /*...*/ }
}
Snippet D
interface Drawable { void draw(); }
class Circle implements Drawable {
  public void draw() { print("○ Circle"); }
}
class Square implements Drawable {
  public void draw() { print("□ Square"); }
}
// Drawable d = new Circle(); d.draw(); → "○ Circle"
Snippet A🔒 Encapsulation

age and id are private — direct external access is blocked. The class controls access through public methods. The setter validates input (age > 0), protecting the object's state from invalid data. This is the essence of encapsulation.

Snippet B🎭 Abstraction

Vehicle is abstract — it defines what any vehicle must do (startEngine), without defining how. The internal details are hidden. ElectricCar fills in the specific implementation. Callers work with Vehicle without needing to know what's inside.

Snippet C🧬 Inheritance

Manager extends Employee — it inherits all fields (name, id) and methods without rewriting them. The super(name, id) call delegates construction to the parent class. Manager IS-A Employee with extra capability. This is single-level inheritance.

Snippet D🎨 Polymorphism

Both Circle and Square implement Drawable. The same call d.draw() produces different output depending on the actual object type at runtime. This is runtime polymorphism (method overriding). The calling code doesn't need to know the concrete type — it just calls draw().

Q6

OOP · Design a University Class Hierarchy

Design a class hierarchy for a University System:

  • Interface Printable with printDetails()
  • Base class Person (implements Printable) — name (private), id (private), getName(), getInfo()
  • Student extends Person — gpa (private), enroll()
  • Faculty extends Person — department (private), teach()
  • GradStudent extends Student — advisor, submitThesis()

Show code and identify which OOP pillar each part demonstrates.

Class Hierarchy Diagram

Java Pseudocode

interface Printable { void printDetails(); }  // ABSTRACTION

class Person implements Printable {
  private String name; private int id;  // ENCAPSULATION
  Person(String n, int i) { name=n; id=i; }
  public String getName() { return name; }  // ENCAPSULATION
  public String getInfo() { return name+", ID:"+id; }
}

class Student extends Person {   // INHERITANCE
  private double gpa;
  Student(String n, int i, double g) { super(n,i); gpa=g; }
  void enroll() { print(getName()+" enrolled"); }
  public void printDetails() {  // POLYMORPHISM (override)
    print("Student: "+getInfo()+", GPA:"+gpa);
  }
}

class GradStudent extends Student {  // INHERITANCE (multi-level)
  private String advisor;
  void submitThesis() { print("Thesis submitted"); }
  public void printDetails() {  // POLYMORPHISM
    print("GradStudent, Advisor:"+advisor);
  }
}

class Faculty extends Person {  // INHERITANCE
  private String dept;
  void teach() { print(dept+" class in session"); }
  public void printDetails() { print("Faculty:"+getInfo()); }
}

Pillars Demonstrated

Encapsulation: private name, id, gpa, dept — access via public methods only
Abstraction: Printable interface hides how details are printed
Inheritance: Student, Faculty ← Person; GradStudent ← Student (multi-level)
Polymorphism: printDetails() gives different output per class

Singleton Pattern (Creational)

Intent & When to Use

Ensures a class has only one instance and provides a global access point. Solves: controlling access to a shared resource.

Use for: Database connections, logging, config managers, thread pools
Key rules: ① Private constructor   ② Static instance field   ③ Public static getInstance()

Structure (UML)

Singleton
- instance: Singleton {static}
- Singleton()  // private
+ getInstance(): Singleton {static}
+ doWork(): void

Implementation

class Logger {
  private static Logger instance = null;          // ① static field
  private Logger() { }                               // ② private constructor
  public static synchronized Logger getInstance() { // ③ factory method
    if (instance == null) instance = new Logger();
    return instance;
  }
  public void log(String msg) { print("[LOG] "+msg); }
}
Logger a = Logger.getInstance();
Logger b = Logger.getInstance();  // a == b → true
Q7

Singleton · Application Config Manager

A web app needs a ConfigManager that loads settings (db_url, max_connections, timeout) from a file exactly once. Multiple modules request the config. Implement Singleton and prove only one instance is created.

class ConfigManager {
  private static ConfigManager instance = null;
  private String dbUrl; private int maxConn; private int timeout;

  private ConfigManager() {               // private — file loaded once here
    dbUrl   = "jdbc:mysql://localhost:3306/mydb";
    maxConn = 100;
    timeout = 30;
    print("Config loaded from file.");
  }
  public static synchronized ConfigManager getInstance() {
    if (instance == null) instance = new ConfigManager();
    return instance;
  }
  public String getDbUrl()  { return dbUrl; }
  public int getTimeout()   { return timeout; }
  public int getMaxConn()   { return maxConn; }
}
// Module A
ConfigManager cfg1 = ConfigManager.getInstance(); // prints "Config loaded"
// Module B
ConfigManager cfg2 = ConfigManager.getInstance(); // no print — same instance
print(cfg1 == cfg2);  // true → both point to same object
The synchronized keyword makes getInstance() thread-safe. The "Config loaded" message prints exactly once, proving the constructor runs only once regardless of how many times getInstance() is called.

Adapter Pattern (Structural)

Intent

Converts the interface of a class into another interface that clients expect. Allows incompatible classes to collaborate.

Real analogy: A power plug adapter — UK plug (existing) → EU socket (expected interface). Same electricity, different connector.

Use when: Integrating a third-party library with an incompatible interface, or reusing a legacy class in a new system.

Implementation Example — XML to JSON Adapter

// Target interface (what new code expects)
interface JsonAnalytics {
  void analyzeJson(String json);
}
// Adaptee (existing class with incompatible interface)
class XmlDataSource {
  public void loadXml(String xml) { print("Processing XML: "+xml); }
}
// Adapter — wraps Adaptee, implements Target
class XmlToJsonAdapter implements JsonAnalytics {
  private XmlDataSource src;
  XmlToJsonAdapter(XmlDataSource s) { src = s; }
  public void analyzeJson(String json) {
    String xml = convertJsonToXml(json); // translate
    src.loadXml(xml);
  }
  private String convertJsonToXml(String j) { return "<data>"+j+"</data>"; }
}
// Client only knows JsonAnalytics — unaware of XmlDataSource
JsonAnalytics analytics = new XmlToJsonAdapter(new XmlDataSource());
analytics.analyzeJson("{user:'Akhlak'}");
Q8

Adapter · Legacy Payment System

You have an existing OldPaymentGateway with method makePayment(int cents). Your new checkout system expects a PaymentProcessor interface with processPayment(double dollars). Write an Adapter class.

// Target interface (new system's expectation)
interface PaymentProcessor {
  void processPayment(double dollars);
}
// Adaptee (legacy — cannot be changed)
class OldPaymentGateway {
  public void makePayment(int cents) {
    print("Paid "+cents+" cents via legacy gateway");
  }
}
// Adapter — bridges the two interfaces
class PaymentAdapter implements PaymentProcessor {
  private OldPaymentGateway legacy;
  PaymentAdapter(OldPaymentGateway g) { legacy = g; }
  public void processPayment(double dollars) {
    int cents = (int)(dollars * 100);  // convert dollars → cents
    legacy.makePayment(cents);
  }
}
// New checkout system uses PaymentProcessor — doesn't know about OldPaymentGateway
PaymentProcessor pay = new PaymentAdapter(new OldPaymentGateway());
pay.processPayment(29.99);  // → "Paid 2999 cents via legacy gateway"
Target: PaymentProcessor (what new code expects)
Adaptee: OldPaymentGateway (legacy, incompatible)
Adapter: PaymentAdapter — translates dollars→cents
Client: Checkout system — uses only PaymentProcessor

Bridge Pattern (Structural)

Intent

Splits a large class into two separate hierarchies — Abstraction and Implementation — which can vary independently.

Problem it solves: Without Bridge, adding M shapes × N renderers = M×N classes. With Bridge: M + N classes.
Real analogy: A remote control (abstraction) works with any TV or Radio (implementation). The remote doesn't need to change when you buy a new device.

Implementation — Remote Control + Device

// Implementation hierarchy (Device side)
interface Device {
  void enable(); void disable();
  int getVolume(); void setVolume(int v);
}
class TV implements Device {
  public void enable()  { print("TV ON"); }
  public void disable() { print("TV OFF"); }
  public int  getVolume()        { return volume; }
  public void setVolume(int v)  { volume = v; }
}
class Radio implements Device { /* similar */ }

// Abstraction hierarchy (Remote side)
class BasicRemote {
  protected Device device;  // ← the Bridge
  BasicRemote(Device d) { device = d; }
  void power() {
    if (device.isEnabled()) device.disable();
    else device.enable();
  }
  void volUp() { device.setVolume(device.getVolume() + 10); }
}
class AdvancedRemote extends BasicRemote {  // extends Abstraction
  AdvancedRemote(Device d) { super(d); }
  void mute() { device.setVolume(0); }
}
// Mix-and-match freely:
new BasicRemote(new TV()).power();       // TV ON
new AdvancedRemote(new Radio()).mute(); // Radio muted
Q9

Bridge · Notification System

You need a notification system. Notifications can be Urgent or Normal (abstraction side). Delivery channels are Email or SMS (implementation side). Without Bridge: 4 classes (UrgentEmail, NormalEmail, UrgentSMS, NormalSMS). Show how Bridge reduces this to 2 + 2 classes that scale much better. Implement it.

Without Bridge: Adding a new channel (WhatsApp) needs 2 more classes (UrgentWhatsApp, NormalWhatsApp). Adding a new type (Emergency) needs 3 more. Scales as M × N.

With Bridge: Add WhatsApp → 1 new class only. Scales as M + N.

// Implementation hierarchy (Channel)
interface MessageChannel {
  void send(String recipient, String message);
}
class EmailChannel implements MessageChannel {
  public void send(String r, String m) {
    print("Email to "+r+": "+m);
  }
}
class SmsChannel implements MessageChannel {
  public void send(String r, String m) {
    print("SMS to "+r+": "+m);
  }
}

// Abstraction hierarchy (Notification type)
abstract class Notification {
  protected MessageChannel channel;  // ← the Bridge
  Notification(MessageChannel ch) { channel = ch; }
  abstract void notify(String recipient, String msg);
}
class UrgentNotification extends Notification {
  UrgentNotification(MessageChannel ch) { super(ch); }
  public void notify(String r, String m) {
    channel.send(r, "🚨 URGENT: "+m);
  }
}
class NormalNotification extends Notification {
  NormalNotification(MessageChannel ch) { super(ch); }
  public void notify(String r, String m) {
    channel.send(r, "ℹ Info: "+m);
  }
}
// Mix freely — no extra classes needed!
new UrgentNotification(new EmailChannel()).notify("admin", "Server down");
// Email to admin: 🚨 URGENT: Server down
new NormalNotification(new SmsChannel()).notify("user", "Your order shipped");
// SMS to user: ℹ Info: Your order shipped

Observer Pattern (Behavioral)

Intent

Defines a one-to-many subscription mechanism. When an object (Publisher/Subject) changes state, all dependents (Subscribers/Observers) are automatically notified.

Real analogy: A YouTube channel (Subject). Subscribers get notified when a new video (event) is uploaded. They can subscribe or unsubscribe any time.

Structure

Implementation Example — Event Editor

// Observer interface
interface EventObserver {
  void update(String eventType, String data);
}
// Concrete Observers
class EmailAlert implements EventObserver {
  public void update(String t, String d) { print("Email: "+t); }
}
class Dashboard implements EventObserver {
  public void update(String t, String d) { print("Dashboard refreshed: "+d); }
}
// Subject (Publisher)
class EventManager {
  private List<EventObserver> listeners = new ArrayList();
  public void subscribe(EventObserver o)   { listeners.add(o); }
  public void unsubscribe(EventObserver o) { listeners.remove(o); }
  public void notify(String type, String data) {
    for (EventObserver o : listeners) o.update(type, data);
  }
}
Q10

Observer · Stock Price Tracker

A StockMarket object tracks a stock price. Three observers are registered: MobileApp, WebDashboard, and EmailAlert. Whenever the stock price changes, all three should be notified automatically. Implement using Observer pattern.

// Observer interface
interface StockObserver {
  void update(String symbol, double price);
}

// Concrete Observers
class MobileApp implements StockObserver {
  public void update(String s, double p) {
    print("📱 Mobile: "+s+" = $"+p);
  }
}
class WebDashboard implements StockObserver {
  public void update(String s, double p) {
    print("🌐 Web chart updated: "+s+" now $"+p);
  }
}
class EmailAlert implements StockObserver {
  public void update(String s, double p) {
    print("📧 Email: "+s+" price alert $"+p);
  }
}

// Subject (Publisher)
class StockMarket {
  private List<StockObserver> observers = new ArrayList();
  private String symbol;
  private double price;

  StockMarket(String sym) { symbol = sym; }

  public void addObserver(StockObserver o)    { observers.add(o); }
  public void removeObserver(StockObserver o) { observers.remove(o); }

  public void setPrice(double newPrice) {  // triggers notification
    price = newPrice;
    notifyAll();
  }
  private void notifyAll() {
    for (StockObserver o : observers) o.update(symbol, price);
  }
}

// Usage
StockMarket market = new StockMarket("AAPL");
market.addObserver(new MobileApp());
market.addObserver(new WebDashboard());
market.addObserver(new EmailAlert());

market.setPrice(175.50);
// 📱 Mobile: AAPL = $175.5
// 🌐 Web chart updated: AAPL now $175.5
// 📧 Email: AAPL price alert $175.5
Subject: StockMarket — holds observer list, triggers events
Observers: MobileApp, WebDashboard, EmailAlert
Loose coupling: Subject doesn't know concrete observer types
Runtime subscribe: Observers can be added/removed dynamically
